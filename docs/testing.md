# Testing

Stitchwort's guarantees are only as good as the compiler's correctness, so the tests have several layers. Each layer catches mistakes the others can't.

## Tiers

Tests are only useful while they aren't friction, so they run in four tiers, each with a time budget. The budgets assume the release test binaries are built (`task build:tests`) and are for this 14-core Mac, but for the quick tier's, which is for a 10-core M1 Pro. Run them through [Task](https://taskfile.dev) (`Taskfile.yml`; `task --list` shows the menu), inside `nix develop`.

| Tier | Command | Budget | When | What |
|---|---|---|---|---|
| lane | `task test:lane AREA=…` | under 10 s | while working, in a subagent lane | a handful of fast tests for one area (the map below) |
| quick | `task test:quick` | under 90 s on a 10-core M1 Pro | in Overmind's rolling broad check of each pushed commit (D3546), or by hand; not per batch: a batch's verifier runs a selection instead (D3545) | feature-set check, rustfmt, a `cargo check` of the web crate for wasm32 (catches 32-bit `usize` overflows; about 15 s after a change to `crates/core`), then a wide smoke test: every lane area but `goals`, a quarter of the accepted, rejected and soundness examples (and of the named-argument differential's), 14 of the AoC days' answers (spread across 2021, 2024 and 2025, the slowest 2021 days left out; all of them in the broad tier and up), a quarter of the examples' and projects' hash snapshots, every extraction example's generated JS and `.d.ts` snapshots, and the driver's navigation snapshot that prints prelude positions |
| broad | `task test:broad` | under 5 minutes | with Matt's approval, or in compute mode; `nix flake check` runs the same | the quick tier plus sampled sweeps, the doctests, `builtins` in the debug profile (built first, then run beside the nextest profile), the board's tests |
| all | `task test:all` | hours | paused (Matt, 12 Nov 2026) | every test, every sweep over the whole corpus, the all-only tests |

`task test:lanes-nonempty` fails, naming the profile, if any `[profile.lane-*]` in `.config/nextest.toml` selects no tests (a filter that matches nothing passes silently; `lane-aoc` once did). It runs `cargo nextest list` (nothing is run) for each lane profile it finds in the file, so a new one is covered at once; it costs about 1 s per profile with the binaries built (about 13 s for all), so `task test:broad` runs it, not the quick tier (it is not part of `nix flake check`). A filter naming a binary that does not exist is already a nextest config error.

`task test:one -- FILTER` runs the tests matching a nextest filter (arguments after `--` reach nextest with their spaces and quotes intact: the task passes them through the shell as written, and `test:affected` passes its filter as a single argument) (a name substring, or `-E 'binary(lsp)'`), at the broad sample. A bare name matches test names only, so a whole test binary needs `-E 'binary(name)'` (for example `task test:one -- -E 'binary(hash_stability)'`, with `EXAMPLES=` for particular examples). `task test:gate` is `nix flake check` (the broad tier in the Nix sandbox, plus a build from clean), and `task test:all:nix` builds `.#stitchwort-all` (the all tier in the sandbox; only when Matt asks).

### The test selector

After each batch of merges, a selector (a model following [test-selector.md](test-selector.md)) picks what to run instead of the fixed quick tier (SW-1098, D2221; on trial, see [workflow.md](workflow.md), "Checks after a merge"). Its tools:

- `task test:inventory [-- --junit PATH[@SCALE] ...]` (`dev/test-inventory`) writes `target/test-inventory.json`, not committed: every test nextest knows (release, workspace), the profiles that include it, whether it is in the `corpus-sweeps` group, and its last known time. Times are kept in `target/test-timings.json`, per test and tier, the fastest of its last five runs counting (the broad runs that supply most times are loaded, and a lane's tests cost about their best time; SW-1778); each run folds in the `--junit` files named and any `target/nextest/*/junit.xml` in the checkout (`PATH@0.55` scales a run made under load; the file's parent folder, if a tier, says which tier it is, else `--tier`). Tests never run in a recorded JUnit file (the broad-only ones) have an unknown time, which the estimate counts as 3 s. Refresh after any run; `task test:selected` folds its `target/nextest/quick/junit.xml` into the timings store when it ends, so its times survive the next run overwriting that file.
- `task test:inventory -- --estimate '<filterset>'` lists what a filterset selects and estimates its wall time on 10 cores: `max(sum of times / 8.4, the corpus-sweeps tests' sum, the longest test)`. On the quick tier itself (963 s of test time) it gives 115 s; measured, about 110 s.
- `task test:selected -- '<filterset>'` (`dev/run-selected`) is the feature-set check, `cargo fmt --check`, then nextest as `test:quick` runs it (`STITCHWORT_TIER=quick`, the memory guard at the broad cap of 16 GB, not the quick tier's 4 GB, since a selection may include tests the tier leaves out (SW-1760), the `quick` profile) but with the given filterset in place of the profile's own, so it can reach tests the tier leaves out. `EXAMPLES=name` or `EXAMPLES=one,two` applies as in the lanes; `SELECTOR_ESTIMATE=N` records the selector's estimate. It folds the run's JUnit times into `target/test-timings.json`, then, in the main checkout only (the file is tracked, and a lane's worktree would dirty it; it is told by `git rev-parse --git-dir` against `--git-common-dir`), appends a line to `dev/selector-log.tsv` (date, commit, estimated and actual seconds, result, failed tests, `EXAMPLES`, filterset), from which the trial is scored.
- `python3 dev/test-inventory_test.py` tests the script.

### The affected-test selection

`task test:affected` (`dev/test-affected`, SW-1752) works out the selector's filterset from a diff by rule, so a lane or a verifier doesn't have to pick tests by hand. It reads the changed files (default: this checkout's work since its merge base with `main`, committed or not; `-- --range OLD..NEW` for a range, such as a merged batch; `-- --paths F...` for files), and maps them to tests with the table in `dev/test-affected.toml`:

- Rust sources by area: `crates/elab/src/omega*.rs` to the omega tests, `matching*` to the match tests and `match` examples, `crates/lsp/` to `lane-lsp`, and so on; a source file with no rule falls back to its crate's tests plus the lane areas of the crates that depend on it (`cargo metadata`). A changed `crates/X/tests/NAME.rs` selects its binary, or when the diff only touches some functions, those tests first and the binary's quick tests after.
- `crates/elab/src/std/**` to the library tests, the prelude and example hash snapshots, `pinned_hashes` and the formatting check; the core files and `order.txt` add `bound_to_the_prelude` and the navigation snapshot. `examples/**` and `*.snap` files to those examples' sweeps (it sets `EXAMPLES`, dropping any part that matches no example, which would fail the run). `aoc/src/Aoc/YearY/DayD/**` to that day's `aoc_answers` test (and a reminder to run `task audit:touched`); `games/**` to the roguelike tests.
- `docs/guide/**` and `docs/tutorial/**` (their examples are checked and the guide quotes the compiler's output) to the `guide` tests; a change to the parser, kernel, elaborator, driver or CLI adds the guide's quoting test at rank 3 and the quick tests (under 3 s each) of the driver's and CLI's feature test binaries at rank 2, as `extra` rules: they add to the file's other rules without taking it out of the fallback ones.
- Every test binary is reached by some rule or lane area, or listed with a reason in `NOT_REACHED` in `dev/test-affected_test.py` (broad-tier benchmarks and fuzzers); a test there fails otherwise, so a new binary gets a rule when it is added. `cheap_only` rules leave their slow tests out of the filterset itself, not just the estimate.
- Documentation and board files otherwise select nothing: "NOTHING TO RUN".

The fixed core (kernel, parser, one AoC day) is always in. Each rule has a rank (1 the tests of the thing that changed, 2 what reads it, 3 crate-graph dependents). The tool estimates the time from the inventory's timings, as `--estimate` does; over the budget (`--budget`, default 90 s) it cuts whole rules, the highest rank first (every rule of a rank before any of the next, and a put-back never skips a rank; the rank 1 rules a changed file maps to are the changed code's own tests and go last: only if those alone are over the budget does it keep the cheapest that fit, and it warns loudly, naming the changed files left without a test of their own), and says what it cut and how much of its own time each held. It checks that the filter selects tests: from the inventory always, and from nextest (`--validate`, and always when running, since a filter naming no binary can look like a pass). `task test:affected -- --dry-run` prints the filter, `EXAMPLES` and estimate only; `--explain` lists each changed file's rules and each rule's tests, so the reason for every test is visible.

Extend the table, not the script: a rule is `paths` globs, a `rank` and `select` clauses (`package`, `binary`, `test` regex, `profile`). `python3 dev/test-affected_test.py` tests the mapping, on the built inventory too when there is one. The inventory goes stale when tests are added or renamed (`task test:inventory`); a rule that selects no test in it is reported, and `task test:affected` (which runs) rebuilds the inventory by itself and selects again when that happens (`-- --refresh` does so on a dry run); a checkout's first refresh starts from the main checkout's timings. A changed test file whose diff touches only helpers (no test function) selects the whole binary at the top rank. The `lsp-sessions` test group (`stitchwort-lsp` `features` and `memory`, three at a time) keeps a cold run of those under the 4 GB quick cap: ten at once peaked past it. The files of the library are not mapped to the examples and AoC days that use them: which library files a program loads follows the types of its dot calls (`m.insert` reaches `Map.insert` without writing `Map`), so a grep for names misses users, and only the driver could say; the sweeps' sample stands in. The earlier whole-area version (`dev/t affected`, `task test:areas`) is retired (SW-1793): `task test:areas` now prints a pointer here and fails. It also ran checks that are not nextest tests, by changed path; rules with `commands` do that now (SW-1794): the board's node tests for `board/` code and `epics.json`, `bash -n` on a changed shell script (by its shebang), the `_test.py` beside a changed `dev/` tool, a parse and `nix flake show` of `flake.nix`, and the playground's colouring tests for `web/` scripts. A rule's `commands` are shell commands run from the repository root, each with an estimated `seconds` that counts towards the budget (so they can be cut like tests, and `--dry-run` lists them under `COMMANDS`); `{path}` or `{test}` in a command makes one per changed file. `--run` runs the ones estimated at 10 s or less before nextest and the rest after it, and ends with `COMMAND RESULTS`, a pass or FAIL for each (the exit status fails if any does). Checks too slow or heavy to run here are a rule's `manual` lines, printed as `RUN BY HAND`: `task test:browser` (builds the WebAssembly bundle, about 35 s) and `task test:vscode` (needs `npm ci`). Clippy (`task lint`) is not selected; run it by hand.

### Features

Every dev and test build compiles the workspace with one set of features, so each crate is compiled once per profile whatever `-p` selects, and a lane's build can be as narrow as its tests. Cargo unifies features per invocation, over only what the invocation builds, so a feature a crate turns on in a dev-dependency reaches `-p` and `--workspace` runs differently unless every crate asks for the same.

- **Where the set is.** `crates/dev-features` has no code; its dependencies are the set: `stitchwort-core` with `reference` (the reference evaluator, for the differential tests) and `stack-check` (see "Stack"), `stitchwort-syntax/stack-check`, `stitchwort-rt/alloc-trace` (see "The allocation trace"), the CLI's `native` (through its `dev` feature), and the features other workspace crates switch on in third-party crates (`nix`, `rustix`, `object`, `cranelift-codegen`, `smallvec`, `syn` and a few more), so that a `-p` build has them too. The tested crates (all but `syntax` and `fmt`) depend on it as a dev-dependency, and `stitchwort-cli` and `stitchwort-bench` also in normal builds (`dev` feature; `bench` always), so `-p X` has the same set as `--workspace`. A new crate with tests adds the dev-dependency; a new feature a test needs goes in `crates/dev-features/Cargo.toml`.
- **What builds it.** `task build` passes `--features stitchwort-cli/dev` (Taskfile.yml `DEV_FEATURES`); the test tasks don't need to. A bare `cargo build` without the feature, or `cargo run -p stitchwort-cli`, is a different variant, one extra compile.
- **Distributed builds differ**: the flake's `stitchwort-bin` and `stitchwort-native-bin`, and the WebAssembly bundle, build `-p` the crates they ship without `dev-features`: no reference evaluator, stack check or allocation trace in the binary people run. (They need the `-p`: a root build also builds `stitchwort-bench`, which depends on `stitchwort-dev-features`, and Cargo would unify the dev features into the binary. `dev/features-check`, in `task test:features` and so the quick tier, fails if `cargo tree -e features` for those arguments shows `test-bypass`, `reference`, `stack-check` or `alloc-trace`.) (`stitchwort-native-bin` has `native`, as before.) `syntax` and `fmt` alone (`-p stitchwort-syntax`, `lane-syntax`) build a leaf variant of `syntax` without `stack-check`; nothing above them is affected.
- **Run-time cost.** `alloc-trace` is compiled into the dev set but records only between `alloc_trace::start()` and `finish()`: a hook is a relaxed load of a counter and a branch until then. Measured on release AoC runs (2024 day 6, 2025 days 8 and 9; CPU user+sys, the variants interleaved, five or six rounds each, the minimum of the rounds): no difference from the build without the feature (within 3%, either way); a hook that looked up a thread-local each time cost 6 to 10%. `stack-check` and `reference` made no difference either (under 1%): the first runs once per top-level operation, the second only adds code.
- **Which packages a test task builds.** `task test:one`, `task test:lane` and `task test:selected` ask `dev/test-scope` which packages the profile's and the `-E` filtersets can reach, and pass `-p A -p B` instead of `--workspace`: `task test:lane AREA=lsp` builds the CLI's test binaries and their dependencies, not the 130 test targets of the workspace. Where a filterset names no package or test binary (a bare name filter such as `task test:one -- named_calls`, or `test(...)` alone) it gives `--workspace`, which builds the same libraries and every test binary: slower to build when sources changed, never a new variant. `dev/test-scope --profile lane-core` shows what a lane gets. The quick, broad and all tiers are `--workspace`.
- **Checking it.** `task test:features` (`dev/features-check`, 3 s, compiles nothing) fails if any crate would be compiled with two feature sets across `task build`, the workspace test build and each `-p` test build; run it after adding a crate, a feature or a dev-dependency. `cargo tree` prints the features per crate; the compiled variants are in `target/release/deps/libstitchwort_elab-*.rlib` (one per feature set; more than one means an invocation differs). For the unit graph of an invocation, `RUSTC_BOOTSTRAP=1 cargo test --release -p … --no-run -Zunstable-options --unit-graph | jq` gives the features of every unit without compiling.

### Allocator

Every test binary uses mimalloc, as the CLI does: the system allocator is slow when many threads allocate at once (musl's, on the Linux build: the elaborator fuzzer's 200 cases took 229 s, against 37.5 s) and on macOS it keeps freed blocks, so memory tests would not measure what the CLI does. The `#[global_allocator]` lives in `stitchwort-test-alloc`, a dev-dependency of each crate; a test target opts in with `use stitchwort_test_alloc as _;` at the end of its root file (for a unit-test binary, `#[cfg(test)] use stitchwort_test_alloc as _;` in `lib.rs`). I chose a shared crate over a line of `#[global_allocator]` per target so that the choice is made in one place. `dev/test-alloc-check` (in `task test:features`, so the quick tier) lists the test targets from `cargo metadata` and fails if one lacks the line, its own `#[global_allocator]` (the counting allocators of `rt/tests/effect_alloc.rs` and `state_match.rs`, which wrap the system allocator on purpose), or a `// test-alloc:` comment saying where its allocator comes from (the targets that link `stitchwort-bench`, whose counting allocator wraps mimalloc). A second `#[global_allocator]` in one binary is a compile error. Distributed builds are unaffected: the crate is a dev-dependency only.

### How a tier is chosen

Two things make a tier, and the tasks set both:

- **Which tests run** is a [nextest profile](https://nexte.st/docs/configuration/) of the tier's name in `.config/nextest.toml`, through its `default-filter` (a [filterset](https://nexte.st/docs/filtersets/)): `quick`, `broad`, `all`, and `lane-AREA` for each lane area. A filter on the command line is intersected with it (`task test:quick -- -E 'package(stitchwort-core)'`). nextest has no includes, so the `quick` profile's filter is generated from the lane profiles' by `dev/nextest-quick` (the lanes but `lane-goals` and `lane-web`, plus a few wider parts); edit a lane, run it, and `python3 dev/test-affected_test.py` fails while the file is stale (SW-1778).
- **Every dev and test build has one set of features** (below), including native code, so that `crates/cli/tests/running/build.rs` tests `build --native`; the default `stitchwort` leaves Cranelift out.
- **How much of a corpus a sweep covers** is the environment variable `STITCHWORT_TIER` (`lane`, `quick`, `broad` or `all`), read by `stitchwort_driver::driver::tier()`, which falls back to nextest's `NEXTEST_PROFILE` when the variable is unset (the profiles have the tiers' names, `lane-AREA` being `lane`, and `default` means `broad`), so the profile alone is enough. A corpus sweep (a test that checks every example, std file or AoC day) takes `tier_sample(items, broad_stride)`: a fixed sample, every `broad_stride`-th item in sorted order in the broad tier, every `4 × broad_stride`-th in quick and lane, and all of them in all. A test or part of one that only the all tier runs asks `all_tier(name)`, which prints what was skipped.

Both are needed: a profile can only include or leave out a whole test, and the sweeps are single tests whose cost is the size of the corpus. The profiles keep the lists of what runs in one file that nextest checks; the environment variable keeps each sweep's sample next to the code that knows what is in its corpus. A sweep's assertion about how much it covered (say, "more than 1,000 arguments named") scales with the sample, and is exactly the old one in the all tier.

What only the all tier runs: `task test:verify-cache` (`stitchwort test --verify-cache` on aoc and games/rogue, D2379), the AoC project in the std_library, rewind and check-cache comparisons (and in `fmt_hashes`'s, all the projects, AoC included; every tier de-formats and formats the whole corpus in memory, since the repository is kept formatted and the formatter would change almost nothing, and loads a fixed sample of the files and projects, SW-2962, SW-3026), `a_check_cancelled_part_way_rewinds`, the bench `examples` benchmark (in `baseline`, and repeated in `repeat`), `search_bench`'s proof-use benchmark, the whole corpus in each sampled sweep (below), and `rt`'s AoC sweeps `aoc_agrees` and `every_aoc_main_lowers` (36 to 38 minutes each in the broad tier on 31 Oct 2026; SW-839 is to give the broad tier a fast check of AoC lowering instead). Those two check the AoC project a part at a time (`Aoc.Common` and each day, `differential::aoc_parts`), side by side, and `AOC_PARTS=Year2024.Day01,Common` runs only the parts named, to try a few days in the all tier (SW-2962).

| Sweep | Daily share | Merge and lane share |
|---|---|---|
| `std_library` `lazy_loading_changes_nothing_*`, `driver` `check_cache` and `rewind` examples | every 8th file (and every 4th project) | every 32nd |
| `differential` `the_evaluators_agree_on_the_prelude_and_every_example`, `conv_shortcut` | every 4th | every 16th |
| `resources` `running_out_at_any_point_only_ever_means_no_answer` (not a sweep, but sampled the same way) | every 4th of its 161 work limits | every 16th |
| `hash_stability` `examples` and `projects` | all | every 4th |
| `extract` `run_lines_*`, `random_inputs_*` | every 2nd | every 8th |
| `cli` `examples` (every folder), `cli` `check_cache` projects | all (projects: every 4th) | every 4th (projects: every 16th); all of those matching any `EXAMPLES` substring when it's set |

When the broad tier grows past its budget, cut it from nextest's own times (`target/nextest/broad/junit.xml`, or the `SLOW` lines): give the slowest sweep a larger stride, or move a test to all only, rather than re-running to see. The quick tier likewise (`target/nextest/quick/junit.xml`); on a loaded machine compare tests with each other, not with the budget.

**Sizes that depend on the tier.** Besides the sampled sweeps, the constant-stack tests scale with the tier: `n2b` `tail_calls_of_every_shape_run_in_constant_stack` runs 10 million iterations on a 64 MiB stack in broad and all, and 1 million on 20 MiB in quick and the lanes; `n3` `tail_applies_run_in_constant_stack` runs 1,000,000 tail applies on 64 MiB in broad and all, 250,000 on 18 MiB in quick and the lanes. The native crossing reserves 16 MiB of any stack (`HOST_ROOM` and `HELPER_ROOM`, `crates/rt/src/native_abi.rs`), so the smaller stacks leave 4 MiB and 2 MiB to run in, which a leak of 8 (or 16) bytes an iteration still overruns: the same point, with a tenth of the work.

### Memory

Several worktrees test on one 48 GB Mac at once, and a tier that runs away can lock the machine up (it did, 26 Oct 2026: the broad tier at about 50 GB). Three things bound it.

**A cap on every test task.** Each task that runs tests (`test:lane`, `test:quick`, `test:broad`, `test:all`, `test:one`, `test:affected`, the `snap:*` tasks, `guide:update`, `bench`) runs its command under `dev/memguard`. About twice a second it sums the memory of the command's whole process tree (the physical footprint on macOS, as `top` shows it; RSS on Linux), leaving out the compiler and linker when cargo builds first. Past the cap, it prints the cap, the total and the five biggest processes with their command lines (a nextest child's names its test: `…/deps/examples-… --exact accepted_examples_check`), kills the tree (SIGTERM, then SIGKILL two seconds later) and exits 137, so the task fails.

| Tier | Cap | Measured peak |
|---|---|---|
| lane | 3 GB | up to 0.7 GB (`aoc`, `hashes`, `examples`, `std`, `core`) |
| quick | 4 GB | 2.5 to 3.1 GB (2 Nov 2026, SW-1076; 1.7 GB on 26 Oct, and killed twice at the old 3 GB cap). One process is 1.4 to 1.5 GB: `search --at` of a goal with `≤` (`what_closes_a_goal`) loads most of the library, and did so before function equations. The rest are 0.1 to 0.4 GB each |
| broad, `test:one`, `test:affected`, `test:selected`, `guide:update`, `bench` | 16 GB | 11.5 GB (31 Oct 2026, SW-921), of which `lsp` `a_newer_edit_cancels_the_check_running` 8.4 GB and `operators` `primitive_and_uniform_lowering_agree_on_the_library_and_aoc` 2.4 GB. Before, over 16 GB when `lsp` `aoc_navigation_matches_check_index` (7.9 GB alone) ran beside `resources` `running_out_at_any_point_only_ever_means_no_answer` (6.7 GB, macOS's allocator keeping freed blocks; under 400 MB on mimalloc) |
| all, `snap:*` | 16 GB | 10.95 GB (4 Nov 2026, SW-1175, 2h 5m), of which `rewind` `a_check_cancelled_part_way_rewinds` 9.6 GB and `search_at_aoc` `search_at_on_aoc_goals` 1.3 GB. Before SW-1181 it was killed at 16 GB: `differential` reached 14.7 GB (30 GB uncapped) on match-bounded-search's branch equations |

The peaks are from 26 Oct 2026; the lane and quick caps are about 1.5 to 2 times them. The caps are the `MEM_CAP_*` variables at the top of `Taskfile.yml`. `STITCHWORT_MEM_CAP_GB` overrides any of them for one run (`STITCHWORT_MEM_CAP_GB=24 task test:all`; `0` for no cap), and `STITCHWORT_MEM_REPORT=1` prints the peak and the biggest processes at the peak when the command ends, for measuring a tier. A kill means a test regressed, or the cap is out of date: look at the named test before raising the cap. `ulimit -v` is no use here (macOS doesn't enforce it), hence the polling.

**On a smaller machine (SW-2413).** The caps are sized for the 48 GB Mac. On Overmind, a 15 GiB Linux laptop, the all tier's 16 GB cap could never fire: the run peaked at 12.7 GB on the `all` profile's 6 test threads and was stopped for low memory at test 1105 of 2321, with nothing naming a test (8 Nov 2026). Two things now fit a tier to the machine:

- *The cap.* `dev/memguard` lowers a cap above three quarters of the machine's physical memory to that share (`MACHINE_SHARE`), and says so: `cap 16 GB lowered to 11.6 GB, 75% of this machine's 15.5 GB`. It only ever lowers a cap, so the Mac's are unchanged. `STITCHWORT_MEM_CAP_GB` is taken as given, without the lowering.
- *Fewer tests at once.* On a machine under 24 GiB (`MemTotal` in `/proc/meminfo`), the broad and all tiers' nextest runs pass `--test-threads 4` (the `TIER_THREADS` variable in `Taskfile.yml`), not the profile's 8 or 6. Memory is set by how many tests run at once, so this is what lets the tier finish, where the cap alone would only turn the low-memory stop into a memguard kill. macOS has no `/proc/meminfo`, so the Mac keeps the profiles' counts.

A tier's `MEM_CAP_*` given on the command line (`task test:all MEM_CAP_ALL=12`) reaches its steps: `test:broad` and `test:all` pass it on to `test:broad:steps` and `test:all:steps`, which run as a task of their own under `dev/tier-report`.

**One process fills a cold cache (SW-1751).** After any change to the compiler the check caches the tests share are empty, and nextest starts every test in a process of its own, so without care each of them checks the library itself, all at once. Two guards: the tests that share the `search-cache` (`doc`, `search`, `search --at`, the search benchmarks) are ordered in `.config/nextest.toml` (as is the test std cache's filler, `pinned_hashes` `every_binding_by_hash_applies_to_the_library`, at the top priority, so that other tests are not holding slots waiting for its lock; SW-1765: broad-tier `examples` + `hash_stability`, cold, 111 s to 48 s wall, 956 s to 351 s of CPU) so that one (`doc` `a_library_name_shows_header_doc_location_and_theorems`) starts first at the top priority and the rest start last (priority -10), after it has filled the cache; and `Session::eager_for_stack`'s test std cache (`target/test-std-cache/{stack}`) is filled by one process at a time, under an advisory file lock beside it, with a marker holding the build's fingerprint and a hash of the library's text (`TestCacheTurn`; with the fingerprint alone, a change to a std file made every process check the changed files at once, three `lsp` tests at 1.34 GB each, SW-3000), `crates/driver/src/driver.rs`), so a sweep's eight workers replay what the first wrote. Measured: the search lane's CPU time 239 s to 125 s, `named_calls_keep_every_hash` cold 133 s to 22 s of CPU. A test that starts early still works, only slowly.

**Two corpus sweeps at a time.** A corpus sweep checks every example, std file or AoC day (or its tier's sample) on a thread pool of its own (`par_map` in `crates/driver/src/driver.rs`). The sweeps are in the nextest test group `corpus-sweeps` (`max-threads = 2`, in `.config/nextest.toml`, for every profile), so no more than two sweeps' pools hold memory together; other tests run beside them. One at a time (the setting until 3 Nov 2026) left cores idle while a sweep's last items ran, 400 s of the broad tier on one to three cores. Measured on 3 Nov 2026 (SW-1104): the two biggest broad sweeps together (`search_at_aoc` `search_at_on_aoc_goals` and `rewind` `rewinding_changes_nothing_for_the_examples`, pools of 5) peaked at 2.95 GB; the quick tier, whose sweeps overlap in the same way on pools of 8, at 2.75 GB. A new test that runs `par_map` over a corpus belongs in the group's filter, unless its pool is small and the group would only make it wait: `extract` `generated_code_is_stable` (about 320 MB at its peak) runs beside the sweeps, since the group's chain of sweeps is the end of the quick tier and it would add its own 4 to 7 s to it. `cargo nextest show-config test-groups --profile broad` lists the members.

**The pools' size.** `par_map` runs `STITCHWORT_TEST_THREADS` threads (default: the cores, at most 8). The broad and all tiers set 5 (`task test:broad`, `task test:all` and the flake), so that two sweeps' pools together are the 10 cores; quick keeps the default. A thread's stack is reserved, not used, so a thread costs what its session holds: about 10 MB in `cli` `examples`, about 50 MB in `hash_stability` `examples` (lane sample, 1 thread against 8). Set `STITCHWORT_TEST_THREADS=2` to shrink every sweep's pool.

**Order.** The longest tests start first (`priority` in the overrides at the end of `.config/nextest.toml`: 100 for the tests of two minutes and more, 50 for those of 40 s and more), so that none is left running alone at the end. Priority orders the tests of a group too.

**Which examples a tier runs.** A corpus sweep's sample is `tier_sample` (`crates/driver/src/driver.rs`): the items sorted by name, then every item in the all tier, every `broad_stride`-th in broad, and every fourth of those in quick and lane. So adding, removing or renaming an example shifts which ones the quick tier runs. Examples that run the read-back size limit out (2 million nodes, `Limits::size`) peak at 0.35 to 0.53 GB each, so none is left out of the sample; at the old limit of 10 million nodes they peaked at 1.3 to 2.4 GB and a sample that picked a few passed the quick tier's 4 GB cap (SW-2996, SW-3010). Why reaching the size limit costs what it does: docs/reviews/SW-2999-size-limit-memory.md.

**Broad and all are run only by the orchestrator, with Matt's approval, on a quiet machine**, never by a lane: they are the tiers with the large caps, and two of them at once, or one beside other worktrees' builds, can still fill the machine. Lanes run `test:lane` and the named tests they changed (`test:one`).

**Slicing the differential sweep.** `STITCHWORT_DIFFERENTIAL_SKIP=N` and `STITCHWORT_DIFFERENTIAL_LIMIT=M` make `differential::the_evaluators_agree_on_the_prelude_and_every_example` run on the sample's examples N up to N+M, so its memory can be measured or bisected without the 10-minute whole run (`STITCHWORT_TEST_THREADS=1` and a low `dev/memguard --cap-gb` then name the example that is too big). The reference evaluator shares nothing, so a normal form that is exponential written out takes exponentially many steps to read back or compare; the test gives the reference a step budget per comparison (`REFERENCE_STEPS`) and prints each one over it as `too big to compare: …` and skips it (`--no-capture` shows them; `STITCHWORT_DIFFERENTIAL_STEPS` overrides the budget, to measure; SW-2613) The test counts the skips and ends with one line, `differential: N comparisons too big to compare`, on stderr (`--no-capture`) and in `differential-skips.txt` in the cargo target's tmp folder (`target/tmp/`), because nextest hides a passing test's output; it fails above `MAX_SKIPPED` (60; the whole corpus skips 48 on 10 Nov 2026, the broad sample 0), unless sliced or given another budget (SW-2620).

**Slicing two more sweeps (SW-2614).** `FMT_HASHES_SKIP=N` and `FMT_HASHES_LIMIT=M` run `fmt_hashes::formatting_changes_no_declaration_hash` on standalone files N up to N+M (no projects, no count check); `STITCHWORT_AT_BENCH_SKIP` and `_LIMIT` do the same for the goals of `search_at_aoc` `search_at_on_aoc_goals`. Measured on 10 Nov 2026 under `dev/memguard`: the formatting sweep peaked at 7.7 to 8.3 GB because two fuzz findings (`dev/fuzz-findings/2468-12893.sw`, 4.5 GB, and `246f-2415.sw`, 1.7 GB) are loaded in it, so both are left out of it (`TOO_LARGE_TO_LOAD`); the rest peaks at 1.6 GB per 120 to 200-file slice. `search_at_on_aoc_goals` holds about 0.7 GB per worker (5.7 GB on 8 workers, 1.5 GB on 2 for the same 13 goals), so its pool is capped at 3 workers (`MAX_GOAL_WORKERS`), 2.3 GB.

### Tier reports

`task test:quick`, `task test:broad` and `task test:all` time their own steps and end with a report of where the time went (SW-2181). Each tier is a wrapper, `dev/tier-report run TIER`, around a hidden task of the steps (`test:quick:steps` and so on; call those only to skip the report). Each step runs under `dev/tier-step NAME -- COMMAND`, which runs the command unchanged, with the same exit code, and appends a line to the run's log (`target/tier-report/logs/TIER-TIMESTAMP.tsv`): name, start, wall seconds, exit code and, for a step under `dev/memguard`, its peak memory (memguard writes the peak to the file named by `STITCHWORT_MEM_PEAK_FILE`). Building is its own step from running: `nextest build` is `cargo nextest run --no-run`, then `nextest run` finds everything built. The steps are `features`, `fmt`, `nextest build`, `nextest run` for quick; `web:pkg`, `fmt`, `lanes-nonempty`, `clippy`, `nextest build`, `builtins build`, `nextest run (with builtins)`, `doctests`, `board:test` for broad; `nextest build`, `nextest run`, `doctests`, `verify-cache` for all. In broad, the `builtins` run and nextest's run are also timed apart, as `beside:` rows that are not in the shares, since they run together.

When the tier ends (passed or failed), `target/tier-report/TIER-TIMESTAMP.md` and `latest-TIER.md` hold:

- the step table (wall seconds, share of the tier, exit code, peak memory) and the time between steps;
- the 15 slowest tests, from nextest's `target/nextest/TIER/junit.xml`;
- test time summed per test binary and per area (a test counts in the first `lane-*` profile of `.config/nextest.toml` that lists it; the map comes from `cargo nextest list` on each lane profile, cached per commit in `target/tier-report/areas-*.json`);
- the tier's wall time against the sum of the tests' own times, and the average number of tests running at once (the sum over nextest's run);
- the load average at the start and the end, and the peak memory.

`target/tier-report/history.tsv` gets a line per run: date, tier, commit (`*` if the tree had uncommitted changes), exit code, wall seconds, tests, failures, the tests' summed seconds, peak GB and each step's seconds. `task tier:report` prints the last ten (`task tier:report -- -n 30 --tier broad`). `target/` is not shared between worktrees, so each checkout has its own history. If the report can't be written (nextest never ran, say) the tier's exit code is unchanged and the report says so. `python3 dev/tier-report_test.py` tests the scripts against a sample JUnit file.

Random tests use fixed seeds, so every run tests the same cases and a failure can always be reproduced.

## Editing the standard library

No build embeds the standard library (`crates/elab/src/std/**`): the compiler reads the files when a process first uses it (SW-1136, `docs/proposals/std-as-data.md`). So an edit to a `.sw` file compiles nothing: `task build` is a no-op, and `task test:one -- -E 'binary(std_library)'` runs the test binary that is already built, on the edited library.

Where a process looks, first match wins:

1. `stitchwort --std-dir DIR`, then `STITCHWORT_STD_DIR=DIR`: an explicit choice.
2. An installed binary's `../share/stitchwort/std` (the flake's package lays it out there).
3. The checkout's `crates/elab/src/std`, found from the executable (cargo's `target/` is inside the checkout, so test binaries find it, in the `nix flake check` sandbox too) and then from the current directory.

If none exists the process stops with a message naming the places tried. WebAssembly has no files: the playground fetches `pkg/std.bundle` beside the wasm (`web/bundle-std.sh`, run by `web/build.sh`) and passes it to `load_std`; a `.sw` edit there needs `task web:build`, not cargo.

- **Checking a std edit (SW-2863).** The library loads lazily: a file is checked (bodies of theorems included) only when something needs it, so `stitchwort --std-dir DIR check prog.sw` and `eval` say nothing about an edited file the program never names. To check what you changed, name it: `stitchwort --std-dir crates/elab/src/std check --std Nat/Arith.sw` (or `Std.Nat.Arith`, or a folder, `Nat`; several allowed). It checks those files and the files they need, in full, reporting errors as `check` does (`the library file std/… doesn't check`, then the diagnostics) and exiting 1; unchanged files come from the check cache, so a file takes well under a second to a few seconds (`Nat` with its 8 files: 1.5 s cold). Run it from the worktree (the cache is `.stitchwort/cache` in the current folder; `--cache-dir` and `--no-cache` as for `check`). It's the lane's check for a std change; the whole library, and the hash and pin tests, are the verifier's.
- The directory is read once, when a process first uses the library. The core's files are read in the order `crates/elab/src/std/core/order.txt` lists, one name per line; a new core file is a new line there. Library files are every other `.sw` file, so a new one is picked up.
- The caches stay correct: the check cache's keys hold the library's text by content, not through the build fingerprint (a library file's key: its text and its dependencies' keys; every key: the core's text and the library's index of names; a namespace's entry records the keys of the library files it names, and is a miss if one changed; an added or removed name misses every entry, the library files' too), and `check_cache.rs` in `crates/cli/tests` edits a copy of the library and compares each `check` with a fresh one. The test-result cache doesn't need it: a test's hash covers the library definitions it uses, and its key has only the evaluation fingerprint (docs/core.md, "Tests and content hashes"). The build fingerprint hashes Rust sources only, so a `.sw` edit recompiles nothing.
- An error in a library file names its path on disk (`…/crates/elab/src/std/Nat/Iterate.sw:12:3`), so an editor can jump to it. The language server opens that real file for a library definition (a `stitchwort-std:` document only when the library has no directory); it reads the library when it starts, so restart it after editing std.
- The hash snapshots (`hash_stability`) and `std_library` print which library they use (`std from <directory>`). Snapshots taken against a library with local edits are of that library.
- A library whose core differs from the built-in natives' expectations is stopped by registration (`E-BUILTIN`) or the pinned hashes (`pinned_hashes`); there is no separate version check (see the note above).

## Running

The tiers are above; `task --list` has the rest. By hand, or for what has no task:

```sh
cargo nextest run --release --workspace --profile quick    # a tier without Task (the profile names the tier)
cargo insta review                             # after changing an error message
cargo llvm-cov --workspace --summary-only      # coverage per file
cargo mutants --package stitchwort-core --test-workspace=true --jobs 6   # slow: minutes to an hour
task bench                                     # benchmarks against the baseline: about 4 minutes on a quiet machine
task test:gate                                 # nix flake check: the broad tier, as CI would
task test:browser                              # the playground in headless Chrome: about 35 s
```

**Incremental release builds (SW-1729).** The devShell sets `CARGO_PROFILE_RELEASE_INCREMENTAL=true`, so the release builds the tests use recompile incrementally: after a one-line `elab` edit, `cargo nextest run --no-run --release --workspace` takes about 20 s instead of about 2½ minutes (21 s against 156 s on 6 Nov 2026, on a busy machine). A first build is no faster, and a target folder is about 2 GB bigger (4.9 GB against 2.9 GB after both kinds of build). Only the devShell sets it: the package and check builds in `flake.nix` are crane derivations that don't read the devShell's environment, so the distributed binary and `nix flake check` are built as before. Whether kache caches incremental compiles isn't established (`kache stats` shows no separate count); the 21 s rebuild was measured in a worktree with kache on, and hits on the workspace crates were rare anyway.

Incremental builds are slower code, so timing tasks don't use them (SW-2474). Incremental compiles use 256 codegen units; the runtime library that every native executable links (`libstitchwort_standalone.a`) then has no cross-unit inlining, and `bench/compare`'s `expressions` retired 320.4 G instructions against 310.6 G from a non-incremental build, the distributed binary's kind (-3.1%). kache strips the incremental flag, so lane worktrees measured the faster code and the main checkout the slower, for the same commit. `bench:compare`, `bench:compare:check`, `bench:instructions`, `bench:aoc` (every AoC day natively, `bench/aoc`), `native:bench` and `profile:native` therefore build into `target/bench` with `CARGO_PROFILE_RELEASE_INCREMENTAL=false`, and are comparable in either kind of checkout. A timing run of anything else (the `stitchwort-bench` crate, for one) should set the variable the same way.

### Differential suites on native code

The differential suites compare the machine with the reference evaluator and
JavaScript; native code is opt-in, so the default runs are unchanged
(docs/reviews/SW-2535-native-default-plan.md, N5a). Put the switch in front of
a test command:

- `STITCHWORT_TEST_RUN=native` adds `--native` to every `run` and `build` the CLI suites
  (`crates/cli/tests/running`) spawn, through `common::cli`, `cli_with` and the
  `build.rs` helper. A run that names its own backend (`--js`, `--reference`)
  or needs the machine (`--profile`, `--alloc-trace`) is left as written.
  `machine` or unset is the default; any other value is a failure.
- The same variable gives `effect_differential.rs` a fourth backend, native
  code compiled in process.
- `crates/rt/tests/it/machine.rs`'s differential cases live in
  `differential.rs`, shared with `crates/native/tests/it/machine_native.rs`,
  which runs them on native code (`stitchwort-rt` can't dev-depend on
  `stitchwort-native`). Those tests are `ignore`d: add `--run-ignored only`,
  e.g. `task test:one -- --run-ignored only -E 'package(stitchwort-native) &
  binary(it) & test(/^machine_native::/)'`.

### Hash dumps

To show what a change to the elaborator does to the declarations it accepts, dump every declaration's hash before and after it and diff the two. `hash_stability`'s ignored test `dump` loads the whole library and one project, and writes one sorted line per declaration (`path hash`, `data path hash` for types) to the file `HASH_DUMP` names:

```sh
HASH_DUMP=/tmp/aoc.txt cargo test --release -p stitchwort-driver --test library -- --ignored hash_stability::dump                               # std + aoc: about 45 s, 10,420 lines
HASH_DUMP=/tmp/rogue.txt HASH_DUMP_PROJECT=games/rogue cargo test --release -p stitchwort-driver --test library -- --ignored hash_stability::dump  # std + rogue: about 7 s
```

- `HASH_DUMP_PROJECT` is a project directory relative to the repository's root; `aoc` if unset.
- With `HASH_DEPS` set to a second path, it also writes each definition's direct references, one line per definition, to work out which changed hashes only follow from another.
- With `STITCHWORT_DEBUG_FORCE_UNGLUED` set, every folded read-back is preceded by an unfolded one with gluing off, which fills the cache of every call it reaches, its result and steps thrown away. A dump with it should equal one without (SW-1782): a difference means some reader used an unfolding computed in another mode. It makes the rogue dump about 2.5 times slower.
- It runs on a thread with the command line's 64 MB stack, so a project loads as `stitchwort check` loads it (on the harness's default stack AoC ran out with `E-RESOURCE`, SW-906).
- The accepted examples' and extract examples' hashes are the `hashes` area's snapshots: `STITCHWORT_TIER=all` with `cargo insta test` shows every one that changed. The quick tier asserts a fixed quarter of them and leaves the rest untouched; the broad and all tiers assert every one, so a new example's snapshot is missing, and noticed, there.

## The allocation trace

A bring-up tool for native compilation (`docs/proposals/native-compilation.md`, "Bring-up trace"): the machine can record every `alloc`, `reuse`, `inc`, `dec` and `free` of a constructor cell, so the machine's memory decisions can be read, and later compared with native code's, event by event.

- **Build.** It is the cargo feature `alloc-trace` of `stitchwort-rt` (`stitchwort-cli` forwards it). Release `stitchwort` is built without it: the hooks are empty `#[inline(always)]` functions, so the machine compiles to the same code. With it, a hook is a load of the count of recording threads and a branch, until a recording starts. A feature rather than `cfg(debug_assertions)` because the tests run in release mode. The dev and test builds switch it on (see "Features"); it records only between `start()` and `finish()`.
- **Use.** `cargo run --release -p stitchwort-cli --features alloc-trace -- run prog.sw --alloc-trace prog.trace` (a hidden flag; it runs on the fast runtime only). In a test, `stitchwort_rt::alloc_trace::start()` before the run and `finish()` after give a `Trace` with `render()`, `leaks()` and `count("reuse")`. See `crates/rt/tests/alloc_trace.rs`.
- **Format.** One event per line: `alloc #3 tag=1 arity=2`, `reuse #3 tag=1 arity=2` (a unique cell refilled in place), `inc #3`, `dec #3`, and `free #3` straight after the last `dec`. Identities are numbered by first appearance, and an address freed and reused is a new identity, so two runs give the same text.
- **Not traced** yet: closures, partial applications, delays, texts and big numbers. Only constructor cells (`Fields`).
- **Checks.** Every `alloc` must have a `free` by the end of a run, including one that ends in an escaped `Fail`.

## Browser tests

**The WebAssembly float tests.** `crates/cli/tests/running/float_paths.rs` runs the float gate on the playground's bundle in `web/pkg`. When the bundle is missing or built from other sources, those tests skip (a pass), so lanes work without a web build. With `STITCHWORT_REQUIRE_WASM=1` they fail instead, naming `web/build.sh`; `task test:broad` sets it and builds `web/pkg` first when it is out of date. The quick tier leaves it unset.

**The editor bundle.** The playground's editor (CodeMirror 6 and `@codemirror/lsp-client`) is JavaScript that is bundled, not committed. `web/editor/` holds the entry modules (`src/`), `package.json` and `package-lock.json`; `web/editor/build.sh` runs `npm ci` and esbuild into `web/dist/` (git-ignored), and `web/build.sh` calls it after the WebAssembly steps. The `editor` flake output (`nix build .#editor`) builds the same bytes with `buildNpmPackage` and nixpkgs' esbuild, and `playground` copies it to `dist/`. After changing `package-lock.json`, set `npmDepsHash` in `flake.nix` to `lib.fakeHash`, build, and paste the hash from the error. The page loads `dist/editor.bundle.js` (from `web/editor/src/editor-entry.js`), which starts the language server's worker, `web/lsp-worker.js`, and that one starts `web/lsp-search-worker.js` for proof searches (the flake's `playground` output copies all three, and `pkg/version.json`'s compiler hash covers them and the bundle). `web/coi-serviceworker.js` is vendored unchanged from the `coi-serviceworker` package (MIT, licence in its header): on a host that cannot send COOP/COEP headers (GitHub Pages) it adds them to every response, so the page is cross-origin isolated and the editor can create the shared counter that cancels a stale check; the first visit loads the page twice, and where service workers are off the editor works without cancellation. The browser tests' server sends the two headers itself (so the service worker does nothing there), and one test turns them off to see the worker do it.

`web/test.sh` builds the playground into `web/pkg/`, then runs `web/tests/browser.mjs` with Node: it serves `web/` itself (on a port the system picks), starts headless Chrome with a temporary profile, drives the page over the DevTools protocol, and stops Chrome at the end. Each test has a fresh tab with empty storage.

```sh
nix develop -c ./web/test.sh                   # build, then run them all
nix develop -c ./web/test.sh --no-build Run    # only tests whose names contain "Run"
nix build .#playground && nix develop -c node web/tests/browser.mjs --dir result   # test the Nix build
```

Chrome comes from the system: `$CHROME`, then `/Applications/Google Chrome.app` or Chromium on a Mac, then `google-chrome` or `chromium` on the `PATH`. Without it, the tests are skipped with a message (exit status 0). They're not part of `nix flake check`: Chrome isn't in the Nix build sandbox (nixpkgs' Chromium doesn't build on macOS), and one test waits out the page's real 15 s timeout, so they depend on the machine's speed. Only Chrome is tested, not Firefox or Safari.

No program is known to crash the compiler any more (its depth guards stop deep programs first), so the crash test serves a worker that checks a marked program with the engine's stack nearly used up, which overflows it inside the WebAssembly as deep programs once did.

## Benchmarks

`crates/bench` runs a fixed set of benchmarks (`--list` shows them): the example suite, evaluation (`lengths 400 3000`), text operations, running a `main` that prints 20,000 lines, generating JS, and checking programs that are known to be slow or near the resource limits (number patterns: one of 200, a 256-row table, one of 10^30, a 1,000-row table, dependent arguments, several columns; long list equations, long sums, deep nesting). Each checks its own result, so it can't get faster by doing something else.

Each benchmark is measured in two ways:

- **Counts**, the regression signal. *Steps* are evaluation steps, from the resource budget (`Budget::total_work`). *Visits* are levels of the recursive passes that aren't evaluation, like the elaborator and type checker (`Budget::total_visits`). *Allocations* and *peak heap* come from a counting allocator in the benchmark binary. They depend only on the program and the compiler, not on how busy the machine is, so they're identical on every run (checked: separate processes give identical numbers, and `crates/bench/tests/repeat.rs` checks two runs in one process) and the threshold can be tight: **+10%**. Two things keep them so: hash maps hash the same on every run (`stitchwort_core::collections`; `clippy.toml` disallows the standard library's, whose random hashing now and then changes when a map grows), and the benchmarks' counterexample searches stop at their count of inputs, never at their time limit (`Elaborator::untimed_counterexamples`). The `examples` benchmark spreads its examples over 8 threads (`--jobs`), each counting its own allocations and peak heap; the peak is the heaviest example's. Which thread takes which example depends only on file sizes, not timing, because a thread's buffers grow as it goes and an example's allocation count depends a little on what the thread did before it. So the counts are the same on every run, but not exactly those of a single thread, nor of each other: runs agree to one part in 100,000, which is what `run` accepts for a benchmark with parts, and `--jobs 1` is exact (on 7 Nov 2026, across 1,498 examples: one example's steps differed by 138 in 67 million, and 33 allocation counts by a few); compare runs with the same `--jobs`. They don't see everything: a loop that neither evaluates, recurses through a guarded pass nor allocates costs time without changing them.
- **Machine instructions**, for the `run-machine-*` benchmarks only (the runtime's machine on `bench/native/` programs and some AoC days; `docs/proposals/interpreter-speed.md` §4.1): the bytecode instructions it executed (`stitchwort_rt::machine::instructions_executed`), deterministic like the other counts, with the same +10% threshold. These benchmarks don't touch the checker, so their steps and visits are 0 (the older `run-` benchmarks run the reference evaluator, and their steps are the checker's budget counter). Frames entered aren't recorded: the machine counts them only per stretch between operations. Checking and lowering `main` aren't timed.
- **Time**, the median of 5 runs (the `examples` sweep is run once) of a release build. It's what matters in the end, but other builds on the same machine make it noisy, so its threshold is loose (**+50%**, and at least 20 ms more) and it's never checked automatically.

```sh
cargo run --release -p stitchwort-bench                  # run, compare with the baseline; fails on a regression
cargo run --release -p stitchwort-bench -- check-number  # only benchmarks whose names contain this
cargo run --release -p stitchwort-bench -- --no-time     # counts only, one run each: about 80 s, most of it `examples`
cargo run --release -p stitchwort-bench -- --parts FILE  # also write each example's counts to FILE, to compare two builds
cargo run --release -p stitchwort-bench -- --update      # record this run as the baseline
```

The baseline is `bench/baseline.toml`: one table per benchmark, so a change reads well in a diff. Update it deliberately: after an improvement (the comparison says so, and the baseline should keep it), or after a regression that's worth its cost, saying why in the commit. Record times on a quiet machine. The example suite and JS generation read `examples/`, so the baseline records a fingerprint of those files, and when they change the counts aren't compared (a note says so) until the baseline is updated.

The test tiers run the counts part (`crates/bench/tests/baseline.rs`): one run of each benchmark, failing if a count grew past the threshold. Being deterministic, it can't fail by chance. The `examples` benchmark checks the whole example corpus (each example in a session of its own, from the library's source, so that the elaborator's work on the library is part of what it counts), over a minute and most of the test's time, so only the all tier compares its counts; the broad tier compares the rest, in about 30 s. It's skipped in debug builds (`cargo test`), where the benchmarks are slow and allocation counts may differ from the release build's.

## Writing tests

- **For a language feature, start with example programs.** Add an `accept/` example, and for each way it can go wrong, a `reject/` or `soundness/` example declaring the error code it expects. Pair every rejection with a nearby acceptance, so a check can't pass by rejecting everything.
- **For a kernel rule, also add a kernel test on core terms.** Prove that the kernel enforces the rule *by itself*, not just that the elaborator does.
- **The kernel must never panic.** If a malformed term can make it panic, that's a bug: it should be an `E-MALFORMED` error.
- **For a new export shape or codec, add an extraction example.** The random differential test then exercises it automatically.
- **A crate's integration tests may be one binary (SW-1736, `docs/proposals/fewer-test-binaries.md`).** `stitchwort-rt` has them as modules of `crates/rt/tests/it/main.rs`: a new test file is `tests/it/NAME.rs` plus `mod NAME;` there, and its tests are `NAME::test_name` in binary `stitchwort-rt::it` (so `task test:one -- lower::`, or `-E 'package(stitchwort-rt) & binary(it) & test(/^lower::/)'`, not `binary(lower)`). `dev/merge-test-binaries` does the move for another crate and rewrites the filters in `.config/nextest.toml`, `dev/nextest-quick` and `dev/test-affected.toml`. Binaries with a `#[global_allocator]` (`effect_alloc`, `state_match`) stay apart. The two biggest crates are in groups (`--group NAME=a,b,c`), so that no one compile is the critical path: `stitchwort-cli` has `extraction` (`extract`, `effect_differential`), `running` (the example, `run*`, `build`, `aoc_answers` and key-mode tests, with `common/` and `pty/`), `server` (`lsp`, `live_memory`, `session`, the caches, `search`, `goal_index`) and `tools` (the rest); `stitchwort-driver` has `elaboration` (language features and error messages), `proofs` (kernel, rewriting, partial programs), `projects` (projects, namespaces, caches, navigation, `run`) and `library` (`std_library`, `builtins`, the hash snapshots, the search tests), with `resources`, `search_at_aoc` (allocators), `fuzz_elab` and `soundness_fuzz` apart. A test is `module::name` in its group, and its snapshot `GROUP__module__name.snap` in `tests/GROUP/snapshots/`. `dev/merge-test-binaries --rewrite-timings` renames the keys of `target/test-timings.json` after a merge.
- **Before trusting a new test, break the code it tests and watch it fail.** `cargo mutants` does this systematically.

### The test std cache

`Session::eager()` and `eager_for_stack(n)` (every library file loaded up front) replay the standard library from the check cache (docs/proposals/check-cache.md) instead of checking it from source: a load costs about 0.6 s of CPU where checking from source costs 9 to 10 s (release; 15 times less, measured under a load average of 40). The cache is `test-std-cache/{stack}/check/` in the cargo target folder of the running test binary (`target/test-std-cache/`), one folder per stack size because the stack is part of an entry's key and writing an entry evicts the unit's others. Entries are keyed by the build fingerprint (the Rust sources, `Cargo.lock`) and by the library's text through each entry's key, so a changed compiler or library misses by itself. The first load after a build checks from source and writes the entries (about 9 MB, one file per library file); concurrent first loads in several test processes each write them, which is safe (a write goes to a temporary file that is renamed over the entry, and all writers write the same bytes). Other builds' entries older than ten minutes are deleted by the first write of a run. The language server's `features` tests use a folder of their own, `test-std-cache/{stack}/lsp` (`Memory::with_cache`), for their project sessions; the two library-replay checks in that binary still check from source on purpose. The first process to start in a cold `lsp` folder fills it alone by opening a small file, under the same lock and marker (`TestCacheTurn`), and the others wait and replay (SW-1741: the binary's CPU time on a cold cache went from 371 s to 181 s); the fill of the checker's entries and the fill of the search entries run side by side, so a cold run waits for the slower (SW-2144: 55 s to 30 s here). Production paths (the CLI, the language server, the playground) don't use it. `rm -rf target/test-std-cache` resets it.

A replayed entry is trusted like any check cache entry, so a test whose point is the from-source check of the library uses `Session::eager_from_source()` or `eager_from_source_for_stack(n)`: `std_library` (all four), `hash_stability` `prelude` (in every tier: the one check from source in the quick tier, and it holds every hash of the library to its snapshot) and its hash dump, `builtins` (the registry is complete once every file has loaded) and `doc_links` (a broken doc link fails the load from source). `hash_stability`'s sweep workers check the library from source in the all tier only (a second guard beside `prelude`) and replay it in every other; `pinned_hashes` (the bindings by content hash, and every std `…Cong` lemma against `validate_cong`) replays it in all tiers, since it reads what the loaded declarations hash to and are, not whether they check. In every tier but the all one `cli` `examples` loads the library for its lazy sessions through the same cache (`Session::use_test_std_cache`), and the tests in `crates/cli/tests/running/build.rs` share one check cache (`--cache-dir`) rather than passing `--no-cache`; that is most of what these cost (SW-1761: `examples` 200 s of CPU to 65 s, `build` 141 s summed to about 55 s, the library checked from source seven times to once). The `check_cache` tests build their own sessions, not eager ones. `rewind`'s sessions (`session(source)`) replay the library outside the all tier and run no counterexample search on a failed theorem but for the examples named for it, since the differential is of the program's check; its cancelled-at-each-cache-use sweep takes every third point there. `extract` (`new_session`), the `std_library` core-alone sweep (whose workers also rewind their sessions) and `cli` `run_js` (one shared `--cache-dir`, as `build`) replay it too; `operators` checks a fixed sample of AoC days, with Target::Everything in the all tier (SW-1770). Everything else that wants the library loaded gets it replayed.

### Stack

A session is told how much stack it has: `Session::new()` and the other constructors without a size assume 2 MiB, a test thread's stack (`Limits::default()`); `Session::for_stack(n)`, `navigable_for_stack(n)`, `eager_for_stack(n)` and `eager_from_source_for_stack(n)` assume `n`. Its stack guard stops deep code with `E-RESOURCE` a quarter short of that. A session told more than its thread has can't stop in time: deep code overflows the real stack first, which aborts the whole test binary instead of failing one test (SW-923: AoC day 22's 2000-deep evaluation did this to two tests run on libtest's 2 MiB thread with 16 MiB limits).

So a session sized for a big stack runs on a thread of that size, made from the same number:

- `with_session(STACK, Session::for_stack, |session| …)` (`stitchwort_driver::driver`) makes the thread and the session together, so they can't disagree. Prefer it for a new test.
- `with_stack(STACK, || …)` around code that makes `Session::for_stack(STACK)` itself, and `par_map(STACK, …)`, whose workers have `STACK` each, do the same when the session is made inside.
- A session with the default limits runs anywhere with at least 2 MiB.

The tests check this. The `stack-check` feature of `stitchwort-core`, which the dev and test builds turn on (see "Features"), makes every outermost operation compare its stack limit with the stack its thread has left (`check_thread_fits` in `crates/core/src/budget.rs`, asking the thread library on Linux and macOS) and panic if the limit doesn't fit, naming this section. It's off in the builds people run.

A binary's tests already share the machine through libtest's test threads and `par_map`, so what is left is CPU work. Under `cargo test` the remaining cost of a whole-suite run was that cargo runs binaries one after another, so each binary's tail (its slowest test) left cores idle: the gate took about 31 minutes (`checkPhase`, 111 binaries, on a loaded 14-core machine; the test binaries summed to 29.5 minutes). The gate now runs under [cargo-nextest](https://nexte.st), which starts the next binary's tests as cores free up and runs every test in its own process.

## The flake

- `nix flake check` (`task test:gate`) is the **broad tier**: the `stitchwort` check (`cargo nextest run --no-fail-fast --profile broad` with `STITCHWORT_TIER=broad`, then `cargo test --doc` for the doctests), `clippy`, `fmt`, `debug-builtins` and `board`.
- `nix build .#stitchwort-all` (`task test:all:nix`) is the same with the `all` profile and `STITCHWORT_TIER=all`. It is a package, not in `checks`, so it is built only on request: only when Matt asks.
- Bench `repeat` repeats the whole example sweep in the all tier (about 190 s); the other tiers repeat four small benchmarks (`eval-lengths`, `run-prints`, `check-long-sum`, `run-machine-calls`; about 4 s).

### Under nextest

- Settings are in `.config/nextest.toml`: the tier profiles, no fail-fast, 8 tests at once in broad (memory is the limit), 6 in all, one per core in quick and the lanes (mostly sub-second tests).
- Every test is its own process, so statics, thread-locals and `OnceLock`s are never shared between tests, and pid-named temp directories are unique per test. State shared through the file system is not: `crates/cli/tests/server/lsp.rs` rebuilds one AoC copy under `CARGO_TARGET_TMPDIR` in each test, so the three tests that call its `aoc()` (`aoc_navigation_matches_check_index`, `workspace_symbols_cover_namespaces_not_checked_yet`, `a_newer_edit_cancels_the_check_running`) are in the `lsp-aoc-copy` test group (`max-threads = 1`); the other `lsp` tests use folders of their own. A new test that calls `aoc()`, or shares files between tests another way, needs a group too. Those tests, and the rest of `lsp.rs`, wait for the server's replies and diagnostics with one 30 min ceiling (`WAIT`), not a timeout tuned to a quiet machine: the wait ends when the event arrives, and under all-tier load a check took 7 to 37 times as long (SW-2584).
- Tests that rely on one process holding a lock (`SPAWN` in `crates/cli/tests/running/run.rs` and `aoc_answers.rs`, which guards the fork/exec race on pipe descriptors) still work: the race is within a process.
- Nextest does not run doctests. `stitchwort-partial-model` has three (`src/typed.rs`, two `compile_fail`), so the check runs `cargo test --doc --workspace` after nextest.
- Per-test times: the `quick`, `broad` and `all` profiles write a JUnit report with the time of every test to `target/nextest/broad/junit.xml` (or `quick/`, `all/`), and nextest flags tests over 60 s (120 s in all) as SLOW while running. Under plain `cargo test`, the `finished in` line per binary is what there is.
- `conv_shortcut` now checks its examples on the `par_map` pool (the shortcut switch is thread-local): 107 s down to 17 s alone.
