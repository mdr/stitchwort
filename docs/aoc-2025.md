covers days 1 to 5 in detail and days 6 to 9 briefly, because the user's repository
(<https://github.com/mdr/aoc-2025>) has solutions for days 1 to 9.

## 0. The short version

- **Days 1 to 5 can already be solved by today's compiler, with no kernel or language change.**
  I wrote a working Stitchwort program for each (they check, pass their own tests, and print
  the same two answers as the user's Scala tests for the user's inputs), using only the prelude
  plus a handful of list helpers defined in the same file. Wall times with `stitchwort run`
  (release build, one run each, a laptop under some load):

  | Day | Wall time | Notes |
  |---|---|---|
  | 1 | 0.2 s | no `Int` needed |
  | 2 | 21.7 s | naive candidate generation; about 14 s of it is one avoidable thing (see day 2) |
  | 3 | 0.26 s | greedy, not the user's memoised search |
  | 4 | 7.1 s | 85 rounds over a 136 by 136 grid held as lists |
  | 5 | 0.47 s | `Nat` holds 15-digit numbers natively |

- So the real stress is not "can it run", but **how pleasant it is, how fast, and how much can be
  proved**. The friction found while writing the five programs is in section 9.
- **`Int` is not needed for days 1 to 5** (nor, I think, 6 to 9): the places where the Scala uses
  negative numbers are all `|a - b|` or "turn left", and both have a `Nat` formulation (section
  2). That makes `Int` a decision for the user, not a blocker (open question 2).
- What's missing is mostly **library**: list functions, a "read all lines" helper, sorting,
  a map/set, and above all a **library of lemmas about `Nat` arithmetic** (`n % d < d`,
  `n = d * (n / d) + n % d`, `<=` transitivity, ...), without which no arithmetic proof about
  these programs can be written. Section 10 has the prioritised list.
- The theorems worth aiming for, in order of value for effort: worked examples as `rfl`
  theorems; parser round trips; day 1's closed-form dial equals the click-by-click simulation;
  day 5's merged ranges are sorted, disjoint and cover the same numbers; day 3's greedy answer is
  optimal (the hardest; a proper showcase); day 4's loop ends in a state where nothing is
  removable.

How the prototypes were run: the only Stitchwort binary I could use without building (other
agents were building) was a release build of the compiler from another worktree, made on
16 October. It has the prelude names unprefixed by namespaces (`textSplit`, not `Text.split`),
so the prototypes use today's names. They were not committed (docs only); say if you want them
under `aoc/`.

### Evaluator speed, for the estimates below

`bench/baseline.toml` gives the cost of the reference evaluator: `eval-lengths` is 44.4 million
steps in 0.92 s and `run-prints` 15.8 million in 0.39 s, so roughly **40 to 50 million steps per
second**. The "steps" counted there are the machine's own reductions, not instructions. From the
prototypes: the day 4 round costs about 3.5 million steps for 18,500 cells, i.e. about 190 steps
per cell for "three horizontal sums, add, compare, rebuild". I use that as a rule of thumb: a
small list-walking function costs 30 to 200 steps per element, and any use of `Text` per element
(e.g. `natToText`) costs thousands.

## 1. What Stitchwort has today, as relevant here

Read from `README.md`, `docs/syntax.md`, `crates/elab/src/prelude.sw` and `TODO.md`.

- **Numbers:** `Nat` only, arbitrary precision (stored compactly; `add`, `sub`, `mul`, `leq`,
  `eqNat` and `divFuel` are native). Subtraction stops at zero. `/` and `%` need a proof the
  divisor isn't zero, which `auto` finds for a literal or a `Succ _`. No `Int`.
- **Lists:** `length`, `append`, `reverseOnto`, `headOr`, `tailOf`, and `decEqList`. No `map`,
  `filter`, folds, `sum`, `zip`, `take`/`drop`, indexing or sorting. Literals `[a, b]` exist.
- **Other data:** `Maybe`, `Pair` (`fst`, `snd`, `MkPair`; no tuple syntax), `Bool`, `Ordering`
  with `compareNat`, `Char`, declared **records** (`type R = { a : Nat, b : Nat }`, `r.a`,
  update, record patterns), `Decidable`.
- **Text:** `textLength`, `++`, `textUncons`, `textFold`, `textToList`, `textTrim`,
  `textSplit` (keeps empty fields), `textJoin`, `natToText`, `textToNat` (digits only, so no
  sign), `textCompare`, `textIsEmpty`. `Char` is a code plus a proof; `charToNat` gives the code.
- **I/O:** the `IO` ability with `print : Text -> {IO} ()` and
  `readLine : () -> {IO} (Maybe Text)` (`Nothing` only at end of input; a blank line is
  `Just ""`). `main : () -> {IO, Partial} ()`, run by `stitchwort run file.sw < input`.
- **Loops of unknown length:** `Partial` (stage 1): a partial function is written without a
  termination check, can only run from `main`, and tests and the checker never run it.
- **Proof tools:** `rfl`, `J`, `cong`, `sym`, `trans`, `eqNatSound`, `decEqNat`, `auto`, a
  term-mode language with no tactics and no `omega`/`ring`. Lemmas on arithmetic are nearly
  absent (the prelude has `lengthAppend`, the `join`/`split` round trip, `canon`, and
  `examples/accept/plus-zero.sw`; `TODO.md` lists `textToNat (natToText n) = Just n` as unproved).
- **Termination:** structural recursion and size-change; "fuel" (a `Nat` that counts down) is
  the idiom for anything else, as in `divFuel` and `natDigits`.
- **Checking costs:** `test "..." = e` is a `Bool` evaluated by the checker (and cached);
  `theorem t : lhs = rhs` with `rfl` makes the kernel compute both sides, so the work counts
  against checking, not running.
- **Namespaces** are in progress (`TODO.md`, Next 1): `List.map`, `Text.split`, `xs.sort`, and
  `import List (map)`. Prelude names can't be redefined today, which bit me immediately (below).

## 2. Cross-cutting design notes

**Pure core, thin shell.** Each day is `solve : List Text -> Pair Nat Nat` (total, structurally
recursive or fuelled) plus a `main` that only reads lines and prints. Then `test` and `theorem`
can exercise `solve` on small inputs (they can't run `Partial`), and all proofs are about
total code. The reading loop is the only `Partial` code:

```
def readRev (acc : List Text) : Maybe Text -> {IO, Partial} List Text
  | Nothing => acc
  | Just l  => readRev (Cons l acc) (readLine ())

def main () : {IO, Partial} () :=
  let ls := reverseOnto (readRev Nil (readLine ())) Nil
  let a := solve ls
  print ("Part 1: " ++ natToText (fst a))
  print ("Part 2: " ++ natToText (snd a))
```

This is the same six lines in every day: a `readAllLines` in the library.

**No `Int` needed.** (1) A left turn on a 100-position dial is a right turn in a mirror:
`m = (100 - pos) % 100`, then rotate right and mirror back. (2) `|a - b|` is `(a - b) + (b - a)`
with truncated subtraction. (3) Signed offsets for grid neighbours are avoided by working with
shifted copies of a row (day 4), or by adding a border of padding and using `+ 1` and `- 1` only
where the cell is known to be interior.

**Numbers are big enough.** The largest values in the user's inputs: day 2 ranges go to about
`9.9 * 10^9` (10 digits); day 5 to `5.6 * 10^14` (15 digits); day 3's part 2 answer and day 7's
part 2 answer have 14 to 15 digits. `Nat` is arbitrary precision, so the Scala `Long` caveat
doesn't arise (and generated JS already uses `bigint`).

**Where the expected answers are.** In the user's repository, in
`src/test/scala/DayNNTest.scala`: each has `it("should work on puzzle input")` blocks with
`shouldBe <number>` (and example blocks with the puzzle's example answers). There are no separate
answer files. Days 1 to 8 have both parts; day 9 has part 1 only (its `solvePart2` is `???`).
I checked the days 1 to 5 values by independent Python implementations, and the Stitchwort
prototypes agree with them. The numbers aren't repeated here: see section 11 for how the harness
reads them.

## 3. Day 1: the dial

**Task.** A circular dial numbered 0 to 99 starts at 50. Each input line is `L` or `R` and a
distance. Part 1: how many rotations end with the dial at 0. Part 2: how many times does the
dial point at 0 during all the rotations (counting every click, so a rotation of 250 passes 0
two or three times).

**The user's approach** (`day01/Day01.scala`). `Rotation` is `Left(n)`/`Right(n)` with a signed
`value`; `mod(a, b) = ((a % b) + b) % b` to handle negatives. Part 1 is `scanLeft` the dial
over the rotations and count positions equal to 0. Part 2 is a fold carrying position and a zero
count: `sum / 100` truncating toward zero, `abs`, plus a special case `position > 0 && sum <= 0`
for going left past or onto 0. (That special case is the subtle part: with truncating division
it's easy to be off by one on exact multiples; the user's test file has 20 hand cases for it.)

**Needs.** Parsing `L68`: `textUncons` then `textToNat`. Modular arithmetic: `Nat` is enough
(mirror trick above). A fold over the rotations. A list of lines.

**Input size** (`day01/input.txt`): 4,462 lines (no trailing newline), amounts 1 to 997, of which
827 are 100 or more; 2,243 left and 2,219 right; the sum of all amounts is 639,879.

**Computation.** Parsing and stepping about 100 to 200 steps per line, so about a million steps.
Measured 0.2 s including loading the prelude. An executable specification that clicks one step at
a time is 639,879 steps of about 30 reductions each, about 20 million steps (0.4 s): affordable
as a `test`.

**Provable.**
1. The puzzle's worked example as a theorem: `theorem example : solve exampleLines = MkPair 3 6 := rfl`.
2. `rotate` keeps the position below 100. Make it structural: `Dial = { pos : Nat, ok : pos < 100 }`,
   the proof field erased at run time. Needs `n % d < d` (library lemma, section 10).
3. The closed form agrees with the click-by-click simulation, for every position below 100 and
   every amount. This is the real theorem: Part 2 *is* "count the clicks", so define
   `clicks : Nat -> Dir -> Nat -> Pair Nat Nat` by recursion on the amount (one click at a
   time) as the specification, and prove `rotate pos r = clicks pos r.dir r.amount` by
   induction on the amount, using `(n + 1) / 100 = n / 100 + (if (n + 1) % 100 == 0 then 1 else 0)`
   and the matching fact for `%`. That in turn needs the division characterisation lemma. It is
   modest in size but needs hand-built arithmetic lemmas (there is no `omega`), which makes it
   a good stress test of the proof side.
4. Parser round trip: `parseRot (unparse r) = Just r`, needing the missing
   `textToNat (natToText n) = Just n`.

**Sketch (runs today; the file I ran, trimmed).**

```
type Dir : Type =
  | TL
  | TR            -- not `L` and `R`: those are prelude constructors (see section 9)

type Rot = { dir : Dir, amount : Nat }

-- new position and the zeros passed. A left turn is a right turn in a mirror.
def rotate (pos : Nat) : Rot -> Pair Nat Nat
  | { dir = TR, amount } => MkPair ((pos + amount) % 100) ((pos + amount) / 100)
  | { dir = TL, amount } =>
    let m := (100 - pos) % 100
    MkPair ((100 - (m + amount) % 100) % 100) ((m + amount) / 100)

def parseRot (t : Text) : Maybe Rot := maybeThen (textUncons t) (\p => parseRotParts (fst p) (snd p))

type Acc = { pos : Nat, atZero : Nat, passes : Nat }

def step (a : Acc) (r : Rot) : Acc := stepWith (rotate a.pos r) a

def stepWith : Pair Nat Nat -> Acc -> Acc
  | MkPair p z, a =>
    { pos = p, atZero = a.atZero + (if p == 0 then 1 else 0), passes = a.passes + z }
```

(Part 2's `(m + amount) / 100` is "how many times the mirrored position crosses a multiple of 100",
which is why no special case is needed: counting crossings of 100 going up includes landing
exactly on 0, and the start position is never counted.)

**Sketch in the namespaced future** (speculative, not checkable today): with `Text.uncons`,
`Nat.toText`, dot notation and `List.foldl`:

```
def solve (ls : List Text) : Acc := ls.mapMaybe parseRot |> List.foldl step { pos = 50, atZero = 0, passes = 0 }
```

(`|>` isn't in the language; `(ls.mapMaybe parseRot).foldl start step` is the dot-notation form.)

**Verdict: done today; the proofs need the arithmetic lemma library.** Easy.

## 4. Day 2: invalid product ids

**Task.** The input is one line of comma separated ranges `a-b`. An id is "invalid" when its
decimal digits are some block written twice (part 1), or some block repeated two or more times
(part 2). Sum the invalid ids that lie in any range.

**The user's approach** (`day02/Day02.scala`). Parse the ranges; for every number in every range
(`(start to end).sumWhere`), test it with a regex on its string: `^(\d+)\1$` for part 1 and
`^(\d+)\1+$` for part 2. Brute force; fine on the JVM.

**Needs.** Splitting on `,` and `-`; `natToText`/digit lists; `Nat` up to 10 digits; either a
decimal digit test per id, or (better) a way to generate or count invalid ids directly.

**Input size** (`day02/input.txt`, 391 bytes, one line, no trailing newline): 28 ranges; **1,917,096
ids in total** (largest single range 181,930); the largest value is 9,899,009,366, so ids have at
most 10 digits and the smallest start is 4.

**Computation.** The brute-force port is about 1.9 million ids, twice (two parts). A digit test on
a 10-digit number through `natToText` is thousands of steps in the reference evaluator (see the
rule of thumb), so something like **10^10 steps, several minutes**: poor. Two better
shapes:
- *Generate the candidates.* Every invalid id is `base` repeated `r >= 2` times, with `base` of
  `k` digits and `k * r <= 10`. For part 1 (`r = 2`), `k` from 1 to 5, that's
  9 + 90 + 900 + 9,000 + 90,000 = 99,999 candidates (my count agrees with an independent
  enumeration). For part 2, to avoid counting an id twice (111111 is `1` six times, `11` three times and
  `111` twice), take only **primitive** bases (not themselves a repetition): 101,088 distinct
  ids. Then check each against the 28 ranges: about 2.8 million `contains` calls each part.
- *Closed form per range.* For each range and each `(length, k)` the invalid ids are
  `base * m` with `m = (10^len - 1) / (10^k - 1)`, so their sum is an arithmetic series over
  `base` in a computed interval. About `28 * 9 * 5` terms, a few hundred thousand steps. Part 2
  needs inclusion-exclusion over the divisors of the length (or the primitive trick).

**What I measured.** The candidate-generation prototype (written naively) printed correct answers
for both parts in 21.7 s. Of that, 14.6 s is generating the candidates (the primitive check calls
`natToText` three times per base, and does so for 100,000 bases), and the rest is
2 * 100,000 ids times 28 ranges. Calling `natToText` once per base, or deciding primitivity
arithmetically, brings it to a few seconds; the closed form to well under one.

**Provable.**
1. The worked example as `rfl`.
2. Parser round trip for the range list (`textJoin`/`textSplit` give the first half; `natToText`
   inverse gives the rest).
3. Soundness of the generator: every id it produces satisfies `Repeats k r id` (a proposition
   defined from the digit list). Straightforward by induction on `r`.
4. Completeness (every invalid id in range appears) is harder: it's the statement that an id
   whose digit list is a block repeated is `rep base r`, needing facts connecting `natToText`,
   its digit list and repeated blocks. Best done on the digit list, with `Nat` entering only at
   the end.
5. The closed form equals the generator on all ranges below some bound, as a `test`, not a
   theorem.

**Sketch (runs today, abbreviated).**

```
def pow10 : Nat -> Nat
  | Zero   => 1
  | Succ k => 10 * pow10 k

-- `base` written r times; shift = 10^(digits of base)
def rep (shift : Nat) (base : Nat) : Nat -> Nat
  | Zero   => 0
  | Succ r => rep shift base r * shift + base

-- is the digit list some shorter block repeated? (d counts down from n - 1)
def hasPeriod : Nat -> Nat -> List Char -> Bool
  | Zero,   n, ds => False
  | Succ d, n, ds =>
    if eqNat (n % Succ d) 0
    then (if eqPrefix (dropN (Succ d) ds) ds then True else hasPeriod d n ds)
    else hasPeriod d n ds
```

**Verdict: runs today but slowly; needs a smarter algorithm (generator or closed form), which
also gives the more interesting proofs. Medium.** The user may prefer a faithful brute-force port
as the *specification* (feasible on the example, not on the input) and the closed form as the
program, proving them equal on small ranges by `test`.

## 5. Day 3: battery banks

**Task.** Each line is a bank of single-digit "batteries". Choose exactly k batteries, in order
(a subsequence), to form the largest k-digit number; part 1 has k = 2, part 2 has k = 12. Sum
the best number of each bank.

**The user's approach** (`day03/Day03.scala`). A memoised search `largestPossibleJoltage(length, fromIndex)`:
try every next position `i >= fromIndex`, recurse with `length - 1` from `i + 1`, take the
maximum. An `@cached` macro annotation memoises it. Exhaustive over positions, polynomial
because of the memo table (about 12 * 100 states, each trying up to 100 positions).

**Needs.** Digits from characters (`charToNat c - 48`), a list, a loop of length k. With the
greedy algorithm, **no map or memo table is needed**, which is the point: the exhaustive memoised
search needs a hash map (or a 2D table) that Stitchwort doesn't have.

**Input size** (`day03/input.txt`): 200 lines of exactly 100 digits, all in 1 to 9.

**Computation.** Greedy: choose each digit as the first largest in the window that still leaves
enough digits. About `k * 100` digit visits per bank, about 15,000 steps per bank, about 3
million steps for the input. Measured 0.26 s. The user's search costs 12 * 100 states * 100
candidates = 120,000 per bank, 24 million for the input, plus the memo's cost.

**Provable.**
1. Worked example as `rfl` (each of the example's four banks and the sums).
2. Structural facts about `best k ds`: the result has at most `k` digits; the chosen digits form
   a *subsequence* of the bank (define `Subseq : List a -> List a -> Prop` inductively).
3. **Optimality:** for every subsequence `s` of `ds` of length `k`, `value s <= best k ds`.
   The proof is the classic exchange argument: the greedy first digit is at least the first digit
   of any admissible subsequence (because the window contains every position such a subsequence
   could use first), and among subsequences starting with the maximum digit at its first
   occurrence, the rest of the subsequence can be assumed to start later. Needs `<=` lemmas and
   a lexicographic-versus-numeric lemma (same-length digit lists compare as their numeric
   values). This is the most interesting proof of days 1 to 5, and is the sort of thing the user
   asked for ("proofs of correctness"). It will be long without automation.
4. Equality with the *user's* exhaustive formulation (a pure recursive `bestBrute`, no memo) on the
   examples by `rfl`/`test`, as a cross-check; the exhaustive version is exponential without the
   memo, fine for 15-digit banks.

**Sketch (runs today).**

```
-- scans at most w elements; returns the first largest and what follows it
def pickGo : Nat -> List Nat -> Nat -> List Nat -> Pair Nat (List Nat)
  | Zero,   ds, b, br => MkPair b br
  | Succ w, Nil, b, br => MkPair b br
  | Succ w, Cons d rest, b, br =>
    if leq (b + 1) d then pickGo w rest d rest else pickGo w rest b br

-- the largest k-digit number from a subsequence of ds, digit by digit
def best : Nat -> Nat -> List Nat -> Nat
  | Zero,   acc, ds => acc
  | Succ k, acc, ds => bestStep k acc (pickGo (length ds - k) ds 0 Nil)

def bestStep (k : Nat) (acc : Nat) : Pair Nat (List Nat) -> Nat
  | MkPair d rest => best k (acc * 10 + d) rest
```

(The start value `0` for the best digit assumes digits are at least 1, true of this input; the
library version takes the first element as the start, and the proof has to carry that.)

**Namespaced future:** `ds.take`/`ds.drop` and `List.maximumBy` would replace `pickGo`; the
proof is easier about a `pickGo`-style scan than about a library `max` plus `indexOf`.

**Verdict: done today; the optimality proof is the showcase. Easy to run, hard to prove.**

## 6. Day 4: paper rolls on a grid

**Task.** A grid with `@` (a paper roll) and `.`. A roll is accessible if fewer than four of its
eight neighbours are rolls. Part 1: how many are accessible. Part 2: remove all accessible
rolls, repeat until none are accessible, and count how many were removed in total.

**The user's approach** (`day04/Day04.scala`). The grid is a `Set[Point]` of roll coordinates;
`adjacent8` is a cross product of offsets minus the point; `forkliftCanAccess` intersects the
neighbours with the set. Part 2 is `iterateUntilStable` of "filter out the accessible ones".

**Needs.** 2D neighbours without negative offsets. A grid representation. A loop until
nothing changes (a fixed point).

**Input size** (`day04/input.txt`): 136 rows of 136 columns, 12,051 rolls (65 %), **84 rounds
until stable (the last removes nothing)**.

**Computation.** The user's version with a set: 85 rounds * 12,051 rolls * 8 lookups is about 8 million
set operations (85 rounds in the user's count; 84 by mine), trivial for a hash set but a problem for lists (a list-based membership test is
linear). Not usable without a map/set structure *or* a representation that avoids lookups:
rows as lists, with each row's horizontal 3-sum computed once and the three rows' sums added
(prototype). Per round that's about 3.5 million steps; 84 rounds is about 300 million steps,
measured **7.1 s**. A worklist version (only recheck the neighbours of a removed roll) touches
about 12,000 rolls * 8 neighbours, but needs random access or a map: with a grid as
`List (List Nat)` an update is O(rows + columns) = about 270 steps, so about 26 million: faster
only with an `Array`.

**Provable.**
1. Worked example (counts for both parts) as `rfl`.
2. `round` only removes rolls (the new grid is cellwise `<=` the old one), and `removed` equals the
   drop in total rolls. Simple induction over the rows.
3. **Fuel is enough:** every round that doesn't stop removes at least one roll, so the number of
   rolls decreases; starting fuel = initial roll count. Then the fixed point theorem:
   *the result has no accessible roll* (`round result` removes 0).
4. `round` agrees with a direct "count the eight neighbours" specification written the way the
   puzzle describes it (a function from a coordinate to a count using list indexing with
   bounds checks), on the example by `rfl` and in general by induction (this is a real proof:
   the row-shifting trick must be shown to compute the 3 by 3 window sum).

**Sketch (runs today; helper definitions elided).**

```
-- horizontal 3-sums of a row of 0/1: hs 0 row
def hs (prev : Nat) : List Nat -> List Nat
  | Nil               => Nil
  | Cons x Nil        => Cons (prev + x) Nil
  | Cons x (Cons y r) => Cons (prev + x + y) (hs x (Cons y r))

-- up, mid, down 3-sums and the row itself: a roll stays if the window holds 5 or more
-- (itself plus at least 4 neighbours)
def combine : List Nat -> List Nat -> List Nat -> List Nat -> Row
  | Cons u us, Cons m ms, Cons d ds, Cons x xs =>
    combineStep (leq 5 (u + m + d)) x (combine us ms ds xs)
  | _, _, _, _ => mkRow Nil 0

def peel : Nat -> List (List Nat) -> Nat -> Nat     -- fuel = number of rolls
  | Zero,   g, acc => acc
  | Succ f, g, acc => peelStep f (round g) acc
```

**Verdict: runs today, correct, 7 s; wants an `Array` (or at least `List.get`/`zip`) and a
`Set` for a natural version. Medium; proofs of the rolling-window trick are the interesting part.**

## 7. Day 5: fresh ingredient ranges

**Task.** The input has two sections separated by a blank line: a list of inclusive ranges
`a-b`, then a list of ingredient ids. Part 1: how many ids fall inside at least one range. Part
2: how many distinct numbers are covered by the ranges together.

**The user's approach** (`day05/Day05.scala`). Parse with `splitOnBlankLines`. Part 1 is
`ranges.exists(_.contains(id))` per id. Part 2 inserts each range, in input order, into a
`SortedDisjointRanges`: `insertAndMaybeMerge` keeps the list sorted by start and disjoint, merging
whatever the new range overlaps (note `a.end < b.start`: adjacent ranges like 1-3 and 4-6 are *not*
merged, which doesn't change the count). The class asserts the invariant on construction.

**Needs.** Reading two sections; a record for a range; `min`, `max`; **no sort** (the insertion
keeps the list ordered); numbers to 15 digits.

**Input size** (`day05/input.txt`): 190 ranges, 1,000 ids; the largest value is
562,888,848,953,868 (15 digits, over 2^31 but below 2^53 and 2^63); the ranges together cover
about 4.2 * 10^14 numbers (so any enumeration is out of the question); the 190 ranges merge into
about 92.

**Computation.** Part 1: 1,000 ids * up to 190 ranges, about 190,000 `contains` calls: under 5
million steps. Part 2: 190 insertions into a list of at most 92: about 17,000 steps of 30
each. Measured 0.47 s total (reading 1,190 lines, 380 `textToNat` on 15-digit numbers
included).

**Provable.** This day is the best fit for dependent types.
1. Worked example as `rfl`.
2. A type for the invariant: `Sorted : List Range -> Prop` ("each range's `hi + 1 <= ` the next range's `lo`")
   and `addRange` returning a list together with a proof that it's sorted,
   or just a lemma `Sorted rs -> Sorted (addRange r rs)`. That's a direct translation of the user's
   `assert`.
3. **Membership is preserved:** `covered (addRange r rs) x = (covered rs x || contains r x)`. By
   induction on `rs`, with the merge case using `min`/`max` lemmas.
4. Part 2 count: `sumL (mapL size merged)` equals the number of `x` below an upper bound for which
   `covered` holds, on small ranges by `test` (brute force); a general proof needs a notion of
   cardinality of a finite subset of `Nat`, not worth it; the right theorem is that the merged
   list is sorted, disjoint, and covers exactly the same numbers, from which the sum of sizes is
   the count by a small standalone lemma about disjoint intervals.
5. Parser round trip for `a-b`: `textSplit` with `textJoin` plus the number round trip.

**Sketch (runs today; helpers `mapMaybe`, `foldl`, `anyL`, `countL`, `sumL`, `minN`, `maxN` are
each four lines and belong in the library).**

```
type Range = { lo : Nat, hi : Nat }

def contains (r : Range) (x : Nat) : Bool := if leq r.lo x then leq x r.hi else False

def size (r : Range) : Nat := r.hi + 1 - r.lo

-- keeps the list sorted and disjoint
def addRange (n : Range) : List Range -> List Range
  | Nil => Cons n Nil
  | Cons h t =>
    if leq (n.hi + 1) h.lo then Cons n (Cons h t) else addAfter n h t

def addAfter (n : Range) (h : Range) (t : List Range) : List Range :=
  if leq (h.hi + 1) n.lo
  then Cons h (addRange n t)
  else addRange (mkRange (minN h.lo n.lo) (maxN h.hi n.hi)) t

def solveWith (rs : List Range) (ids : List Nat) : Pair Nat Nat :=
  MkPair (countL (\i => anyL (\r => contains r i) rs) ids)
         (sumL (mapL size (foldl (\acc r => addRange r acc) Nil rs)))
```

(Termination: `addRange` recurses on the list in both branches that recurse, once with the
merged range, which is a different first argument but the list gets shorter: structural.)

**Verdict: done today; the most natural place for an invariant-carrying proof. Easy.**

## 8. Days 6 to 9, briefly

(Not part of the requested scope; the user's repository has them, and the early ones decide what
the library must grow into.)

- **Day 6** (`input.txt`: 5 lines of 3,780 characters; 4 rows of numbers then an operator row).
  The user transposes a character block. Part 1 reads whitespace-separated columns; part 2 reads
  digits column by column, right to left, with blank columns separating problems. Needs
  `transpose`, `splitOnWhitespace`, products (to about 10^13: fine). **Easy-medium, library only**
  (transpose over `List (List Char)`, padding the last short line). About 4 * 3,780 characters:
  trivial.
- **Day 7** (142 lines of 141 columns, 1,711 splitters; the user reads every second line). Beam
  splits: part 1 counts splits with a set of positions per row; part 2 counts paths with a
  memoised function over `(position, row)`. In Stitchwort: a vector of counts per row (a
  `List Nat` of 141 entries), one pass per splitter row, about 71 rows * 141 cells = 10,000
  updates. The path count has 14 digits: fine for `Nat`. **Easy, library only**; no map
  needed. The invariant "the count vector sums to the number of timelines" is a nice theorem.
- **Day 8** (1,000 points, coordinates up to 99,986). Sort all pairs by distance
  (**499,500 pairs**), then merge circuits as the closest pairs are connected; part 1 stops after
  1,000 connections and multiplies the three biggest circuits; part 2 continues until one circuit
  remains. Needs: **sorting** (a merge sort of 500,000 pairs is about `500,000 * 19` = 9.5
  million comparisons, each a few dozen steps: a few hundred million steps, tens of seconds,
  and a stack-depth worry for non-tail-recursive list functions); integer *squared* distance in
  `Nat` (`dx^2 + dy^2 + dz^2` using `|a - b|`; no `Double`/`sqrt` needed, and ordering by squared
  distance is equivalent); a union-find or a label-per-point structure (a `List Nat` of 1,000
  labels with relabel-on-merge is O(n) per merge: 1,000 * 1,000 = 1 million for part 1 but up to
  499,500 * 1,000 worst case for part 2). A different algorithm avoids most of that: part 2 is the
  **largest edge of a minimum spanning tree**, and Prim's algorithm is `n^2` = 1 million steps and
  needs no sort; part 1 needs the 1,000 smallest edges, i.e. a partial sort (a heap, or repeated
  selection). **Medium-hard; needs sort or heap, and an array or map.**
- **Day 9** (495 points, coordinates to 98,471; the user's `solvePart2` is `???`). Part 1: the
  largest rectangle with two points as opposite corners: all pairs, about 122,000 of them,
  `(|dx| + 1) * (|dy| + 1)`: trivial for `Nat` with the `|a - b|` trick. Part 2 (inside a polygon
  given by the points) isn't solved in the Scala. **Part 1 easy; part 2 is a hard puzzle in any
  language** (coordinate compression and a polygon fill).

## 9. Friction found while writing the five programs

Found by actually writing and running them, so these are evidence, not guesses.

1. **Prelude names clash** with natural user names: my first `add` (adding a range to a list)
   was `E-DUPLICATE: add is already defined` (prelude `add`). Also `L` and `R` (constructors of
   the prelude's `Plus`) for left/right. Namespaces fix this. The programs use `addRange`, `TL`
   and `TR` instead.
2. **A crash:** declaring `type Dir : Type = | L | R` and then using the constructors in a
   *record* pattern, e.g. `f { dir = R, amount } = amount`, makes the compiler panic
   (`index out of bounds: the len is 0 but the index is 0` at `crates/elab/src/records.rs:430`),
   instead of reporting the `E-DUPLICATE` it gives for the same declaration alone. Repro file:
   a `Dir` type, `type Rot = { dir : Dir, amount : Nat }` and one such equation. Probably error
   recovery after the duplicate. (Built from another worktree's binary; may already be fixed.)
3. **`else` at the start of a line is a parse error** with a baffling message
   (`expected else, but found else`): an `if ... then ... ` followed by `else` on the next
   line is read as a block statement. Everyone writing `if/else if/else` chains over several
   lines will hit it. I wrote three one-line `if`s or moved the else-branch into a helper
   function in both days 2 and 5. A real `else`-continues-the-line rule would fix it.
4. **A record literal needs a known type**: `Just { dir = TL, amount = n }` inside a lambda
   passed to `maybeThen` is `E-CANNOT-INFER`; a `mkRot : Dir -> Nat -> Rot` helper fixes it
   (annotation `(… : Rot)` also works, per the error's own note). *Fixed (17 October 2026):
   the expected result type is now used first
   ([syntax-conveniences.md §7](proposals/syntax-conveniences.md#7-knowing-more-expected-types-result-type-first)).*
5. **No `where` and no local functions**: every helper is a top-level definition with a
   signature, so a 30-line algorithm becomes 10 definitions (`combine`, `combineStep`, ...).
   Stepping through "recurse, then post-process the result" costs a named helper each time
   (`rndStep`, `rndJoin`), because patterns can't appear in `let` or lambdas. A `case`
   expression or pattern-matching `let`/lambda would remove most of these.
6. **No tuple sugar**: `MkPair`, `fst`, `snd` everywhere.
7. **Repeated helpers**: `mapL`, `foldl`, `anyL`, `countL`, `sumL`, `mapMaybe`, `dropN`,
   `minN`, `maxN` and the six-line reader are redefined in each file (about 30 lines each).
8. **Text is slow in the reference evaluator**: the day 2 generator spent 14 s mostly on
   `natToText`/`textToList`. A native (or a counted version) for digits of a `Nat` would be
   worth having if digit problems matter. (The generated JS `Text` is native: this is about the
   interpreter that `run`, `test` and the checker use.)
9. **Run speed**: 40 to 50 million steps per second. The `run` command doesn't print timings
   (I used `time`).
10. **Good surprises:** big `Nat` arithmetic is native and instant (15-digit values everywhere,
    no care needed); `auto` found the non-zero proofs for `% 100`, `/ Succ k` without help; records
    and `Partial` worked on first use; error messages with source spans were precise.

## 11. Harness design

**Layout (proposal).**

```
aoc/
  day01.sw ... day05.sw      the programs (pure `solve`, thin `main`); small examples as `test`s
  run.sh                      runs one day or all
  README.md                   how to get the inputs (only a pointer; not puzzle text)
  inputs/                     gitignored: day01.txt ..., expected.txt
```

`.gitignore` gets `aoc/inputs/`. The inputs directory is overridable by `AOC_INPUTS`, so the
inputs can live outside the repository entirely (the user's own `aoc-2025` clone, whose layout
is `src/main/resources/dayNN/input.txt`, can be pointed at directly: the script accepts either
`$AOC_INPUTS/dayNN/input.txt` or `$AOC_INPUTS/dayNN.txt`).

**Running a day.** `stitchwort run aoc/day01.sw < "$AOC_INPUTS/day01.txt"`; each program prints
exactly `Part 1: N` and `Part 2: M`, as the Scala does. `run.sh` does, per day:
`stitchwort check`, `stitchwort test` (the inline example tests and `theorem`s: these run
without any input, so they can also run in CI), then `run` under `time`, and compares the output
with `expected`.

**Expected answers.** They're in the user's repo, in `src/test/scala/DayNNTest.scala`, as the
literals after `shouldBe` in the `"should work on puzzle input"` blocks. A one-off script
(not committed) extracts them into `aoc/inputs/expected.txt` (lines like `day01 1 <answer>`).
Keeping them out of the repository is the conservative choice: they're derived from personal
inputs, and Advent of Code asks people not to publish inputs; if the user is happy for
answers to be public (they already are, in the Scala repo), `expected.txt` could be committed.
Open question 3.

**Examples.** The puzzle's small worked examples are the best tests and the best `rfl`
theorems, but they're part of the puzzle statements, which we aren't to reproduce. The user's
Scala tests already contain them verbatim, so the same applies. Until the user says otherwise,
our own tests use tiny inputs of our own making (like the ones I used: three ranges, six ids)
and the real examples live only in the user's repo (open question 1).

**Keeping this out of the main gate.** `cargo test` and `nix flake check` run the example
programs (171 files in the benchmark), so `aoc/` is deliberately a separate directory, not
under `examples/`: its programs (several seconds each) shouldn't slow the gate. A generated
input in-language (an LCG producing 4,462 rotations) would let a single `aoc/` benchmark row run
without any puzzle data, which also fills the "generated rows aren't benchmarked" gap in
`TODO.md` Later.

**Timing and limits.** `stitchwort run` has no `--time`; the script times it. Resource limits:
the default limit is 2 million frames and a million-deep recursion peaks near 750 MB
(`TODO.md`, Known issues), so non-tail-recursive list functions are fine at day 1 to 5 sizes
(4,462 elements) but worth care for day 8's 500,000-element sort.

### Proofs (October 2026)

`aoc/day01.sw` now proves the solution correct. Everything checks, tests included, in about
0.27 s (`stitchwort check`, release build, prelude load included). Answers are still 1076 and
6379; `stitchwort run` takes 0.9 s.

The program was reshaped for the proofs. The dial size is a parameter, `top` being its largest
number (99 for the puzzle). A position is `type Pos (top : Nat) = { at : Nat, ok : at <= top }`,
made by `wrap`, which uses `Int.modNat` for both directions. Part 1 counts the zeros in
`List.scanl (move top) start turns`. Part 2 adds up `passes`, the closed form (`(p + n) / size`
going right, the mirror image going left). The specification `part2Spec` splits each turn into
single clicks (`Left 1`, `Right 1`) with `List.concatMap`, runs the same `move` over them with
`List.scanl`, and counts the positions that are 0.

Theorems:

1. Positions are on the dial by their type (`alwaysOnDial` just reads the `ok` field).
2. `part2Correct : (top : Nat) -> (start : Pos top) -> (turns : List Turn) -> part2 top start
   turns = part2Spec top start turns`, and `part2Puzzle`: the printed part 2 is the click-by-click
   count of the parsed input. The per-turn core is `turnCount` (`passes` counts the zero clicks
   of one turn) and `turnAt` (the clicks end where the turn does).
3. Part 1 is its own specification (`part1Puzzle` is `rfl`).

Added to the prelude, as generally useful: `Nat.divUnique`, `Nat.modUnique` (from
`Nat.quotUnique`), `Nat.modSmall`, `Nat.divSmall`, `Nat.addDivSelf`, `Nat.addModSelf`,
`Nat.modSelf`, `Nat.divOne`, `Nat.modLt` (`Nat.modLess` with an `auto` proof), `Nat.zeroSub`,
`Nat.subEqZero`, `Nat.succSub`, `Nat.succAddSub`, `Nat.subSuccRight`, `Nat.addOne`;
`List.countOccurrences` (`List.count` is `List.occurrences`), `List.occurrencesAppend`,
`List.scanlCons`, `List.scanlAppend`. The `Int.subNatNat` facts stay in the file.

**Friction**

- **Checking `% 100` is slow.** `Nat.mod n d` is `n - d * (n / d)`, and `100 * q` unfolds to a
  hundred additions. Even `rfl : (100 + n) % 100 = (100 + n) % 100` took 5 s, `n % 100 = (100 +
  n) % 100` by `Nat.addModSelf` over 20 s, and a one-line induction step about `((a + 1) % 100 +
  n) % 100` over 20 s; `n % 100 = n % 100` is instant. So the lemmas are about a dial of any
  size, where `Succ top * q` stays put; after that change the whole file checks in 0.27 s.
  Defining `Nat.mod` as `n - (n / d) * d` (stuck on the unknown quotient) would avoid it, but
  changes hashes. *Done since:* `Nat.mod n d` is now `n - (n / d) * d`. The `rfl` above checks
  in 0.2 s (it took 4.4 s), and `n % 100 = (100 + n) % 100` by `Nat.addModSelf` in 0.33 s
  (22.8 s), prelude load included. The division lemmas behind `Nat.modLess` were restated as
  `q * d` too, which also makes their proofs cheap to compute on numbers.
- **`stitchwort run` computes proofs.** With `ok = Int.modNatLt x 100` in `wrap`, 50 input lines
  took 4.2 s (0.09 s without the field), so the full input would take minutes. `quickLt`
  compares the numbers instead, keeping `Int.modNatLt` in a thunk for the impossible branch.
  Erasing proofs in the evaluator, as JS extraction does, would make this unnecessary. *Done
  since:* `run` and `test` erase proofs and types (`crates/core/src/erase.rs`), and `quickLt`
  is gone: `wrap` uses `Int.modNatLt` directly. The file checks in 0.8 s (checking still
  computes the proof where a type mentions a concrete position; before the `Nat.mod` change
  that took 16 s) and runs on the full input in 1.1 s, checking included.
- **`auto` proofs differ by context.** `Eq.cong (\y -> Int.modNat y (Succ t)) rfl` does not prove
  `Int.modNat x (Succ t) = Int.modNat x (Succ t)` (`rfl` does), and the error reads "expected
  `Int.modNat x (Succ t) = …`, but this has type `Int.modNat x (Succ t) = …`" with identical
  text, since `auto` arguments aren't printed. Presumably the `d != 0` proof found inside the
  lambda isn't the same term as the one in the signature, and there's no proof irrelevance to
  make them equal. Workaround: the definition `place top x = Int.modNat x (Succ top)`, so every
  use shares one proof.
- **No rewriting.** Every step is `Eq.trans`/`Eq.cong` with the context written out as a
  lambda, and every case split is `Bool.inspect` with the goal restated as its motive. The left
  turn's step is 15 lines for what is two rewrites per case. A `rewrite` (or `calc` chain) and
  a way to name the goal would halve the file.
- **`J` returning a function can't be applied** (`E-ARITY`: `J` takes exactly 3 arguments), and
  `let same = J …` is `E-UNIVERSE` ("expected something of type `Type`, but this has type
  `Prop`"): a `let` can't bind a proof. Workaround: a helper theorem (`posExtAt`).
- `(Unit -> P)` with `slow ()` is "expected `Unit`, but this has type `()`"; the parameter has to
  be written `(() -> P)`.
- `++` in the prelude before `Text` is `E-UNKNOWN-NAME` "this needs the prelude's `Text`" even on
  lists; written `List.append`.
- `a + 1` isn't `Succ a` (addition recurses on the left), so `Nat.addOne` is used at every click.
- Missing: `Int` arithmetic laws (no `Int.add` associativity or commutativity). The left turn
  is proved through `Int.subNatNat` instead, which works but ties the proof to the
  representation.
