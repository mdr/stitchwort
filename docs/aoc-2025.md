covers days 1 to 5 in detail and days 6 to 9 briefly, because the user's repository
(<https://github.com/mdr/aoc-2025>) has solutions for days 1 to 9.

## 0. The short version

- **Days 1 to 5 can already be solved by today's compiler, with no kernel or language change.**
  I wrote a working Stitchwort program for each (they check, pass their own tests, and print
  the same two answers as the user's Scala tests for the user's inputs), using only the prelude
  plus a handful of list helpers defined in the same file. Wall times with `stitchwort run`
  (release build, one run each, a laptop under some load; days 2, 4 and 5 re-measured on 22 Oct 2026 with the committed programs):

  | Day | Wall time | Notes |
  |---|---|---|
  | 1 | 0.2 s | no `Int` needed |
  | 2 | 0.5 s | the committed program (the first version took 21.7 s: naive candidate generation) |
  | 3 | 0.26 s | greedy, not the user's memoised search |
  | 4 | 0.7 s | 85 rounds over a 136 by 136 grid held as lists (the prototype took 7.1 s) |
  | 5 | 0.2 s | `Nat` holds 15-digit numbers natively (merging ranges; the first version took 0.47 s) |

- So the real stress is not "can it run", but **how pleasant it is, how fast, and how much can be
  proved**. The friction found while writing the five programs is in section 9.
- **`Int` is not needed for days 1 to 5** (nor, I think, 6 to 9): the places where the Scala uses
  negative numbers are all `|a - b|` or "turn left", and both have a `Nat` formulation (section
  2). That makes `Int` a decision for the user, not a blocker (open question 2).
- What's missing is mostly **library**: list functions, a "read all lines" helper, sorting,
  a map/set, and above all a **library of lemmas about `Nat` arithmetic** (`n % d < d`,
  `n = d * (n / d) + n % d`, `<=` transitivity, ...), without which no arithmetic proof about
  these programs can be written. Section 10 has the prioritised list.
- The theorems worth aiming for, in order of value for effort: worked examples as `rfl`
  theorems; parser round trips; day 1's closed-form dial equals the click-by-click simulation;
  day 5's merged ranges are sorted, disjoint and cover the same numbers (done, `solvePart2Correct`); day 3's greedy answer is
  optimal (the hardest; a proper showcase); day 4's loop ends in a state where nothing is
  removable.

How the prototypes were run: the only Stitchwort binary I could use without building (other
agents were building) was a release build of the compiler from another worktree, made on
16 October. It has the prelude names unprefixed by namespaces (`textSplit`, not `Text.split`),
so the prototypes use today's names. They were not committed (docs only); say if you want them
under `aoc/`.

### Evaluator speed, for the estimates below

`bench/baseline.toml` gives the cost of the reference evaluator: `eval-lengths` is 44.4 million
steps in 0.92 s and `run-prints` 15.8 million in 0.39 s, so roughly **40 to 50 million steps per
second**. The "steps" counted there are the machine's own reductions, not instructions. From the
prototypes: the day 4 round costs about 3.5 million steps for 18,500 cells, i.e. about 190 steps
per cell for "three horizontal sums, add, compare, rebuild". I use that as a rule of thumb: a
small list-walking function costs 30 to 200 steps per element, and any use of `Text` per element
(e.g. `natToText`) costs thousands.

## 1. What Stitchwort has today, as relevant here

Read from `README.md`, `docs/syntax.md`, `crates/elab/src/std/core.sw` and `TODO.md`.

- **Numbers:** `Nat` only, arbitrary precision (stored compactly; `add`, `sub`, `mul`, `leq`,
  `eqNat` and `divFuel` are native). Subtraction stops at zero. `/` and `%` need a proof the
  divisor isn't zero, which `auto` finds for a literal or a `Succ _`. No `Int`.
- **Lists:** `length`, `append`, `reverseOnto`, `headOr`, `tailOf`, and `decEqList`. No `map`,
  `filter`, folds, `sum`, `zip`, `take`/`drop`, indexing or sorting. Literals `[a, b]` exist.
- **Other data:** `Option`, `Pair` (`fst`, `snd`, `MkPair`; no tuple syntax), `Bool`, `Ordering`
  with `compareNat`, `Char`, declared **records** (`type R = { a: Nat, b: Nat }`, `r.a`,
  update, record patterns), `Decidable`.
- **Text:** `textLength`, `++`, `textUncons`, `textFold`, `textToList`, `textTrim`,
  `textSplit` (keeps empty fields), `textJoin`, `natToText`, `textToNat` (digits only, so no
  sign), `textCompare`, `textIsEmpty`. `Char` is a code plus a proof; `charToNat` gives the code.
- **I/O:** the `IO` ability with `IO.print: Text -> {IO} ()` and
  `IO.readLine: () -> {IO} (Option Text)` (`None` only at end of input; a blank line is
  `Some ""`). `main: () -> {IO, Partial} ()`, run by `stitchwort run file.sw < input`.
- **Loops of unknown length:** `Partial` (stage 1): a partial function is written without a
  termination check, can only run from `main`, and tests and the checker never run it.
- **Proof tools:** `rfl`, `J`, `cong`, `sym`, `trans`, `eqNatSound`, `decEqNat`, `auto`, a
  term-mode language with no tactics and no `omega`/`ring`. Lemmas on arithmetic are nearly
  absent (the prelude has `lengthAppend`, the `join`/`split` round trip, `canon`, and
  `examples/accept/plus-zero.sw`; `TODO.md` lists `textToNat (natToText n) = Some n` as unproved).
- **Termination:** structural recursion and size-change; "fuel" (a `Nat` that counts down) is
  the idiom for anything else, as in `divFuel` and `natDigits`.
- **Checking costs:** `test "..." = e` is a `Bool` evaluated by the checker (and cached);
  `theorem t: lhs = rhs` with `rfl` makes the kernel compute both sides, so the work counts
  against checking, not running.
- **Namespaces** are in progress (`TODO.md`, Next 1): `List.map`, `Text.split`, `xs.sort`, and
  `import List (map)`. Prelude names can't be redefined today, which bit me immediately (below).

## 2. Cross-cutting design notes

**Pure core, thin shell.** Each day is `solve: List Text -> Pair Nat Nat` (total, structurally
recursive or fuelled) plus a `main` that only reads lines and prints. Then `test` and `theorem`
can exercise `solve` on small inputs (they can't run `Partial`), and all proofs are about
total code. The reading loop is the only `Partial` code:

```
def readRev (acc: List Text): Option Text -> {IO, Partial} List Text
  | None => acc
  | Some l  => readRev (Cons l acc) (IO.readLine())

def main(): {IO, Partial} () :=
  let ls := reverseOnto (readRev Nil (IO.readLine())) Nil
  let a := solve ls
  IO.print ("Part 1: " ++ natToText (fst a))
  IO.print ("Part 2: " ++ natToText (snd a))
```

This is the same six lines in every day: a `readAllLines` in the library.

**No `Int` needed.** (1) A left turn on a 100-position dial is a right turn in a mirror:
`m = (100 - pos) % 100`, then rotate right and mirror back. (2) `|a - b|` is `(a - b) + (b - a)`
with truncated subtraction. (3) Signed offsets for grid neighbours are avoided by working with
shifted copies of a row (day 4), or by adding a border of padding and using `+ 1` and `- 1` only
where the cell is known to be interior.

**Numbers are big enough.** The largest values in the user's inputs: day 2 ranges go to about
`9.9 * 10^9` (10 digits); day 5 to `5.6 * 10^14` (15 digits); day 3's part 2 answer and day 7's
part 2 answer have 14 to 15 digits. `Nat` is arbitrary precision, so the Scala `Long` caveat
doesn't arise (and generated JS already uses `bigint`).

**Where the expected answers are.** In the user's repository, in
`src/test/scala/DayNNTest.scala`: each has `it("should work on puzzle input")` blocks with
`shouldBe <number>` (and example blocks with the puzzle's example answers). There are no separate
answer files. Days 1 to 8 have both parts; day 9 has part 1 only (its `solvePart2` is `???`).
I checked the days 1 to 5 values by independent Python implementations, and the Stitchwort
prototypes agree with them. The numbers aren't repeated here: see section 11 for how the harness
reads them.

## 3. Day 1: the dial

**Task.** A circular dial numbered 0 to 99 starts at 50. Each input line is `L` or `R` and a
distance. Part 1: how many rotations end with the dial at 0. Part 2: how many times does the
dial point at 0 during all the rotations (counting every click, so a rotation of 250 passes 0
two or three times).

**The user's approach** (`day01/Day01.scala`). `Rotation` is `Left(n)`/`Right(n)` with a signed
`value`; `mod(a, b) = ((a % b) + b) % b` to handle negatives. Part 1 is `scanLeft` the dial
over the rotations and count positions equal to 0. Part 2 is a fold carrying position and a zero
count: `sum / 100` truncating toward zero, `abs`, plus a special case `position > 0 && sum <= 0`
for going left past or onto 0. (That special case is the subtle part: with truncating division
it's easy to be off by one on exact multiples; the user's test file has 20 hand cases for it.)

**Needs.** Parsing `L68`: `textUncons` then `textToNat`. Modular arithmetic: `Nat` is enough
(mirror trick above). A fold over the rotations. A list of lines.

**Input size** (`day01/input.txt`): 4,462 lines (no trailing newline), amounts 1 to 997, of which
827 are 100 or more; 2,243 left and 2,219 right; the sum of all amounts is 639,879.

**Computation.** Parsing and stepping about 100 to 200 steps per line, so about a million steps.
Measured 0.2 s including loading the prelude. An executable specification that clicks one step at
a time is 639,879 steps of about 30 reductions each, about 20 million steps (0.4 s): affordable
as a `test`.

**Provable.**
1. The puzzle's worked example as a theorem: `theorem example: solve exampleLines = MkPair 3 6 := rfl`.
2. `rotate` keeps the position below 100. Make it structural: `Dial = { pos: Nat, ok: pos < 100 }`,
   the proof field erased at run time. Needs `n % d < d` (library lemma, section 10).
3. The closed form agrees with the click-by-click simulation, for every position below 100 and
   every amount. This is the real theorem: Part 2 *is* "count the clicks", so define
   `clicks: Nat -> Dir -> Nat -> Pair Nat Nat` by recursion on the amount (one click at a
   time) as the specification, and prove `rotate pos r = clicks pos r.dir r.amount` by
   induction on the amount, using `(n + 1) / 100 = n / 100 + (if (n + 1) % 100 == 0 then 1 else 0)`
   and the matching fact for `%`. That in turn needs the division characterisation lemma. It is
   modest in size but needs hand-built arithmetic lemmas (there is no `omega`), which makes it
   a good stress test of the proof side.
4. Parser round trip: `parseRot (unparse r) = Some r`, needing the missing
   `textToNat (natToText n) = Some n`.

**Sketch (runs today; the file I ran, trimmed).**

```
type Dir: Type =
  | TL
  | TR            -- not `L` and `R`: those are prelude constructors (see section 9)

type Rot = { dir: Dir, amount: Nat }

-- new position and the zeros passed. A left turn is a right turn in a mirror.
def rotate (pos: Nat): Rot -> Pair Nat Nat
  | { dir = TR, amount } => MkPair ((pos + amount) % 100) ((pos + amount) / 100)
  | { dir = TL, amount } =>
    let m := (100 - pos) % 100
    MkPair ((100 - (m + amount) % 100) % 100) ((m + amount) / 100)

def parseRot (t: Text): Option Rot := optionThen (textUncons t) (p => parseRotParts (fst p) (snd p))

type Acc = { pos: Nat, atZero: Nat, passes: Nat }

def step (a: Acc) (r: Rot): Acc := stepWith (rotate a.pos r) a

def stepWith: Pair Nat Nat -> Acc -> Acc
  | MkPair p z, a =>
    { pos = p, atZero = a.atZero + (if p == 0 then 1 else 0), passes = a.passes + z }
```

(Part 2's `(m + amount) / 100` is "how many times the mirrored position crosses a multiple of 100",
which is why no special case is needed: counting crossings of 100 going up includes landing
exactly on 0, and the start position is never counted.)

**Sketch in the namespaced future** (speculative, not checkable today): with `Text.uncons`,
`Nat.toText`, dot notation and `List.foldLeft`:

```
def solve (ls: List Text): Acc := ls.filterMap parseRot |> List.foldLeft step { pos = 50, atZero = 0, passes = 0 }
```

(`|>` isn't in the language; `(ls.filterMap parseRot).foldLeft start step` is the dot-notation form.)

**Verdict: done today; the proofs need the arithmetic lemma library.** Easy.

## 4. Day 2: invalid product ids

**Task.** The input is one line of comma separated ranges `a-b`. An id is "invalid" when its
decimal digits are some block written twice (part 1), or some block repeated two or more times
(part 2). Sum the invalid ids that lie in any range.

**The user's approach** (`day02/Day02.scala`). Parse the ranges; for every number in every range
(`(start to end).sumWhere`), test it with a regex on its string: `^(\d+)\1$` for part 1 and
`^(\d+)\1+$` for part 2. Brute force; fine on the JVM.

**Needs.** Splitting on `,` and `-`; `natToText`/digit lists; `Nat` up to 10 digits; either a
decimal digit test per id, or (better) a way to generate or count invalid ids directly.

**Input size** (`day02/input.txt`, 391 bytes, one line, no trailing newline): 28 ranges; **1,917,096
ids in total** (largest single range 181,930); the largest value is 9,899,009,366, so ids have at
most 10 digits and the smallest start is 4.

**Computation.** The brute-force port is about 1.9 million ids, twice (two parts). A digit test on
a 10-digit number through `natToText` is thousands of steps in the reference evaluator (see the
rule of thumb), so something like **10^10 steps, several minutes**: poor. Two better
shapes:
- *Generate the candidates.* Every invalid id is `base` repeated `r >= 2` times, with `base` of
  `k` digits and `k * r <= 10`. For part 1 (`r = 2`), `k` from 1 to 5, that's
  9 + 90 + 900 + 9,000 + 90,000 = 99,999 candidates (my count agrees with an independent
  enumeration). For part 2, to avoid counting an id twice (111111 is `1` six times, `11` three times and
  `111` twice), take only **primitive** bases (not themselves a repetition): 101,088 distinct
  ids. Then check each against the 28 ranges: about 2.8 million `contains` calls each part.
- *Closed form per range.* For each range and each `(length, k)` the invalid ids are
  `base * m` with `m = (10^len - 1) / (10^k - 1)`, so their sum is an arithmetic series over
  `base` in a computed interval. About `28 * 9 * 5` terms, a few hundred thousand steps. Part 2
  needs inclusion-exclusion over the divisors of the length (or the primitive trick).

**What I measured.** The candidate-generation prototype (written naively) printed correct answers
for both parts in 21.7 s. Of that, 14.6 s is generating the candidates (the primitive check calls
`natToText` three times per base, and does so for 100,000 bases), and the rest is
2 * 100,000 ids times 28 ranges. Calling `natToText` once per base, or deciding primitivity
arithmetically, brings it to a few seconds; the closed form to well under one.

**Provable.**
1. The worked example as `rfl`.
2. Parser round trip for the range list (`textJoin`/`textSplit` give the first half; `natToText`
   inverse gives the rest).
3. Soundness of the generator: every id it produces satisfies `Repeats k r id` (a proposition
   defined from the digit list). Straightforward by induction on `r`.
4. Completeness (every invalid id in range appears) is harder: it's the statement that an id
   whose digit list is a block repeated is `rep base r`, needing facts connecting `natToText`,
   its digit list and repeated blocks. Best done on the digit list, with `Nat` entering only at
   the end.
5. The closed form equals the generator on all ranges below some bound, as a `test`, not a
   theorem.

**Sketch (runs today, abbreviated).**

```
def pow10: Nat -> Nat
  | Zero   => 1
  | Succ k => 10 * pow10 k

-- `base` written r times; shift = 10^(digits of base)
def rep (shift: Nat) (base: Nat): Nat -> Nat
  | Zero   => 0
  | Succ r => rep shift base r * shift + base

-- is the digit list some shorter block repeated? (d counts down from n - 1)
def hasPeriod: Nat -> Nat -> List Char -> Bool
  | Zero,   n, ds => False
  | Succ d, n, ds =>
    if eqNat (n % Succ d) 0
    then (if eqPrefix (dropN (Succ d) ds) ds then True else hasPeriod d n ds)
    else hasPeriod d n ds
```

**Verdict: runs today but slowly; needs a smarter algorithm (generator or closed form), which
also gives the more interesting proofs. Medium.** The user may prefer a faithful brute-force port
as the *specification* (feasible on the example, not on the input) and the closed form as the
program, proving them equal on small ranges by `test`.

## 5. Day 3: battery banks

**Task.** Each line is a bank of single-digit "batteries". Choose exactly k batteries, in order
(a subsequence), to form the largest k-digit number; part 1 has k = 2, part 2 has k = 12. Sum
the best number of each bank.

**The user's approach** (`day03/Day03.scala`). A memoised search `largestPossibleJoltage(length, fromIndex)`:
try every next position `i >= fromIndex`, recurse with `length - 1` from `i + 1`, take the
maximum. An `@cached` macro annotation memoises it. Exhaustive over positions, polynomial
because of the memo table (about 12 * 100 states, each trying up to 100 positions).

**Needs.** Digits from characters (`charToNat c - 48`), a list, a loop of length k. With the
greedy algorithm, **no map or memo table is needed**, which is the point: the exhaustive memoised
search needs a hash map (or a 2D table) that Stitchwort doesn't have.

**Input size** (`day03/input.txt`): 200 lines of exactly 100 digits, all in 1 to 9.

**Computation.** Greedy: choose each digit as the first largest in the window that still leaves
enough digits. About `k * 100` digit visits per bank, about 15,000 steps per bank, about 3
million steps for the input. Measured 0.26 s. The user's search costs 12 * 100 states * 100
candidates = 120,000 per bank, 24 million for the input, plus the memo's cost.

**Provable.**
1. Worked example as `rfl` (each of the example's four banks and the sums).
2. Structural facts about `best k ds`: the result has at most `k` digits; the chosen digits form
   a *subsequence* of the bank (define `Subseq: List a -> List a -> Prop` inductively).
3. **Optimality:** for every subsequence `s` of `ds` of length `k`, `value s <= best k ds`.
   The proof is the classic exchange argument: the greedy first digit is at least the first digit
   of any admissible subsequence (because the window contains every position such a subsequence
   could use first), and among subsequences starting with the maximum digit at its first
   occurrence, the rest of the subsequence can be assumed to start later. Needs `<=` lemmas and
   a lexicographic-versus-numeric lemma (same-length digit lists compare as their numeric
   values). This is the most interesting proof of days 1 to 5, and is the sort of thing the user
   asked for ("proofs of correctness"). It will be long without automation.
4. Equality with the *user's* exhaustive formulation (a pure recursive `bestBrute`, no memo) on the
   examples by `rfl`/`test`, as a cross-check; the exhaustive version is exponential without the
   memo, fine for 15-digit banks.

**Sketch (runs today).**

```
-- scans at most w elements; returns the first largest and what follows it
def pickGo: Nat -> List Nat -> Nat -> List Nat -> Pair Nat (List Nat)
  | Zero,   ds, b, br => MkPair b br
  | Succ w, Nil, b, br => MkPair b br
  | Succ w, Cons d rest, b, br =>
    if leq (b + 1) d then pickGo w rest d rest else pickGo w rest b br

-- the largest k-digit number from a subsequence of ds, digit by digit
def best: Nat -> Nat -> List Nat -> Nat
  | Zero,   acc, ds => acc
  | Succ k, acc, ds => bestStep k acc (pickGo (length ds - k) ds 0 Nil)

def bestStep (k: Nat) (acc: Nat): Pair Nat (List Nat) -> Nat
  | MkPair d rest => best k (acc * 10 + d) rest
```

(The start value `0` for the best digit assumes digits are at least 1, true of this input; the
library version takes the first element as the start, and the proof has to carry that.)

**Namespaced future:** `ds.take`/`ds.drop` and `List.maximumBy` would replace `pickGo`; the
proof is easier about a `pickGo`-style scan than about a library `max` plus `indexOf`.

**Verdict: done today; the optimality proof is the showcase. Easy to run, hard to prove.**

## 6. Day 4: paper rolls on a grid

**Task.** A grid with `@` (a paper roll) and `.`. A roll is accessible if fewer than four of its
eight neighbours are rolls. Part 1: how many are accessible. Part 2: remove all accessible
rolls, repeat until none are accessible, and count how many were removed in total.

**The user's approach** (`day04/Day04.scala`). The grid is a `Set[Point]` of roll coordinates;
`adjacent8` is a cross product of offsets minus the point; `forkliftCanAccess` intersects the
neighbours with the set. Part 2 is `iterateUntilStable` of "filter out the accessible ones".

**Needs.** 2D neighbours without negative offsets. A grid representation. A loop until
nothing changes (a fixed point).

**Input size** (`day04/input.txt`): 136 rows of 136 columns, 12,051 rolls (65 %), **84 rounds
until stable (the last removes nothing)**.

**Computation.** The user's version with a set: 85 rounds * 12,051 rolls * 8 lookups is about 8 million
set operations (85 rounds in the user's count; 84 by mine), trivial for a hash set but a problem for lists (a list-based membership test is
linear). Not usable without a map/set structure *or* a representation that avoids lookups:
rows as lists, with each row's horizontal 3-sum computed once and the three rows' sums added
(prototype). Per round that's about 3.5 million steps; 84 rounds is about 300 million steps,
measured **7.1 s**. A worklist version (only recheck the neighbours of a removed roll) touches
about 12,000 rolls * 8 neighbours, but needs random access or a map: with a grid as
`List (List Nat)` an update is O(rows + columns) = about 270 steps, so about 26 million: faster
only with an `Array`.

**Provable.**
1. Worked example (counts for both parts) as `rfl`.
2. `round` only removes rolls (the new grid is cellwise `<=` the old one), and `removed` equals the
   drop in total rolls. Simple induction over the rows.
3. **Fuel is enough:** every round that doesn't stop removes at least one roll, so the number of
   rolls decreases; starting fuel = initial roll count. Then the fixed point theorem:
   *the result has no accessible roll* (`round result` removes 0).
4. `round` agrees with a direct "count the eight neighbours" specification written the way the
   puzzle describes it (a function from a coordinate to a count using list indexing with
   bounds checks), on the example by `rfl` and in general by induction (this is a real proof:
   the row-shifting trick must be shown to compute the 3 by 3 window sum).

**Sketch (runs today; helper definitions elided).**

```
-- horizontal 3-sums of a row of 0/1: hs 0 row
def hs (prev: Nat): List Nat -> List Nat
  | Nil               => Nil
  | Cons x Nil        => Cons (prev + x) Nil
  | Cons x (Cons y r) => Cons (prev + x + y) (hs x (Cons y r))

-- up, mid, down 3-sums and the row itself: a roll stays if the window holds 5 or more
-- (itself plus at least 4 neighbours)
def combine: List Nat -> List Nat -> List Nat -> List Nat -> Row
  | Cons u us, Cons m ms, Cons d ds, Cons x xs =>
    combineStep (leq 5 (u + m + d)) x (combine us ms ds xs)
  | _, _, _, _ => mkRow Nil 0

def peel: Nat -> List (List Nat) -> Nat -> Nat     -- fuel = number of rolls
  | Zero,   g, acc => acc
  | Succ f, g, acc => peelStep f (round g) acc
```

**Verdict: runs today, correct, 7 s; wants an `Array` (or at least `List.get`/`zip`) and a
`Set` for a natural version. Medium; proofs of the rolling-window trick are the interesting part.**

## 7. Day 5: fresh ingredient ranges

**Task.** The input has two sections separated by a blank line: a list of inclusive ranges
`a-b`, then a list of ingredient ids. Part 1: how many ids fall inside at least one range. Part
2: how many distinct numbers are covered by the ranges together.

**The user's approach** (`day05/Day05.scala`). Parse with `splitOnBlankLines`. Part 1 is
`ranges.exists(_.contains(id))` per id. Part 2 inserts each range, in input order, into a
`SortedDisjointRanges`: `insertAndOptionMerge` keeps the list sorted by start and disjoint, merging
whatever the new range overlaps (note `a.end < b.start`: adjacent ranges like 1-3 and 4-6 are *not*
merged, which doesn't change the count). The class asserts the invariant on construction.

**Needs.** Reading two sections; a record for a range; `min`, `max`; **no sort** (the insertion
keeps the list ordered); numbers to 15 digits.

**Input size** (`day05/input.txt`): 190 ranges, 1,000 ids; the largest value is
562,888,848,953,868 (15 digits, over 2^31 but below 2^53 and 2^63); the ranges together cover
about 4.2 * 10^14 numbers (so any enumeration is out of the question); the 190 ranges merge into
about 92.

**Computation.** Part 1: 1,000 ids * up to 190 ranges, about 190,000 `contains` calls: under 5
million steps. Part 2: 190 insertions into a list of at most 92: about 17,000 steps of 30
each. Measured 0.47 s total (reading 1,190 lines, 380 `textToNat` on 15-digit numbers
included).

**Provable.** This day is the best fit for dependent types.
1. Worked example as `rfl`.
2. A type for the invariant: `Sorted: List Range -> Prop` ("each range's `to + 1 <= ` the next range's `from`")
   and `addRange` returning a list together with a proof that it's sorted,
   or just a lemma `Sorted rs -> Sorted (addRange r rs)`. That's a direct translation of the user's
   `assert`.
3. **Membership is preserved:** `covered (addRange r rs) x = (covered rs x || contains r x)`. By
   induction on `rs`, with the merge case using `min`/`max` lemmas.
4. Part 2 count: `sumL (mapL size merged)` equals the number of `x` below an upper bound for which
   `covered` holds, on small ranges by `test` (brute force); a general proof needs a notion of
   cardinality of a finite subset of `Nat`, not worth it; the right theorem is that the merged
   list is sorted, disjoint, and covers exactly the same numbers, from which the sum of sizes is
   the count by a small standalone lemma about disjoint intervals.
5. Parser round trip for `a-b`: `textSplit` with `textJoin` plus the number round trip.

**Sketch (runs today; helpers `filterMap`, `foldLeft`, `anyL`, `countL`, `sumL`, `minN`, `maxN` are
each four lines and belong in the library).**

```
type Range = { from: Nat, to: Nat }

def contains (r: Range) (x: Nat): Bool := if leq r.from x then leq x r.to else False

def size (r: Range): Nat := r.to + 1 - r.from

-- keeps the list sorted and disjoint
def addRange (n: Range): List Range -> List Range
  | Nil => Cons n Nil
  | Cons h t =>
    if leq (n.to + 1) h.from then Cons n (Cons h t) else addAfter n h t

def addAfter (n: Range) (h: Range) (t: List Range): List Range :=
  if leq (h.to + 1) n.from
  then Cons h (addRange n t)
  else addRange (mkRange (minN h.from n.from) (maxN h.to n.to)) t

def solveWith (rs: List Range) (ids: List Nat): Pair Nat Nat :=
  MkPair (countL (i => anyL (r => contains r i) rs) ids)
         (sumL (mapL size (foldLeft (acc r => addRange r acc) Nil rs)))
```

(Termination: `addRange` recurses on the list in both branches that recurse, once with the
merged range, which is a different first argument but the list gets shorter: structural.)

**Verdict: done today; the most natural place for an invariant-carrying proof. Easy.**

## 8. Days 6 to 9 (refreshed 18 October 2026)

The first version of this section was written before namespaces, the list toolkit, `Int`,
sorting, `==` on lists, `readAllLines`, `Nat.digits`, tuples, pattern `let` and local
definitions existed. Today the prelude has: `List.map filter foldLeft foldRight sum sumBy product any
all count find elem partition lookup filterMap concat concatMap zip zipWith zipWith3 take drop get last
replicate range rangeFrom reverse maximum minimum scanLeft`, `List.sort/sortBy/sortWith` (stable
merge sort, O(n log n), with `Sorted` and `Perm` proved), `Text.split lines join trim toNat
toList fromList uncons`, `Nat.min max absDiff pow digits fromDigits toText`, `Int` with `abs`,
`natAbs`, `tdiv`, `fmod` etc., and `IO.readAllLines`. Still absent: arrays, maps, sets, any
random access better than `List.get` (O(n)), `transpose`, `List.maximumBy`, `[x, ..rest]`
patterns (queued), and a fixed-point or `iterate` helper. "Steps" below use the section 0 rule of
thumb: 40 to 50 million steps a second, 30 to 200 steps per list element for a small function.

### Day 6: worksheet of column problems

- **Needs.** The input is 5 lines of 3,780 characters: four rows of numbers, then a row of `+`
  and `*`. Part 1 reads each whitespace-separated column as a problem. Part 2 reads each
  character column (right to left) as one number, blank columns separating problems.
- **Covered today.** `Text.lines`/`readAllLines`, `Text.split` then dropping empty fields
  (`filter`), `Text.toNat`, `sum`, `product`, `Text.toList`, `List.zip`, `Nat.fromDigits`.
- **Missing.** `List.transpose` (small; part 1 can use `zipWith`, part 2 needs it, with the
  short lines padded with spaces: a `padRight` helper). A split-a-list-at-blank-entries helper
  would also be reused by day 5's input. Nothing in the language.
- **Cost.** About 4 * 3,780 = 15,000 characters, each touched a few times: under a million
  steps (well under a second).
- **Plain approach.** Part 1: split each row on spaces, drop empty fields, transpose, pair with
  operators, fold each column. Part 2: take the character grid, pad, transpose, group the
  columns into problems at blank columns, read each column's digits with `fromDigits`, and take
  the operator from the last row at the first column of each group.
- **Worth proving.** Examples by `rfl`; transposing twice gives back a rectangular list.
  Anything deeper is low value.

### Day 7: tachyon beam splitters

- **Needs.** 142 lines of 141 columns, 1,711 splitters. Part 1 counts splits as a beam falls
  row by row; part 2 counts the distinct paths ("timelines") through the splitters; answers
  have up to 14 digits (fine, `Nat` is native).
- **Covered today.** Everything, if the state is a `List Nat` of 141 per-column counts and one
  row is one `zipWith`-style pass: a splitter at column c sends its count to c-1 and c+1.
  Part 1 counts the splitters whose incoming count is above zero.
- **Missing.** Nothing essential. A 3-wide window helper (`windows 3`) makes the row step one
  line (new count at c = the left neighbour's count if it is a splitter + the right neighbour's
  if it is a splitter + the beam falling straight on if there is no splitter below);
  otherwise it is three `zip`s. `[x, ..rest]` patterns would help a hand-written version.
- **Cost.** About 71 splitter rows * 141 columns * 150 steps = 1.5 million steps: well under a
  second. No performance risk.
- **Plain approach.** Fold over rows, state = counts vector; the answer to part 2 is the sum
  of the final vector; part 1 adds, per row, how many splitters had a non-zero count above.
- **Worth proving.** The best candidate of days 6 to 9: each row step preserves the total
  (plus the splits it counts), so the final sum is the number of paths. An invariant over
  `zipWith`, by induction on the row. Medium effort; Opus.

### Day 8: junction boxes (1,000 points in 3D)

- **Needs.** Join the 1,000 closest pairs of points (by squared distance) into circuits; part 1
  is the product of the three biggest circuit sizes after 1,000 joins; part 2 keeps joining
  until one circuit remains and multiplies the x coordinates of the final pair.
- **Covered today.** Squared distance with `Nat.absDiff` and `*`, so no `sqrt` or `Double` is
  needed (ordering by squared distance is the same ordering). `List.sortBy` exists and is
  O(n log n). Parsing: `Text.split` on `,` and `Text.toNat`.
- **Missing.** (1) A cheap way to ask "which circuit is point i in, and merge two circuits":
  with a `List` label vector each merge is O(n). (2) Speed at 499,500 pairs.
- **Cost.** Sorting all 499,500 pairs: about 9.5 million comparisons at roughly 60 steps each,
  plus building the pairs, so 600 million steps or more (12 to 15 seconds), and half a million
  tuples in memory. Part 1's merges: 1,000 * 1,000 = 1 million steps. Part 2 walks on in sorted
  order; the worst case is 499,500 merges * 1,000 = 500 million steps, but it stops once the
  last point joins, normally after a few thousand pairs. So about 15 to 25 seconds in total:
  acceptable for a one-off run. (Prim's algorithm needs no sort for part 2, but part 1 still
  needs the 1,000 smallest edges, so it is not worth it.) These are estimates; the evaluator
  speed check should confirm them.
- **Plain approach.** Generate pairs (`i < j`), compute squared distance, sort once, fold over
  the sorted pairs with a label `List Nat` (relabel on merge: `map (l => if l == a then b else
  l)`); stop part 2 when one circuit is left.
- **If too slow:** an `Array` (union-find with O(1) access), or a native `sortBy` in the
  evaluator.
- **Worth proving.** Sort correctness is already in the prelude. Beyond that: the worked
  example by `rfl`, and that each useful join lowers the circuit count by one. A proof that the
  label vector stays an equivalence is hard and low value.

### Day 9: movie theatre rectangles (495 points)

- **Needs.** Part 1: the largest rectangle with two of the red tiles as opposite corners, area
  `(|dx| + 1) * (|dy| + 1)`. Part 2: the largest such rectangle lying wholly inside the
  closed loop made by joining the points in order. The user's Scala has no part 2 (`???`).
- **Covered today.** Part 1: all pairs (about 122,000), `Nat.absDiff`, `maximum`: roughly 12
  million steps, a quarter of a second.
- **Missing for part 2.** Coordinates run to about 98,000, so a pixel grid (10^10 cells) is out.
  The standard answer is coordinate compression: only the distinct x and y values of the 495
  points matter, giving a grid of about 250 by 250. Then mark the outside with a flood fill,
  build a 2D prefix-sum table so "is this rectangle all inside" is four lookups, and test every
  pair. That needs **random access in a 2D table** (`List.get` on lists of lists is O(n) per
  access; 122,000 pairs * 4 lookups * 250 steps is about 120 million steps, around 3 seconds:
  bearable, but an `Array` makes it clean) and a **sorted dedup plus index lookup** (small).
  Part 2 is a hard puzzle in any language and the most design work of the four days.
- **Plain approach.** Part 1 as above. Part 2: compress, rasterise the edges, flood from
  outside, prefix sums over inside cells, check each pair.
- **Worth proving.** The area formula on the example by `rfl`; "area is symmetric in the two
  corners" is a short lemma over `absDiff`. Nothing deep.
- **Done** (24 October 2026): see "Day 9" below; both parts proved for every input, with a
  summed-area table over lists and no `Array`.

## 9. Friction found while writing the five programs

Found by actually writing and running them, so these are evidence, not guesses.

1. **Prelude names clash** with natural user names: my first `add` (adding a range to a list)
   was `E-DUPLICATE: add is already defined` (prelude `add`). Also `L` and `R` (constructors of
   the prelude's `Plus`) for left/right. Namespaces fix this. The programs use `addRange`, `TL`
   and `TR` instead.
2. **A crash:** declaring `type Dir: Type = | L | R` and then using the constructors in a
   *record* pattern, e.g. `f { dir = R, amount } = amount`, makes the compiler panic
   (`index out of bounds: the len is 0 but the index is 0` at `crates/elab/src/records.rs:430`),
   instead of reporting the `E-DUPLICATE` it gives for the same declaration alone. Repro file:
   a `Dir` type, `type Rot = { dir: Dir, amount: Nat }` and one such equation. Probably error
   recovery after the duplicate. (Built from another worktree's binary; may already be fixed.)
3. **`else` at the start of a line is a parse error** with a baffling message
   (`expected else, but found else`): an `if ... then ... ` followed by `else` on the next
   line is read as a block statement. Everyone writing `if/else if/else` chains over several
   lines will hit it. I wrote three one-line `if`s or moved the else-branch into a helper
   function in both days 2 and 5. A real `else`-continues-the-line rule would fix it.
4. **A record literal needs a known type**: `Some { dir = TL, amount = n }` inside a lambda
   passed to `optionThen` is `E-CANNOT-INFER`; a `mkRot: Dir -> Nat -> Rot` helper fixes it
   (annotation `(…: Rot)` also works, per the error's own note). *Fixed (17 October 2026):
   the expected result type is now used first
   ([syntax-conveniences.md §7](proposals/syntax-conveniences.md#7-knowing-more-expected-types-result-type-first)).*
5. **No `where` and no local functions**: every helper is a top-level definition with a
   signature, so a 30-line algorithm becomes 10 definitions (`combine`, `combineStep`, ...).
   Stepping through "recurse, then post-process the result" costs a named helper each time
   (`rndStep`, `rndJoin`), because patterns can't appear in `let` or lambdas. A `case`
   expression or pattern-matching `let`/lambda would remove most of these.
6. **No tuple sugar**: `MkPair`, `fst`, `snd` everywhere.
7. **Repeated helpers**: `mapL`, `foldLeft`, `anyL`, `countL`, `sumL`, `filterMap`, `dropN`,
   `minN`, `maxN` and the six-line reader are redefined in each file (about 30 lines each).
8. **Text is slow in the reference evaluator**: the day 2 generator spent 14 s mostly on
   `natToText`/`textToList`. A native (or a counted version) for digits of a `Nat` would be
   worth having if digit problems matter. (The generated JS `Text` is native: this is about the
   interpreter that `run`, `test` and the checker use.)
9. **Run speed**: 40 to 50 million steps per second. The `run` command doesn't print timings
   (I used `time`).
10. **Good surprises:** big `Nat` arithmetic is native and instant (15-digit values everywhere,
    no care needed); `auto` found the non-zero proofs for `% 100`, `/ Succ k` without help; records
    and `Partial` worked on first use; error messages with source spans were precise.

## 11. Harness design

**Layout (proposal).**

```
aoc/
  stitchwort.yaml             a project: sources are src/
  src/Aoc/Common/Range.sw     namespace Aoc.Common, what days share
  src/Aoc/Year2025/Day01/Day01.sw ...  namespaces Aoc.Year2025.Day01 ... Aoc.Year2025.Day07 (the program: parse, solve, thin `main`)
  src/Aoc/Common/Tests/, src/Aoc/Year2025/DayNN/Tests/
                              namespaces Aoc.Common.Tests, Aoc.Year2025.DayNN.Tests: the example puzzle texts, unit tests
                              (Examples.sw) and the real-input answer tests (Input.sw, which `include`s inputs/)
  src/Aoc/Common/Proofs/, src/Aoc/Year2025/DayNN/Proofs/
                              namespaces Aoc.Common.Proofs, Aoc.Year2025.DayNN.Proofs: theorems and proof-only definitions,
                              so `stitchwort run Aoc.Year2025.DayNN.main` checks only the program, not its tests or proofs
                              (folders follow namespaces by convention: Aoc/Year2025/Day02/Proofs/ holds Aoc.Year2025.Day02.Proofs)
  run.sh                      runs one day or all
  README.md                   how to get the inputs (only a pointer; not puzzle text)
  inputs/                     committed: day01.txt ..., expected.txt
```

`.gitignore` gets `aoc/inputs/`. The inputs directory is overridable by `AOC_INPUTS`, so the
inputs can live outside the repository entirely (the user's own `aoc-2025` clone, whose layout
is `src/main/resources/dayNN/input.txt`, can be pointed at directly: the script accepts either
`$AOC_INPUTS/dayNN/input.txt` or `$AOC_INPUTS/dayNN.txt`).

**Running a day.** `cd aoc && stitchwort run Aoc.Year2025.Day01.main < "$AOC_INPUTS/day01.txt"`, or, much faster on
the heavy days, `stitchwort run --js Aoc.Year2025.Day01.main < …` (compiles `main` to JavaScript and runs it
with Node; day 4 takes 1.0 s instead of 17 s); each program prints
exactly `Part 1: N` and `Part 2: M`, as the Scala does. `run.sh` does, per day:
`stitchwort check`, `stitchwort test` (the inline example tests and `theorem`s: these run
without any input, so they can also run in CI), then `run` under `time`, and compares the output
with `expected`.

**Expected answers.** They're in the user's repo, in `src/test/scala/DayNNTest.scala`, as the
literals after `shouldBe` in the `"should work on puzzle input"` blocks. A one-off script
(not committed) extracts them into `aoc/inputs/expected.txt` (lines like `day01 1 <answer>`).
Keeping them out of the repository is the conservative choice: they're derived from personal
inputs, and Advent of Code asks people not to publish inputs; if the user is happy for
answers to be public (they already are, in the Scala repo), `expected.txt` could be committed.
Open question 3.

**Examples.** The puzzle's small worked examples are the best tests and the best `rfl`
theorems, but they're part of the puzzle statements, which we aren't to reproduce. The user's
Scala tests already contain them verbatim, so the same applies. Until the user says otherwise,
our own tests use tiny inputs of our own making (like the ones I used: three ranges, six ids)
and the real examples live only in the user's repo (open question 1).

**Keeping this out of the main gate.** `cargo test` and `nix flake check` run the example
programs (171 files in the benchmark), so `aoc/` is deliberately a separate directory, not
under `examples/`: its programs (several seconds each) shouldn't slow the gate. A generated
input in-language (an LCG producing 4,462 rotations) would let a single `aoc/` benchmark row run
without any puzzle data, which also fills the "generated rows aren't benchmarked" gap in
`TODO.md` Later.

**Timing and limits.** `stitchwort run` has no `--time`; the script times it. Resource limits:
the default limit is 2 million frames and a million-deep recursion peaks near 750 MB
(`TODO.md`, Known issues), so non-tail-recursive list functions are fine at day 1 to 5 sizes
(4,462 elements) but worth care for day 8's 500,000-element sort.

**Pleasant**

- The input reader is one call, `solve IO.readAllLines()`, against six hand-written lines.
- `match Text.uncons t with | Some (c, rest) -> ...` and tuple patterns in equations
  (`step (pos, landed, passes) t = ...`) read well.

  mirror trick for left turns.)

- `test` and `theorem ... = rfl` on the real example need no ceremony.

**Hurt**

- No pattern-matching `let`: `let (pos, landed, passes) = e` gives `E-PARSE: expected a name,
  but found (`, so a one-use helper `final` takes the triple apart.
- No alias for a tuple type: `type Dial = (Nat, Nat, Nat)` gives `E-PARSE: expected | and a
  constructor, or {`, so the triple is spelled out in three signatures. (The syntax docs say an
  alias is an ordinary definition, `Dial: Type`; the error doesn't hint at that.)
- No `where` (known missing, not tried): `turnOf`, `settle`, `final` are top-level only
  because they take apart a value inside a larger function.
- `==` on a user type needs a decision procedure: `parseTurn "L68" == Some (Left 68)` gives
  `E-AUTO-NONE: no way to decide Some (Left 68) = Some (Left 68)`. The note suggests
  `Option.decEq`, which helps, but with no `deriving` the tests compare a projection
  (`Option.map signed ...`) instead.
- A prelude name clash is reported with byte offsets only: adding `Nat.digits: Nat -> List
  Nat` next to the existing helper gave `E-TYPE-MISMATCH ... start: 65956` (a debug dump of
  `Diagnostic`, no file or line), not a duplicate-definition error.
- The `Partial` recipe (`{IO, Partial | e}`, a `more` parameter) is needed for every loop,
  library or not, and can't be guessed from the types.
- `Int` and `Nat` mixing: `Nat.toInt pos + signed t` everywhere; no literal or coercion
  help for a `Nat` position.

**Missing library functions noticed**: `List.scanLeft` (the Scala uses `scanLeft` for part 1; I
folded instead), an `Int` sum, and a way to take the first character off a `Text` and parse the

### Proofs (18 October 2026)

The shortcut in `aoc/src/day02/day02.sw` adds up whole runs of invalid ids with a formula instead of
testing each id. Two parts of it are now proved to give the same answer as the plain method,
and the third is checked against the plain method by a test. The implementation is unchanged;
everything new is below it in the file.

1. **One block length and repeat count** (`repeatedCorrect`). For every range `r`, block
   length `k` and repeat count `n`, `r.repeated k n` (the formula) equals `r.repeatedSpec k n`:
   take every `k`-digit block, write it `n` times (`writeTimes`, which shifts the copies so far
   `k` digits left and appends the block), keep the results that lie in the range, add them
   up. The specification walks blocks rather than ids; it counts the same ids, as an id made of
   a block written `n` times has just one such block (its first `k` digits). That choice keeps
   the proof about whole numbers rather than digit lists. The proof goes: writing `b` `n` times
   gives `b * m`; `lo <= b * m <= hi` exactly when `b` lies between `lo / m` rounded up and
   `hi / m` rounded down; so the ids in the range are `m` times a run of consecutive blocks,
   and a run's sum is Gauss's formula, `(first + last) * count / 2`.
2. **Part 1** (`part1BlocksCorrect`, named `part1Correct` until SW-6). The printed part 1 equals `part1Blocks`: for every range, every
   block length up to the number of digits of the range's end, the blocks of that length
   written twice that lie in the range, added up. Besides (1), this needed: the repeat counts
   other than 2 add nothing; a block too long to fit (written twice it has more digits than
   `hi`) adds nothing, from `hi < 10 ^ (number of digits of hi)` (`digitsBound`); and the sums
   of `Int`s are sums of `Nat`s.
3. **Part 2** (not proved). Its inclusion–exclusion over repeat counts (the Möbius weights) is
   checked by the test `brute force agrees`: on 160 ranges (40 ids each, starting every 13 up
   to 2,000, plus ranges across 100, 1,000, 10,000, 100,000 and 1,000,000 and around 111111) both
   parts are compared with a digit-by-digit brute force (an id is invalid when its digits are
   its first `k` digits written `n` times). About 2.5 s; changing a weight or the rounding
   makes it fail. (The `aoc` files aren't part of `nix flake check`.)

### Part 2 for every input (20 October 2026, SW-166)

`part2Correct` now has no hypothesis: `solvePart2 ranges = part2Spec ranges` for every list of

**The program change.** The weights are computed, not tabled: `plus n` and `minus n` (with
`weightFuel`, fuel recursion, and `divisorWeights`), so that over the divisors of any K from 2
on, plus adds up to one more than minus; `plus n - minus n` is minus the Möbius function (a test

**How** (for one id x with L digits, as in the prototype):

- `Period g len hl p`: rotating the digits by p places (index arithmetic,
  `g ((i + p) % len) = g i`) changes nothing. Periods add and subtract (`periodAdd`,
  `periodSub`, `periodMul`), so every period is a multiple of the smallest one (`periodDvd`:
  the remainder is a smaller period, so 0).
- The smallest period is a `Bool` search, `Nat.firstFrom` over 1..L with `isPeriod`
  (`smallestPeriod x = Succ (periodIndex x)`, so `/` and `%` by it need no proof), and
  `blockCount x = L / smallestPeriod x` is how often the smallest block is written.
- Digits are a k-digit block written n times exactly when k is a period (`writtenPeriod`,
  `periodWritten`, from `List.getOr` index lemmas and `Nat.modModOfMul`); so `copies x n`
  exactly when n divides the block count (`copiesDivides`), and `repeats x` exactly when the
  block count is at least 2 (`repeatsBlocks`).
- `plusOneMore`: over the divisors of m from 2 on, plus is minus plus `[m >= 2]`. Then one id's
  plus terms are its minus terms, plus x if x repeats (`idPlusMinus`), and `weightedIds` /
  `rangeSplit` swap the sums as before; `repeatedIds` (the n-copies lemmas) is reused as is.

### Proofs (18 October 2026)

`aoc/src/day03/day03.sw` now proves the greedy `best` correct. Everything checks in about 0.17 s
(`stitchwort check`, release build, prelude included); answers unchanged (17263 and
170731717900423). The file is 340 lines, 280 of them proofs.

What is proved, in plain words, for any `k` and any list of digits `ds`:

1. **It picks real batteries, in order** (`bestSub`): `Bank.best k ds` is a subsequence of `ds`,
   meaning `ds` with some digits left out and the rest kept in order (`List.Subsequence`).
2. **It picks the right number of them** (`bestLength`): `Bank.best k ds` has `min k (length ds)`
   digits, so exactly k when the bank has at least k.
3. **Nothing beats it** (`bestOptimal`, `bestIsLargest`): for every subsequence `s` of `ds`
   with k digits, `Nat.fromDigits s <= Nat.fromDigits (best k ds)`. (Until 22 October 2026
   this needed a hypothesis that every element of `ds` is below 10, and a `joltageIsLargest`
   restated it for an input line, discharging the hypothesis through `Bank.parse`. A bank is
   now a list of `Fin 10` digits, so neither exists: see "Over digits" below.)

The optimality argument is the usual one. Any choice of k digits starts with some digit `y`
inside the stretch `pick` scans (it has to leave k - 1 digits after it). If `y` is smaller
than pick's digit, the choice loses on its first digit: equal-length numbers with a smaller
first digit are smaller (`headLess`, which needs the digits to be below 10). If `y` is equal,
pick's digit is at the same place or earlier, because pick takes the leftmost largest, so the
rest of the choice comes from what follows pick's digit, where `best` does at least as well by
induction on k.

`best` changed slightly: `let (top, after) := pick …` became `let chosen := pick …` with
`chosen.fst` and `chosen.snd`, because a `let` pattern is a `match`, and a `match` on
`pick …` doesn't compute when `pick`'s arguments are unknown, so no proof could see inside it.
Once lets became transparent (docs/proposals/let.md), the pattern let came back: it now
elaborates to `Pair.fst`/`Pair.snd` of the value, so the proofs needed no change at all.

Added to the prelude: `List.Subsequence` with `List.subsequenceCons`, `List.subsequenceRefl`
and `List.subsequenceLength`; `Nat.leMulRight`; `Nat.minLeft`, `Nat.minRight`;
`Nat.fromDigitsFrom` and `Nat.fromDigitsCons` (the first digit counts `10^n`).

**Friction**

- **`let` hides its value from the checker.** Inside a proof, `let p := Nat.pow 10 n` makes `p`
  a fresh name: the checker won't see that `p` is `Nat.pow 10 n`, so lemmas about one don't
  apply to the other. A `let` whose value is a proof (`let h: a <= b := …`) failed outright
  with a universe error ("expected something of type `Type`, but this has type `Prop`").
  So the proofs repeat long expressions such as `Nat.pow 10 (List.length r)`, or move them into
  small named lemmas (`windowFits`, `windowStep`, `pickRestLength`).
- **No pair eta** (the point above about `let (top, after)`): a proof can't use that `p` and
  `(p.fst, p.snd)` are the same for an unknown `p`.
- **Reasoning about `if`** goes through `Bool.inspect` with the motive written by hand, and
  that motive has to spell out what the `if` became (`Decidable.elim (Bool.decTrue b) (u =>
  …) (u => …)`). Every lemma about `pick` repeats it.
- **Recursive calls had to be fully applied**, even when passed along as an induction
  hypothesis: `c2 a2 g1 g2 g3 y2 s2 g4 g5 g6 => pickBest k ih w more c2 a2 g1 g2 g3 y2 s2 g4
  g5 g6`. Since 27 October 2026 `pickBest k ih w more` is accepted: the argument that gets
  smaller, `w`, is among those given, so every call through it passes the same smaller `w`.
- **No indexed data types**, so `List.Subsequence` is a function computing a proposition
  (like `List.Sorted`) rather than a list of rules. That worked well: proofs match on its
  `Inl`/`Inr` cases directly.
- **Arithmetic is all by hand**: `Eq.trans`/`Eq.cong` chains with every argument written out.
  A `calc` block or a rewriting tactic would halve the arithmetic lemmas.

### Part 1 for every input (20 October 2026, D108; superseded by SW-180 below)

`part1Correct (lines) (w) (rect): solvePart1 (parseGrid lines) = part1Spec lines`, where `rect`

**The spec** (Spec/Spec.sw), in plain words: the lines are the rows of a grid; a cell holds a
roll when it is `@`, and everything off the grid is floor. "The forklifts can only access a roll
of paper if there are fewer than four rolls of paper in the eight adjacent positions": a roll is
accessible when fewer than 4 of its 8 neighbours hold rolls. Part 1 counts the accessible rolls,
row by row. The cells are read with an empty border (`rollAt` counts rows and columns from 1, so
row 0 and column 0 are the border). That way "the cell above" is row `r`, not `r - 1`, and needs
no special case at the top. The neighbours are added up column by column: the left column, the
cells above and below, the right column. The spec shares only `parseChar` with the program. Two

of floor past the top and bottom (`gap`) holds no rolls, the same as no row at all (`gapCells`).
The window is the neighbours plus the cell itself (`windowIsNeighbours`). A round only removes
rolls (`keepLe`), so `rolls - round.rolls` is the sum, cell by cell, of what the round takes
(`List.sumBySub`). What is taken is 1 exactly when the roll is accessible (`taken`).

**Part 2: the plan at the time** (carried out by SW-180, below). Part 2 uses `sweep`, which removes rolls in place going down
the grid, and only looks again at rows that changed or whose neighbours changed. Its end state is
the same as repeating `round`, but proving that takes an argument of its own:

1. *Spec.* Repeat the part 1 round (remove every accessible roll at once) until no roll is
   accessible, and count the rolls removed. As a function, iterate the round `rolls + 1` times;
   each round that changes something removes a roll, so that is enough. Part 1's `cellRound`
   already holds for any 0/1 grid, so the program's `round` is the spec's round.
2. *The core.* Call a set of rolls *stable* when every roll in it has at least 4 neighbours in
   it. Stable sets are closed under union, so there is a largest one inside the grid: the core.
   Removing only accessible rolls, in any order and any grouping, never removes a core roll,
   because a core roll always keeps its 4 core neighbours. A process that stops when no roll is
   accessible stops at a stable set, which lies inside the core. So every such process, the
   rounds and the sweep alike, ends exactly at the core, and both count `rolls - |core|`.
3. *The sweep.* Show that (a) a sweep removes only rolls that are accessible in the grid as it
   is at that moment (the row above is already swept); (b) the marks are sound: a row whose
   mark is False and whose neighbours' marks are False has no accessible roll, so skipping it is
   safe and a pass that changes nothing means no roll is accessible; and (c) the fuel suffices:
   every pass that changes something removes a roll, so after `rolls` passes nothing is left.

Estimate: 600 to 900 lines, most of it step 3(b) and the set reasoning in step 2 on lists of
lists. A cheaper alternative is to make part 2 repeat `round` until nothing changes. The proof
is then mostly part 1's, plus the fuel argument (perhaps 150 lines). But it runs 84 whole-grid
rounds instead of the sweep's 60 passes, most of them over skipped rows, so `dev/t aoc` would
slow down, possibly several times over (not measured). That trade-off is the user's call.

**Part 2: the core argument** (Proofs/Core.sw). Cells are a set of rolls. `Stable k`: every roll

- `stepKeeps`: a step never removes a roll of a stable set inside s, since that roll keeps its 4
  neighbours (`neighboursMono`). So `Keeps` passes along steps.
- `endsAgree`: two sets that are both stable, inside s0 and `Keeps s0` are the same, each
  holding the other. Both processes end at such a set, the largest stable set (the core), so they
  leave the same rolls and the answers agree.
- The rounds: a round is a step (`removeStep`). `roundsStable`: as many rounds as there are rolls
  leave a stable set, because a round with an accessible roll removes one (`roundCount`), and a
  stable set is left alone by every later round (`roundsFixed`).

**Part 2: the sweep** (Proofs/Sweep.sw, Proofs/Part2.sw).
- `sweepAt`: row r after a pass is `sweepRow` of the swept row above, and the row and the row
  below as they were (index lemma, as `roundFromAt`).
- `passKeeps`: a pass is a run of steps, one row at a time. `mix k` is the grid with rows 0 to

  `peelRowCells` with `mix k`'s rows), so it is a step (`rowStep`).
- `invSweep`: the marks are sound. `Inv m`: a row whose mark and the next row's mark are unset is

### Proofs (19 October 2026)

`solvePart2Correct (db: Database): solvePart2 db = countFresh db`, for every database.
`countFresh` is the puzzle read literally: the ids from 0 to the largest end of a range that
some fresh range holds, `List.range (top + 1) |> .count (id => db.fresh.any (r =>
r.contains id))`. Part 1 needs no theorem: `solvePart1` already is that sentence ("count the
available ids some range holds"). `aoc` checks in 0.41 s (0.37 s before); answers unchanged with
`run` and `run --js`.

The argument, in three parts:

1. **Merging keeps the covered ids** (`stackCovers`, and `mergeCovers` for `merge` itself).
   Sorting and reversing are permutations, and `any` only depends on how many elements pass
   (`List.anyPerm`). One `absorb` step adds exactly the new range's ids (`absorbCovers`), because
   a range starting inside the latest one, or just after it, joins it without gaining or losing
   ids (`mergedContains`). That needs the new range to start no earlier than the latest one
   (`LoAtMost`), which the sorted order gives (`Fits`, `fitsStep`).
2. **The merged ranges are stacked** (`stackStacked`): latest first, each starts after every id
   the ones below it hold. A range that isn't merged starts more than one past the latest end,
   and that range started after everything earlier.
3. **Stacked ranges add up** (`stackedCount`): the ids below `n` they hold number the sum of their
   sizes, when they hold nothing at or above `n`. The first range shares no id with the rest
   (`List.occurrencesOr`), and holds `size` ids below `n` (`Range.countFrom`, by induction on
   the ids; an empty range, `from > to`, has size 0 and holds none).

The bound comes from `coveredTop`: every held id is at most the largest end.

`stack` repeats `merge` without its last `reverse`, so the proofs can name the list being folded;
`merge` itself is unchanged. The test that merging keeps coverage on the example (ids up to 21)
became `mergeCovers`; a test checks `countFresh` on the example (14).

### Both parts for every input (20 October 2026, D108 and SW-144)

**Spec accepted (D121, 20 October 2026; Matt delegated the call).** The spec is puzzle-literal enough: it finds problems by the puzzle's own rule (a full column of spaces between problems), reads numbers cell by cell in the two directions the puzzle describes, and never transposes or splits. The pieces it borrows from the program are small and plainly right (`evaluate` adds or multiplies; `Operator.parse` maps `+` and `*`), and the one with real logic, `parseNumber`, is justified by `parseNumberWritten`. Reading past a line's end as a space is format, not meaning. The edge cases it settles arbitrarily (no operator counts 0; the first of several operators) never occur in a valid worksheet.

`part1Correct (lines): solvePart1 (parseWorksheet lines) = part1Spec lines`, and the same for
part 2 (`Aoc.Year2025.Day06.Proofs`, Proofs/Correct.sw). There is no precondition: the spec says what
happens on any input, so the theorems hold for every list of lines.

**The spec** (Spec/Spec.sw) reads the worksheet cell by cell. It never transposes or splits;
a problem is named by the column numbers where it starts and stops. In plain words:

- Column c of a line is its c-th character, or a space past its end.
- The last line holds the operators; the others (`numberLines`, `List.init`) hold the numbers.
- "Problems are separated by a full column of only spaces": columns `lo .. hi - 1` are one
  problem (`isProblem`) when column `lo - 1` is blank or `lo` is the left edge, `lo < hi`, none
  of its columns is blank, and column `hi` is blank. Every column past the widest line is blank,
  which covers the right edge.
- The operator is the `+` or `*` in the last line under the problem (the first, if there were
  several).
- Part 1: each number line, read across the problem's columns, is a number; spaces are skipped
  ("the left/right alignment of numbers within each problem can be ignored").
- Part 2: each column, from the rightmost ("cephalopod math is written right-to-left in
  columns"), is a number, its digits read from the top line down.
- The grand total (`grandTotal`) adds every problem's answer: a sum over all `lo` below the
  width and all `hi` up to it, keeping the pairs that are problems.

What is format and what is meaning: padding (short lines, the trimmed trailing spaces) is format,
so the spec reads a missing cell as a space and never mentions padding. Blank separator columns
are meaning (the puzzle says that is how problems are told apart), so they are in the spec, as
blank columns on either side of a problem. The spec shares four small things with the program:
`parseNumber` (the digits in some cells, as a number), `evaluate` (`+` adds, `*` multiplies; a
problem without an operator, which the puzzle never has, counts 0), `Operator.parse`, and
`gridWidth` (only a bound on where problems can be). `parseNumberWritten` shows the reading is the
right one: a number written in decimal with any spaces before and after it reads back as itself.
Tests check the spec on the example (4277556 and 3263827) and on one problem's numbers.

**The proof**, in three steps:

1. Padding then transposing gives the worksheet's columns cell by cell (`columnsAre`). This is
   the cell-level transposition the first round lacked: the library's `List.transposeGrid` says a
   grid given by a function `cell x y` transposes to `cell` with the roles swapped.
2. Splitting the columns at the blank ones gives exactly the spec's problems (`blocksTotal`). The
   general fact is the library's `List.splitByRuns`: for positions `0 .. n - 1` with position `n`
   a separator, summing over `List.splitBy` is summing over all maximal runs `lo .. hi - 1`
   (`Nat.isRun`). Its proof reads `splitBy`'s right-to-left loop: the open group is the run up to
   the first separator (`Nat.firstFrom`), and a group is closed at every separator followed by a
   position that isn't one. Then for each `lo` exactly one `hi` makes a run, or none
   (`List.sumRangeOne`/`sumRangeNone`).
3. Each block, transposed back, reads the same numbers and operator as the spec reads from the
   cells (`blockRows`, `blockColumns`, `blockOperator`), and the right-to-left order of part 2
   changes neither a sum nor a product (`evaluateReverse`).

Design: `parseManifold` finds the first S and turns the rows below it into rows of splitter
flags, all padded to the widest line. Part 1 carries a row of beam flags down (`fall`: a beam
passes a column without a splitter, a splitter with a beam sends one down each side) and adds up
the splitters each row's beams reach. Part 2 works up from the bottom (`splitRow`): below the
last row every column has one timeline; a column of a row above has the count of the column

## Day 8 proofs (22 October 2026, SW-198, D543)

Day 8 is proved for every list of boxes, against the connectivity spec of D543
(`aoc/src/Aoc/Year2025/Day08/Proofs/`). No other day 8 solution we found proves anything about the answer
(docs/comparisons/aoc-day08-community.md).

**Spec** (Spec.sw). The connections are every pair of boxes `i < j`, sorted by the key
`(squared distance, i, j)`, so ties are decided and stated: `connectionOrder points` is
`(List.range n).pairs` sorted by `Ord.compare` on that key, and `firstConnections k` its first
k. Pairs already in one circuit count. Two boxes are in the same circuit when a chain of the
connections links them:

```
type Joined (connections: List (Nat, Nat)): Nat -> Nat -> Prop =
  | Itself (box: Nat): Joined connections box box
  | Connected [a b: Nat] (connection: List.Mem (a, b) connections): Joined connections a b
  | Backwards [a b: Nat] (joined: Joined connections a b): Joined connections b a
  | Chain [a b c: Nat] (first: Joined connections a b) (next: Joined connections b c): Joined connections a c
```

`Joined` is a proposition, so counting boxes needs a test for it: `Tells n connections
sameCircuit` says the Bool test agrees with `Joined` on the boxes `0 .. n - 1`.
`circuitSizes n sameCircuit` lists each circuit's size once, at its lowest-numbered box, and
`threeLargestProduct` sorts descending, takes 3 and multiplies. `OneCircuit n connections`
says all boxes are joined, and `LastNeeded points k` says connection k is the one after which
they first are.

**Theorems.**

```
theorem labelsTell (n: Nat) (connections: List (Nat, Nat)) (ok: List.all (boxesBelow n) connections = True):
```

### Pain points

1. **`rewrite` replaces every occurrence, and a `J` motive often wants one.**
   `twiceBlockLength` (`day02.sw:276`), `twiceAbove` (`day02.sw:309`) and `repAbove`
   (`part2proof.sw:91`) carry a fact along `length (take k ds) = k` or `take k ds = ds`, but the
   motive abstracts only the exponent (`t => pow 10 (t - 1) <= fromDigits (take k ds)`), not the
   `k` inside `take k ds`; `rewrite` would change both. The proposal's "choosing occurrences"
   (stage 3) is the missing tool. There is no workaround but `J`.
2. **No `rewrite … at h`.** `Eq.trans (Eq.sym (J (y q => writtenAs (digits y) … = True) fact e)) hq`
   (`day02.sw:372`, `part2proof.sw:157`) rewrites a *hypothesis* in a position whose goal isn't
   known (the argument of `Eq.sym`), so `rewrite` there would be `E-REWRITE-NO-GOAL`. A form that
   rewrites a named hypothesis, or the type of a term, would remove these `J`s.
3. **`match` generalises more than the scrutinee you see, so a branch's goal is not the one you
   wrote.** `Range.countFrom` (`range.sw:58-80`): under `match t: Nat.leq r.lo s, i: Nat.leq s r.hi with`
   each branch's goal has already unfolded `contains` and `max`. A `calc` that starts at the
   statement fails with `E-CALC-GOAL`: "the first line, `List.occurrences (id => Aoc.Common.Range.contains r id)
   (List.rangeFrom (Succ c) s)`, differs from the goal's left side `List.occurrences (id => Bool.ifThenElse
   (Decidable.toBool (Bool.decTrue (Nat.leq … id))) …) (List.rangeFrom c (Succ s))`". Each branch's
   `calc` starts and ends at the computed form (with a comment saying so). A hypothesis's type is
   generalised as well (`termsSum`, now `twiceTerms` in `day02.sw`: `fits` becomes `False = False -> …`, so the call is
   `fits rfl`; `coveredTop`, `day05.sw:83`: `h` is already `covered rs id = True`). This is syntax.md's
   "branch goals have already computed one step", and it is the surprise.
4. **Generalising leaks `Decidable.toBool (Bool.decTrue …)`.** `Range.countEmpty` (`range.sw:96`):
   `E-TYPE-MISMATCH` "expected `Decidable.toBool (Bool.decTrue (Nat.leq id (Aoc.Common.Range.hi r))) = False`,
   but this has type `Nat.leq id (Aoc.Common.Range.hi r) = False`". The fix is `Bool.decTrueToBool`
   (also `day05.sw:196` and `198`). `x <= y` as a `Bool` should print and compute as `Nat.leq`.
5. **`match h: a <= b with` can be `E-MATCH-MOTIVE`; `match h: Nat.leq a b with` is fine.**
   `day02.sw:549` (`laterCounts`) first failed with "generalising this `match`'s scrutinee makes
   its type ill-formed … checking the type it would have: type mismatch". The message doesn't say
   which scrutinee form to use, and the helper-function advice doesn't help.
6. **`||` and `&&` in a `calc` need parentheses.** `day05.sw:210`: `E-PARSE` "expected a step
   `_ = e` on the next line, indented past `calc`, but found `||`" for the first expression, and
   "expected the end of the arm, but found `||`" for a step. `+` and `*` are fine.
7. **`%` and `/` unfold before the search, so a rule about them often finds nothing.**
   `stepLeftTop` (`day01.sw:256-263`): `rewrite Nat.divOne n, Nat.divOne (Succ n)` is
   `E-REWRITE-NOTHING` "found no `Succ (Nat.divFuel n n 1)` in the goal" (the first rule had
   already rewritten both), and `rewrite Nat.modSmall 1 …` is "found no `1`" because
   `1 % Succ (Succ t)` computes to `1` by itself, so that `calc` step needs no proof at all. The
   computed goal in the note is what made each of these quick to fix.
8. **`rewrite` can be slow where the goal contains a big closed computation** (the `*Checked`
   facts above: about 1 s each), and `E-REWRITE-BUDGET` shows an unreadable term when the rule is
   closed and big (`kFold`). The metrics line (`steps=`) doesn't show the slow case at all. A
   per-declaration time report from `stitchwort check` would have found it at once: I bisected by
   swapping proofs back against a copy of the old project.

   *Since (SW-207, 24 October 2026):* for 7, `E-REWRITE-NOTHING` now shows what the left side
   computes to (`Succ n / 1` is looked for as `Succ (Nat.divFuel n n 1)`), labels the goal as
   the one after the rules before, and says when that goal already holds by computing
   (`examples/reject/rewrite-nothing-computed.sw`). For 8, `E-REWRITE-BUDGET` puts the two terms
   in notes, shortened, with the left side read back with its calls folded, and points at
   `STITCHWORT_FULL_TERMS=1`. A call that computes at once (`kFold`'s `9` and `2`) still shows
   computed.
9. **A `match` reports one branch error at a time.** In `mergedContains` (`day05.sw:192`) three
   branches were each wrong, and each fix revealed the next error. The branches are
   independent, so all could be reported.
10. **`calc` accepts a `<` chain for a `<=` goal.** `rangeEnd` (`range.sw:17`): a chain `x < … = Succ hi`
    against the goal `x <= hi` passes, because `x < Succ hi` computes to `x <= hi`. syntax.md says the
    relation must be the goal's; the document and the checker disagree. It is harmless, and handy.
