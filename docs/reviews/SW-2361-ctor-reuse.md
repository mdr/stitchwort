# SW-2361: why matcher's `CtorReuse` never reuses in place

Question: on matcher (bench/compare, 2020 day 19) native code calls
`sw_ctor_reuse` 3.46 M times (SW-2359). Why does none of them reuse a cell?

## Answer

The call count is the **slow path only**. Native code does the unique-cell
case of `CtorReuse` inline (`ctor_reuse` in `crates/native/src/n1.rs`: token
is `Data`, field count matches, count is 1) and calls `sw_ctor_reuse` only
when one of those fails. So every counted call is a miss; reuses that
succeed aren't counted at all. "None takes the in-place path" is therefore
true of the 3.46 M calls by construction, and the real question is why they
miss.

They miss for one reason, in every case measured: **the token register is
`Erased`**. `Unpack` leaves its token `Erased` when the cell it unpacks is
shared (it copies the fields and leaves the cell alone, `sw_unpack`). It
is not a field-count mismatch and not a token erased later. The unpacked
cells are shared because the program needs them again.

## Method

Temporary, uncommitted instrumentation (reverted): `sw_ctor_reuse` printed
the body number, instruction index and the token's state on each call
(erased, wrong length, shared, or unique), and the native compiler printed
body names and the bytecode of the hot bodies (`Instr` derives `Debug`).
The matcher input is bench/compare's (`repeat = 16`); the executable was
built with `stitchwort build --native` in `aoc/` and run on
`target/compare/inputs/matcher.txt`. Total 3,458,220 calls, matching SW-2359.

| Case | Count |
| --- | ---: |
| token `Erased` (Unpack found the cell shared) | 3,458,220 (100%) |
| token present, wrong field count | 0 |
| token present, shared | 0 |

### Site 1: the message is shared by design

`leftAfterWith` is a backtracking matcher. For `Alternatives sequences` it
runs `sequences.flatMap (sequence => leftAfterAllWith rule more sequence
message)`: the same `message` list goes to every alternative, so the
closure's captured environment holds a reference while each call runs, and
each call gets a clone. Its cells are shared for the whole search, however
the caller passes them. The results `[rest]` hold the message's tail,
so those cells are shared too (the message's own cell still refers to them).
Sharing here is the algorithm, not a lost last-use: the cell would have to
be unique for reuse to be sound, and at most one alternative could ever be
the last user, and the closure keeps its reference anyway.

The generated bytecode is right: the `Unpack` has a token and the arm's
`Ctor` of the same size claims it (`Unpack { src: 1, ..., token: 10 }` at
17, `CtorReuse { ..., token: 10 }` at 28). The analysis pairs correctly.

### Site 2: `reverseOnto` over a shared list (inferred)

The count (270,811) is within 0.2% of the total number of message
characters in the input (270,336), so it's one `reverse` per parsed
message. `Parse.repeatOptional` ends in `found.reverse`, and `found` is
captured by both continuations of `Parse.onFound` (`value => ...` and
`() => found.reverse`); the one that runs still has the other's closure,
and the running closure's environment, holding `found`, so the first
`reverseOnto` sees a shared head cell and, since the head cell stays alive
and keeps the rest, every later cell too. This site is inferred from the
counts and the code, not measured (no caller was recorded).

## What would make them reuse

- **Site 1:** nothing in the reuse analysis. No pass could make these
  unique, because sharing is the program's. The only way to save the
  allocations is a different algorithm: return the number of characters
  consumed (or the remaining tail as an index) instead of building `[rest]`
  cells, which changes the result type of `leftAfterWith` and its proofs.
  That is a program change, not a runtime one, and a matter for the AoC
  day, not the reuse design.
- **Site 2:** `Parse.repeatOptional` could reverse in a place where `found`
  isn't also captured (build the result in a helper that takes `found`
  by move). Possible, but the call is 0.7% of matcher's cell builds
  (270 k of 38.6 M).
- **Reuse analysis design:** no flaw found. Pairing `Unpack` with a same-size
  `Ctor`, the token's life and the inline unique path all behave as designed.
  A different-size pairing (`tokens` is claimed only on equal field
  counts, `code.rs` `Expr::Ctor`) wasn't the cause in any measured case.

## Gain

Reuse saves an allocation and a free only for a unique cell. At site 1 no
change makes the cell unique. Site 2's best case is 270 k allocations out
of 38.6 M, 0.7% (an estimate; each costs on the order of 20-50 ns, so about
5-15 ms of 5.3 s). Neither is worth a lane.

A smaller, separate option: when the token is `Erased`, the slow path
spills the fields and goes through `sw_ctor_reuse`, which collects them into
an `Rc<[Value]>`, rather than `sw_cell_new`'s direct fill. Sending a
known-`Erased` token to the plain constructor path might save a little per
call on 3.46 M calls, but SW-2359 removed the calls entirely
(by emitting `Ctor` rather than `CtorReuse`) and measured 5.29 s to 5.26 s,
noise. So the helper's overhead isn't a bottleneck either.
