Stitchwort's elaborator state: a design for review

Brief for an outside reviewer. 3 November 2026. Stitchwort is a private repository, so this page tries to be self-contained: it quotes the code it relies on.

We have restructured the state of a dependently typed elaborator by lifetime, and we are about to replace the copies it takes at rewind points with undo logs. Before we do, we would like an experienced implementer to look at the design. Section 8 has the questions. The rest gives you enough to answer them.

Labels used throughout: measured a number from a run, with the file it is recorded in; estimate reasoning or a benchmark standing in for the real thing; planned not built yet. Paths are relative to the repository root.

1Stitchwort, briefly

Stitchwort is a small, total, dependently typed functional language, used both for programs and for proofs about them. Functions terminate by default; anything that might not says so in its type (Partial). Effects are algebraic abilities with handlers, translated into ordinary data in the prelude, so the core has no effect judgement.

  • Kernel. A small core calculus (de Bruijn terms, inductive families, a built-in equality with J, quotients, numbered universes without polymorphism). The kernel, in crates/core, re-checks every term the elaborator produces from scratch. The elaborator is not trusted.
  • Elaborator. crates/elab, about 101,000 lines of Rust (counted). Metavariables and unification, implicit and auto arguments, instance search, pattern-match compilation into case trees, termination checking, derived instances, records, interfaces. It is single-threaded. Terms are Rc, and mutation goes through RefCells on a shared &Elaborator.
  • Standard library. 91 source files, about 28,000 lines (counted), loaded per file and on demand.
  • Runtimes. The kernel's own reference evaluator; a bytecode runtime with Perceus-style reference counting and in-place reuse; native code through Cranelift; and JavaScript.

Who drives the elaborator

  • The command-line check of a project. A project is a folder of namespaces. Each library file and each namespace is a unit: elaborated as one piece, and stored as one entry in an on-disk check cache. An entry holds what the unit added, written by path and content hash rather than by load-order id, so it can be replayed into a session whose ids differ. Replay re-admits the declarations through a trusted path and extends the elaborator's side tables.
  • The language server keeps one session. It loads the whole library, takes a mark (a value it can later rewind to) before each namespace it checks, and keeps all of them. After an edit it rewinds to the mark before the first changed namespace and checks from there. A check cancelled from another thread also rewinds. Marks are only taken between units, never inside one.
  • search --at, a proof-action search, builds two sessions: one searches, the other checks candidates so the first isn't disturbed. Each loads the library separately.
  • Tests, including differential tests that compare a session against a fresh one: replayed from cache against fresh (check_cache.rs), rewound and re-checked against fresh (rewind.rs), and hash stability. What they compare is a canonical dump of everything a later unit can read, plus content hashes, the navigation index and diagnostics.

2The problem

Before this work the Elaborator was one struct of 116 fields, 47 of them RefCell, plus 22 fields in a shared Globals (the kernel environment and the metavariable store together), plus about a dozen thread-locals and process globals (design note §1). The fields had very different lifetimes: per speculative attempt, per declaration, per unit, per session, and "grows with every unit and is read by later ones". Nothing in the code said which was which.

Six mechanisms walk that state, and each kept its own hand-written list of fields:

  1. Undoing a failed attempt (undo::Snapshot): 18 named things plus 9 maps filtered in restore. It runs on every application with an expected type, every dot call, every instance search step; 126 call sites.
  2. Per-declaration cleanup (clear_metas), called from about 65 sites, plus other clears elsewhere. Four tables were undone by Snapshot but not cleared by it.
  3. A library file loaded in the middle of a unit: save the unit's fields, elaborate the library file, put them back. Written out twice.
  4. Rewind for the language server. The only list the compiler checked: rewind destructured every field.
  5. The check cache: a Before snapshot per unit, then about 1,350 hand-written lines of encode, decode and replay, one block per table.
  6. The canonical dump, the differential tests' oracle. Also a hand-written list.

So a new table could be wrong in five ways the compiler couldn't see. These bugs were real:

  • Three tables missing from the cache and the dump. Why Finite and a decision procedure weren't derived for a type, and the D.All generated for a nested container. They were rewound correctly but neither encoded nor dumped. After a replay, a later namespace lost the "why not" notes, and generated a private copy of All instead of reusing the existing one: different hashes, different terms. The differential test couldn't see it, because the dump had the same gap. Reproduced and fixed.
  • The same shape, found by the design note: the set of definitions re-checked with total row variables was rewound but not cached or dumped. After a replay, an error note and a hover line went missing. Reproduced and fixed. A fourth table had the same gap but no visible effect.
  • State outside the object. Seven thread-locals in unification and 26 global counters in the postponement queue, so two sessions on one thread (the language server beside a search) shared them.
  • Memory from marks. A mark copies every table whose old rows a later unit can change. The language server keeps a mark per namespace, so the copies grow with namespaces times table size: quadratic in the project. Once, 8 of 13 GB of an editor session was copies of the navigation recorder measured. That one table was moved to an undo log; about 15 others are still copied, the name scope among them (§5).
  • The cache's Before copies the scope's entries, a map of 15,000–30,000 name-keyed rows on aoc estimate, once per unit, 289 times per check.

The cause was the same each time: fields with no declared lifetime, and mechanisms that are lists kept by hand.

3The design

3.1 Components by lifetime

The Elaborator becomes a handful of structs, one per lifetime. A field's lifetime decides which struct it goes in. Each mechanism is a method that destructures its component without .., so a new field doesn't compile until every mechanism says what it does with it.

ComponentLifetimeHow each mechanism treats it
Optionsthe session; fixed when it is builtnever rewound; destructured to make the settings part of the cache key
Kernel plannedgrows with each unitdefinitions and data types in load-order Vecs: marked by length. Today still inside Globals
Tablesgrows with each unit; read by later unitseach table has a kind that supplies mark, rewind, encode, replay and dump (3.2)
Session (with Stats)project and run bookkeeping; the counters that were globalssmall maps copied at a mark today (undo-logged in step 6); counters left alone
Cachesany; derivableemptied or cut by id at a rewind, never encoded. A test switch empties them before every declaration and checks nothing changes
Presentation plannedthe session: navigation recorder, goals shown, logsnavigation is already an undo log; the rest still on the Elaborator
Unitthe unit being elaboratedswapped out whole (mem::replace) while a nested library file loads
Declone declaration or groupreset by Decl::default(); asserted empty at a mark
Attemptone declaration, with speculative sub-scopesa Copy mark of 13 lengths plus a trail; restore by exhaustive destructuring
Globalsmixed: kernel environment, metavariable store, operation statestill one struct in the core crate; split later in its own design (§5)

3.2 Table kinds

The long-lived tables are not bare HashMaps. Each is one of four kinds, a small generic type that states its policy once, where the table is declared:

KindInvariantMark / rewindCache entry holdsStatus
GrowVec<T>push only, in load orderlength / truncaterows past the markbuilt 5 tables
OwnedBy<Id, V>a row for declaration i is written only while the unit that declared i is elaborated; insert asserts itdrop rows with ids past the markrows for the unit's own ids, by path and hashbuilt 11 tables
Logged<K, V>none: any row may changeundo log: O(1) mark, O(changes) rewindthe rows changed since the mark: the log is the deltastep 6 scope maps, instances, helper keys
Derivedcorrect if emptied at any timeemptied or cut by idnothingbecame the Caches component rather than a type

A table that fits no kind implements the Table trait by hand, and the compiler insists that it does. OwnedBy's assertion turns a run-time check the cache used to make by hand ("a row for an older data type changed") into an invariant upheld at every write, so the bug is caught at its source in every test, not only in a cached run.

3.3 The codec and the dump stay independent

The dump is the differential tests' oracle, so it must not be generated from the encoder. The kind supplies which rows: the encoder writes the delta since a mark, the dump prints the whole live table. Each row type implements Codec (bytes) and Dump (text) separately, written by hand in different files. A delta selected wrongly, or a row that decodes wrongly, still shows up as a difference between replayed and fresh sessions, because the fresh session is the reference. What generation could mask is a table missing from the mechanism altogether, and that is what exhaustive destructuring prevents.

3.4 No persistent data structures as the general representation

Our workflows mark and rewind in stack order: a rewind is never to a mark older than one already rewound past. They don't need many live versions branching from each other, which is what persistence buys. Undo logs serve stack order at a fraction of the time and memory, and leave every lookup as it is. The numbers are in §7.

3.5 A frozen library base, later and only behind a measurement

Some workflows do need two live states sharing a past: the search's second session, tests that load the standard library repeatedly (about 9 CPU-seconds per load, 136 tests, about 1,220 CPU-seconds per daily test run measured), and parallel namespaces some day. They all fork at one place, after the library has loaded. The proposal: freeze Kernel and Tables into an Rc there and give each session an overlay. Ids below the base's length go to the base (one comparison); maps probe the overlay first. Unlike Lean's staged map, an overlay row may shadow a base row. It touches every hot lookup, so it waits until a measurement shows the fork's value planned.

4What the code looks like

Excerpts from crates/elab/src/state/ as merged, trimmed only where marked.

table.rs: the trait every kind implements

/// A row's bytes in a check cache entry: declarations by path and hash
/// (through [`Encoding`]'s references), never by load-order id.
pub(crate) trait Codec: Sized {
    fn encode(&self, e: &mut Encoding<'_>);
    fn decode(b: &mut Body<'_>) -> Read<Self>;
}

/// A row's text in the canonical dump, written independently of [`Codec`].
pub(crate) trait Dump {
    fn dump(&self, out: &mut String);
}

/// How a table of one kind serves each mechanism.
pub(crate) trait Table {
    type Mark;
    /// What a check cache entry holds of the table, read back.
    type Rows;
    /// Where the table is, with `ids` declarations made so far.
    fn mark(&self, ids: Ids) -> Self::Mark;
    /// Back to `m` (stack order: no older mark has been rewound to since).
    fn rewind(&mut self, m: &Self::Mark);
    /// What the unit being encoded added since `m`; an error if it changed
    /// what was there before in a way an entry can't hold.
    fn encode_since(&self, m: &Self::Mark, e: &mut Encoding<'_>) -> Result<(), String>;
    fn decode(b: &mut Body<'_>) -> Read<Self::Rows>;
    /// Adds an entry's rows, read back.
    fn replay(&mut self, rows: Self::Rows);
    /// The whole table, one line per row, each starting with `name`.
    fn dump(&self, name: &str, out: &mut String);
}

Decoding is split from replaying because a replay must change nothing until the whole entry has been read and the kernel has admitted its declarations.

table.rs: OwnedBy, its ownership floor, and its encoder's check

pub(crate) struct OwnedBy<I, V> {
    rows: HashMap<I, V>,
    /// The first id of the unit being elaborated: rows below it are
    /// another unit's.
    floor: usize,
}

impl<I: Id, V> OwnedBy<I, V> {
    pub(crate) fn insert(&mut self, id: I, row: V) -> Option<V> {
        self.owned(id);
        self.rows.insert(id, row)
    }

    fn owned(&self, id: I) {
        assert!(
            id.index() >= self.floor,
            "a row for declaration {} written by a later unit (its first is {})",
            id.index(),
            self.floor,
        );
    }
    // ... remove, sorted
}

impl<I: Id, V: Codec + Dump> Table for OwnedBy<I, V> {
    // ... mark, rewind (rows.retain(|id, _| id.index() < m.cut))
    fn encode_since(&self, m: &OwnedMark, e: &mut Encoding<'_>) -> Result<(), String> {
        let (old, new): (Vec<_>, Vec<_>) = self
            .sorted()
            .into_iter()
            .partition(|(id, _)| id.index() < m.cut);
        if old.len() != m.rows {
            return Err("a row for an older declaration changed".to_string());
        }
        e.count(new.len());
        for (id, row) in new {
            id.encode(e);
            row.encode(e);
        }
        Ok(())
    }
    // ... decode, replay, dump
}

        instances: _,
        helper_keys: _,
        namespace_defs: _,
        prelude_defs: _,
    } = self;
    records.set_floor(start);
    interfaces.set_floor(start);
    // ... the same for the other eight OwnedBy tables
    total_rows.set_floor(start);

mark, rewind, encode_since, replay and dump have the same shape: destructure, then one line per field, which for a table of a kind is a call to the kind. decode builds the Delta struct whole, so it is exhaustive too.

rewind.rs: the top level. Every component is named; only the scope and navigation are still handled outside a component.

pub fn rewind(&mut self, mark: &Mark) {
    let Elaborator {
        globals, tables, scope, attempt, decl, unit,
        // Settings: they say how to check, not what was checked.
        options: _,
        session, caches, goals, goal_snapshots, nav,
    } = self;
    let defs = mark.globals.defs();
    globals.rewind(&mark.globals);
    tables.rewind(&mark.tables);
    *scope = mark.scope.clone();            // the big copy step 6 removes
    attempt.rewind();
    *decl = crate::state::Decl::default();
    unit.rewind(&mark.unit);
    session.rewind(&mark.session);
    caches.rewind(&mark.caches, defs);
    // ... goals emptied, navigation rewound through its undo log
}

(The original is formatted one field per line; the comment on the scope line is ours.) The Elaborator itself now has 13 fields, down from 116.

nav.rs: the undo-logged map that step 6 generalises

pub(crate) struct Logged<K, V> {
    map: HashMap<K, V>,
    /// Each change since the first mark, oldest first: its key, and the
    /// value it replaced (`None`: there was none).
    undo: Vec<(K, Option<V>)>,
    /// The keys changed since the last mark (or rewind): only a key's first
    /// change since then is logged, as rewinding to that mark or an earlier
    /// one puts back the value from before it.
    touched: HashSet<K>,
    /// Whether a mark has been taken: changes before the first need no
    /// undoing (a session without marks, such as `check --index`, logs
    /// nothing).
    logging: bool,
}

6How others do it

From the design note's survey of sources (links below), plus the undo-log precedent outside proof assistants. To be candid: none of the proof assistants we looked at keeps an undo log for its environment. They use persistence, copying, or a registry of freezable tables. Undo logs are standard for speculative inference state, which is where our Attempt already uses one.

SystemWhat it doesWhat we take
Lean 4Persistent everywhere. Meta.SavedState.restore restores "the backtrackable parts of the state", and the source documents which caches survive. Constants live in a staged map, SMap: imported entries in a hash table, local ones in a persistent map, never overwritten. Elaborator tables are environment extensions, each registering how it is imported and exported. The undo-log precedent

  • Prolog's WAM. Variable bindings older than the newest choice point are recorded on a trail; backtracking unwinds the trail to the choice point's saved height. Only bindings that need undoing are trailed, which is the analogue of Logged recording only a key's first change since a mark. (Standard textbook material; not re-checked against a source for this page.)
  • SAT and SMT solvers. CDCL solvers keep a trail of assigned literals by decision level and backtrack by popping it. SMT solvers expose push/pop over logged undo actions. Strict stack order in both. (Also from general knowledge, not re-checked.)
  • rustc's inference tables, which we did check. The ena crate's SnapshotVec (src/snapshot_vec.rs) is "a utility class for implementing 'snapshottable' things": it logs NewElem(index), SetElem(index, old value) and an extensible Other, and only while a snapshot is open. commit keeps the changes, which "can still be undone if there is a snapshot further out", and its tests show out-of-order rollback panicking. UnificationTable (src/unify/mod.rs) is generic over its store, with an in-place store built on SnapshotVec's log and a persistent alternative. In rustc, compiler/rustc_infer/src/infer/snapshot/undo_log.rs defines InferCtxtUndoLogs, "the combined undo log for all the various unification tables": one Vec<UndoLog> and a count of open snapshots, with variants for type, const, int and float variables, region constraints, the projection cache and opaque types. rollback_to pops entries back to the snapshot's length; committing the outermost snapshot clears the log; an assertion's comment says failures "may indicate a failure to follow a stack discipline". So rustc logs in-place tables, and a cache (projections) is in the same log. Checked against the current master branches on 3 November 2026.

So the mechanism is well established for speculative inference state, but we found no proof assistant that uses it for the long-lived environment. Ours would: the scope's maps, instances and session maps, logged across marks that live for a whole editing session.

7Alternatives we rejected

OptionWhy not
Persistent maps and vectors throughout (imbl or rpds)A mark becomes one clone of the whole state, so rewind can't forget a field, but encode and dump still can. Every lookup gets slower (below), including the evaluator's reads of definitions and metavariables on every unfolding. Marks are not free in memory either, because each namespace's writes copy paths of 64-wide nodes and each mark keeps its paths alive
A run-time registry of tables (Rocq's summaries, Lean's extensions)The same policy as our kinds, decided at run time. It suits systems where plugins add tables the core doesn't know. We have no plugins, so the compile-time version is better: no indirection, and a forgotten table is a compile error rather than a test failure
Query-based incremental computation (salsa)Elaboration has side effects on a shared environment: metavariables, lifted helpers, generated declarations. In a dependently typed language a theorem about f can depend on f's body, so rust-analyzer's "a body edit never invalidates global data" doesn't hold. The language-server design reached the same conclusion
A macro or derive to generate the components and their implsIt would save about 100 lines, but hide the exhaustive destructuring that is the point, and a proc macro would add a crate to the build
Keep the lists and add more testsThat is what we had. The tests compare against a dump that is itself a hand-kept list, so they share its gaps: the first bug in §2 passed them

8Questions for you

  1. Is an environment-level undo log sound here? Marks are only between units, in stack order, and a mark can be rewound to many times. But a library file can load in the middle of a namespace, writing scope and instance rows; a check can be cancelled part way through a unit and rewound; and step 6 wants the cache's per-unit Before to become a log mark, which means logging is on in every cached command-line check, not only in the language server. (The design note says elsewhere that outside a language server nothing is logged; those two statements need reconciling.) Do you see an interleaving where "log a key's first change since the last mark" restores the wrong value, or where the log grows without bound? Would rustc's rule, clearing the log when the outermost snapshot is committed, carry over?
  2. Is the OwnedBy floor the right ownership rule? A row for a declaration is written only by the unit that declared it. Today a namespace's floor is set when the namespace starts, before the library files it uses load inside it, so the namespace could write rows for those library files' declarations without the assertion firing; the encoder's count check would then refuse the entry. Should the floor move to after the nested loads? And is there a class of table (instances, whose valid flag a later unit can change) where ownership by declaring unit is the wrong model altogether?
  3. Should the frozen library base come before step 6? Much of what a mark copies today is the library's, loaded before the first mark (inferred: the project has 8,780 symbols of an estimated 15,000–30,000 scope rows). A frozen base would take them out of every mark and make the undo log cover only project rows. It also touches every hot lookup. Which order would you choose, and why?
  4. Is the differential oracle independent enough? The table's kind now chooses both the rows the encoder writes and the rows the dump prints (delta against whole table); only per-row encode and dump are written separately. Is there a failure this lets through that a fully hand-written dump would catch?
  5. What would you measure before and after step 6? We plan the language server's resident memory on aoc after a full check, and counters for attempts per check and rows per table. Is there a better proxy for mark cost, or a workload we are missing (long editing sessions, many rewinds to the same mark)?
  6. Is Lean-style persistence worth a second look? We rejected it on lookup cost in Rust. Stitchwort's own runtimes already do Perceus-style in-place reuse, and widening that is on our research horizon, but the elaborator is written in Rust, so that work doesn't change the elaborator's costs unless it were ever self-hosted. Is there a persistent structure with cheap unique-owner mutation, or a hybrid, that we haven't priced?
  7. Does the design stretch to marks inside a unit? The language server's later stage would rewind to a declaration, not a namespace, which needs O(1) marks. With undo logs that looks feasible; with today's copies it isn't. Do the components (Unit and Decl assumed empty at a mark) get in the way?
  8. What risks have we missed? For example: Rc terms and RefCells that rule out parallel namespaces; a cache of failed dot calls keyed by the lengths of the metavariable store and trail, which only identifies a state while lengths do; anything from your own implementation that bit you late.
