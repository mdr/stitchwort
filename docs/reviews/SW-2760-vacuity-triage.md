# SW-2760: triage of the audit's vacuity warnings

The audit with the counterexample search (1,500 inputs, 2 s each; no
`--no-search`), run on this branch (from `main` at 9c247a853; Overmind's run
was at 96d29b46b) with the release CLI: `stitchwort audit Std --json` from the
repo root, and `stitchwort audit --json` in `games/rogue/` and in `aoc/`. All
three reported 0 failures. Warnings: **std 10, rogue 10, aoc 126** (Overmind's
run had 127 for aoc; the inputs tried vary from 766 to 1,500 where a statement
is slow, so one theorem is on the edge of the time backstop). Each warned
theorem's statement was read.

Classes: **(a)** narrow but fine; **(b)** truly vacuous; **(c)** generated by
the compiler; **(d)** unsure.

**No theorem is vacuous.** Every handwritten warned theorem has hypotheses
that can hold together: witnesses for std are below; for the rest the shape of
a satisfying input is in the patterns and the appendix. The warnings are
blind spots of the search, not defects in the statements. The 62 generated

None.

## (c): generated declarations

Rogue: `Level.ext`, `Plan.ext`, `State.ext` (record extensionality) and
`enter.eq.some`, `playerMoves.eq.some`, `resolve.eq.playing.descend.ifTrue`.
Aoc: 56 equation lemmas (`f.eq.…`, `f.eq2.…`), listed by definition in the
appendix.

Their hypotheses are what the compiler wrote, so they can't be contradictory by
accident, and the kernel has already checked each:

- **`T.ext`** is `(a b: T) (h₁: a.f₁ = b.f₁) … : a = b`. It is satisfied by
  `b := a`, but the search draws `a` and `b` independently, so it holds only
  by chance: 32 of 1,500 for `Position.ext` (two `Nat`s), 0 for the larger
  records. The warning says nothing about the lemma.
- **`f.eq.<branch>`** carries the branch's conditions as hypotheses
  (`value.stripSuffix "cm" = Some number`). When the search can't steer into
  an arm, the lemma is warned. The only meaningful reading would be "this arm
  of `f` is dead", which is a real lint, but a random miss doesn't show it.

**Recommendation: don't emit the vacuity warning for generated declarations.**
Keep the counterexample search on them (a counterexample to one would be a
compiler bug, and it costs nothing extra). It is one condition: the
`Verdict::NeverHeld if !search.refutes` arm in `audit_one`
(`crates/driver/src/audit.rs`) gets `&& !audit.generated`, and
`TheoremAudit.generated` is already computed there by `is_generated`. Also drop
the `#[serde(skip)]` on that field, so the JSON says which theorems are
generated and a consumer needn't match the names (`.eq`, `.eq2`, `.ext`,
`.induct`, `.update.`). A dead-arm lint, if wanted, is a separate feature:
search the parent `f` and record which arms ran (branch coverage), not each
lemma on its own.

That removes 62 of the 146 warnings (42 %). The summary line's "generated"
count (1,768 in aoc) would then also cover the warnings.

## (a): patterns, and generator improvements

Of the 84 handwritten warnings (10 std, 4 rogue, 70 aoc; 83 are (a), 1 is
(d)), these shapes account for nearly all of them (a theorem can have several;
the counts are of aoc theorems, std and rogue in the last column):

| Pattern | What blocks the search | aoc | std, rogue |
|---|---|---:|---|
| P1 output-determined | a hypothesis `f x = Some y`, `= Ok y`, `y ∈ f x` or `y = e` where `y` is a parameter: `y` has to be what `f x` gives, and is drawn independently | 57 | rogue 5 |
| P2 aliasing | two parameters that must be the same value or share a part (`first ∈ gates` and `second ∈ gates`, one key looked up in two maps, `a = b` for two parses) | 4 | rogue 2 |
| P3 valid structure | the input must be a coherent whole: adjacent cells of one grid, a number nested four deep, a climbing path, a cavern that has settled | 34 | rogue 3 |
| P4 exact arithmetic | equations over big or related numbers (`Succ m = e × 2^52 + 2^52`; Bézout `s·er + t·ec = 1`; `first + second = best`) | 6 | std 6 |
| P5 conclusion with `∀ … →` | the checker takes the conclusion's binders and implications as inputs and hypotheses, and those are rarely true | 8 | none |
| P6 specific constants | a character or list that random inputs don't make (`'\n'`, `['\n']`, `Cave.start`) | 1 | std 5 |

### Proposed generator improvements

All in `crates/elab/src/counterexample/` (`inputs.rs` makes the values,
`mod.rs` builds and runs the checker). Today every parameter is drawn
independently of the hypotheses.

1. **Solve for the determined variable (P1; the largest group).** For a
   hypothesis of the form `lhs = Some y` / `Ok y` / `y = e` / `y ∈ e` with
   `y` a parameter that no earlier hypothesis needs: draw the other
   parameters first, evaluate `lhs`, and bind `y` to what it gives (for `∈`,
   an element of the list when it has one). Covers the 57 aoc and 5 rogue
   P1 theorems, though many also need P3 (a parse that succeeds needs valid
   text) and so would improve only to "sometimes".
2. **Reuse values (P2, and the `ext` lemmas).** Draw a later parameter of the
   same type as an earlier one equal to it (or to a part of it) a quarter of
   the time, or equal to it with one field changed. Covers `gateUnique`,
   `pairsIntro`, `scoringTile`, `writtenUnique`, and the `ext` lemmas had
   they not been skipped.
3. **Constants from the statement (P6, and P4 for std).** Collect the
   literals the statement and the definitions it unfolds mention
   (`4503599627370496`, `9007199254740992`, `'\n'`, `"cm"`) and add them, and
   their neighbours (±1, doubles), to the pool of numbers, characters and short
   texts. `random_nat` (`inputs.rs`, ~line 1199) has edges at 2^32, 2^63 and
   2^64 and none in [2^52, 2^53). **`ALPHABET` (~line 55: `a b 0 space`) and
   `random_char` (~line 1254) never make `'\n'` or `'\r'`** except in the
   one-in-ten draw of a random scalar value, so `Parse.lineBreakChar` (the
   char is a line feed or a carriage return) can't be satisfied, and the three
   `Parse.line*` statements can't either. Adding `'\n'`, `'\r'` and `'\t'` to
   the alphabet is a one-line change worth making on its own.
4. **Say which hypothesis blocked.** The checker returns the index of the
   first false hypothesis (`mod.rs`, `run_batch`: `code < falsified - 1`),
   and the log keeps only the total. A histogram per hypothesis ("`rel` false
   in 1,498 of 1,500") would have made this triage a lookup, and lets the
   warning name the hypothesis to steer instead of "no input made the
   hypotheses true". The audit JSON should carry it.
5. **Coherent inputs (P3), later.** The grids, paths and nested numbers some
   hypotheses need are what a hand-written generator is for: an attribute
   naming a generator for a type, or inputs made through a smart constructor
   that keeps an invariant. A design question, larger than the rest; only
   worth it if items 1 to 4 leave many.

Two warnings on closed or near-closed statements need item 4 to read:
`Day21.directionalWalksYours` takes no parameters and `Day11.stableAtSize` only
`cavern`. Their `∀ … →` conclusions are taken as inputs and hypotheses (P5):
right for finding counterexamples, but the vacuity verdict then counts
"hypotheses" the author never wrote. `directionalWalksYours` is (d): its
statement has an implicit key type `k` that the search fills with `Nat`
(D1157) while the rows hold `Heading`s, so it may be unsatisfiable in the
search's terms, which I couldn't confirm without running it.

## Proposed tickets

1. Skip the vacuity warning for generated declarations, and put `generated` in
   the audit JSON (the (c) policy; small).
2. Add `'\n'`, `'\r'`, `'\t'` to `ALPHABET` and edges near 2^52 and 2^53 to
   `random_nat` (small; clears the four `Parse.*` and, with the next one, the
   six `Float.Theory`).
3. Constants from the statement as a generator pool (item 3).
4. Per-hypothesis discard histogram in the search log, the audit JSON and the
   warning text (item 4).
5. Hypothesis-directed generation: solve for the determined variable (item 1).
6. Value reuse between parameters of one type (item 2).
7. Statements with no hypotheses of their own (`stableAtSize`,
   `directionalWalksYours`): no vacuity verdict, or lift a conclusion's `∀`
   binders as inputs without counting its implications as hypotheses.
