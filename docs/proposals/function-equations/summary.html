Equations for each arm, and functional induction

A summary of docs/proposals/function-equations.md: generated, kernel-checked theorems that say "this arm (or this branch of an if/match in it) gives this result when these conditions hold", and an induction principle that follows a function's own recursion.

The problem

A proof about a Stitchwort function has rfl (when the arguments are known enough to compute) and f.unfold (the whole body, for decreasing and opaque definitions). Nothing states one arm on its own. Agents reshaped four programs to get such statements (2021 day 18; 2024 days 12, 16 and 23) and wrote hand step lemmas for three of them. This design makes all four reshapes unnecessary.

When a definition has a named match on a Bool (or on popMin), every way of stepping through it fails. Reproduced on a cut-down day 23:

def firstBig: List Nat → Option Big
  | Nil => None
  | Cons x rest =>
    match big: Nat.leq 10 x with
      | True => Some ({ value = x, isBig = big })
      | False => firstBig rest

-- rewrite h in rfl          → E-REWRITE-MOTIVE
-- match e: Nat.leq 10 x …   → E-MATCH-MOTIVE
-- cases                     → E-CASES (E-MATCH-MOTIVE on a decreasing version)

The step needs the scrutinee and its equation replaced together, one J whose motive names the hidden helper firstBig.%match1. Source can't write that name; a generator can. The one-J proof checks.

Before and after: 2024 day 12's flood fill

Before

Three hand-written step lemmas (21 lines), each rewrite Garden.fill.unfold … and a nested Decidable.elimEq:

theorem fillSkip … (taken: visited.contains position = True):
    Garden.fill garden plant (Cons position rest) visited members
      = Garden.fill garden plant rest visited members :=
  rewrite Garden.fill.unfold garden plant (Cons position rest) visited members in
    Decidable.elimEq _ _ _ _ (fresh => Void.exfalso …) (other => rfl)

fillCorrect (67 lines) recurses on the same measure, proves the three decreases again, and converts == back to a Prop.

After

Generated, nothing to write:

Garden.fill.eq2.ifFalse
  (notFresh: visited.contains position = True):
  Garden.fill garden plant (Cons position rest) visited members
    = Garden.fill garden plant rest visited members

fillCorrect by Garden.fill.induct: 51 lines with the plain form (prototype checks), about 45 with the unfolding form and match induct. No decrease proofs, no splitting on Bools to convert back to Props.

match induct (Garden.fill garden plant stack visited members) with
  | eq1 visited members => …
  | eq2IfTrueIfTrue position rest visited members fresh grows ih => …
  | eq2IfTrueIfFalse … ih => …

What is generated

A case is an arm plus which way each if / match in tail position went. Every arm gets an equation; every path through a split gets one more. Proofs are kernel terms checked by the kernel, so nothing new is trusted.

Not generated: theorems, instances, Partial and ability-performing definitions (effect-polymorphic ones get equations at the empty row), opaque with an unfolding clause, a decreasing definition's local helpers, an arm on an indexed family whose overlap would compare different indices, and a branch of if h: p whose result still uses h unless p is an equation in a type with DecEq (comparisons on Nat and Int included). Naming a skipped one gives E-NO-EQUATION with the reason.

Names, and how agents find them

  • f.eqK for arm K (a whole-body match on parameters counts as arms); a suffix per split: .ifTrue, .ifFalse, the constructor in lower case (.some, .cons), .altN or .orN; f.eq.… for any other := body. Worked out from source alone, so the library index knows them; reserved.
  • Hypotheses keep the source's names (fresh, notFresh for the else), or isSome/isNone, notArmJ, notListed.
  • stitchwort doc f gets an Equations section; search flags them generated and ranks a written theorem first on a tie.
  • E-MATCH-MOTIVE, E-REWRITE-MOTIVE and E-REFL on a definition's hidden match name the equation instead of "define a helper".

f.induct

f.induct (fixed parameters)
  (motive: (other parameters) → (result) → Prop)
  (one case per equation: eq1, eq2IfTrue, …:
     (variables) → (hypotheses) → (IH per recursive call: motive args (f args)) →
     motive patterns rightSide)
  : (other parameters) → motive params (f params)

Proved by f's own recursion: structural, or the same decreasing measure with the decrease proofs f's calls already carry. Applied explicitly, or as match induct (f args) with | eqK … => … with the motive worked out from the goal.

Review

An independent Opus reviewer read draft 1 against the repository: approve with changes. It re-ran every prototype (all behave as stated) and found ten things to fix, all addressed in draft 2: overlap hypotheses are ill-typed on indexed families (now skipped, D2185); Bool guards should take the hand-written form (D2186); the if h: limit is narrower than claimed, and std's many such branches are provable with Bool.uniqueEq (D2180 rewritten); or-patterns, decreasing helpers, implicit parameters, _ names and opaque definitions with number patterns past 64 were missing; a whole-body match should be named like arms (D2187); the cost needed a realistic data point (now about 1 ms each); the prototypes are now committed.

Open questions

  1. D2173. Build stage 1, generated equations for arms and branches? [Yes]Assumes the evidence (four reshaped programs, three sets of hand step lemmas) is typical, and that generated terms cost what the measurements suggest or less.
  2. D2174. One equation per source arm with earlier overlapping arms as hypotheses (Lean), plus one per branch of each tail if/match; not per leaf (Isabelle, Rocq Equations)? [Yes]Assumes agents think in arms and branches as written; per leaf is impossible for a character catch-all.
  3. D2175. Hypothesis forms: one per earlier overlapping arm, (vars) → x = C vars → … → Void; n ≠ k per number literal; character literals constraining one column merged into c ∉ […]; the tested condition for a split. [Yes]Assumes omega keeps not reading n ∉ [3, 7], that programs' key lists are literal lists or compute to them, and that no index is fixed by an earlier arm (D2185).
  4. D2176. Names: f.eqK plus a suffix per split; f.eq.… for other := bodies; reserved; E-NO-EQUATION for a skipped one. Not Lean's flat numbering. [Yes]Assumes names a few segments long are acceptable in proofs.
  5. D2177. Which definitions: every def (local ones too, except a decreasing definition's) with arms or a tail split, transparent, decreasing or opaque without an unfolding clause; effect-polymorphic at the empty row; not theorems, instances, ability-performing or Partial. Including the ones that hold by rfl. [Yes]Assumes the rfl ones are cheap and the separate doc section keeps them from crowding search; they can't be used by rewrite, but they name every arm.
  6. D2178. Eager with the definition, with a 10% cold-check gate; on demand only if it trips. [Yes]Assumes std's cold check is dominated by its theorems rather than its definitions; stage 1a measures it.
  7. D2179. Discovery: doc Equations section, search flag and tie-break, notes on three errors, proving-guide section. [Yes]
  8. D2180. A branch of if h: p whose result uses h gets an equation when h is gone after unfolding or p is an equation in a DecEq type (comparisons on Nat/Int included), by one J along uniqueEq; others wait for proof irrelevance. [Yes]Such branches are common in std and all found are covered; assumes the rest are rare (stage 1b counts them).
  9. D2181. Stage 2, f.induct in the unfolding form only, fixed prefix, cases named after the equations, no IH under binders, no mutual groups. [Yes, after stage 1]Assumes most theorems that need it are about f's result.
  10. D2182. Stage 2b, match induct (f args) with | eqK … => …, motive from the goal, hypotheses generalised as match does. [Yes]Assumes match's generalisation is what the motive needs; explicit f.induct stays the fallback.
  11. D2183. Equations for lifted match helpers not in tail position? [No]A local def names one and gets its own equations.
  12. D2184. Delete std's Graph.searchEmpty/Skip/Settle and rename their uses to the generated equations (same statements); leave Graph.searchFrom's signature and AoC programs as they are (days 12 and 18 as acceptance tests only)? [Yes]No outside users, so compatibility names would only double what search lists.
  13. D2185. On an indexed family, skip an arm whose overlap hypothesis would compare different indices (counted, reason in doc), rather than a heterogeneous equation, a transport or a generated Bool predicate. [Yes, for now]Assumes such definitions are rare among those proofs need; stage 1a counts them.
  14. D2186. A split on b = True/b = False states its else as the other equation (notFresh: b = True), as the hand-written lemmas did. [Yes]Assumes agents' facts come as b = True/b = False, as match e: and cases give them.
  15. D2187. A whole-body match on parameters counts as arms (Garden.fill.eq1, .eq2.ifFalse), so both spellings of a definition get the same names. [Yes]Assumes rewriting between the two spellings matters more than having the constructor in the name.
