# Deep input: one policy for recursion that grows with the input

**Status:** draft, 7 November 2026 (SW-1956). Waiting for Matt's decisions
D2750 to D2754. Builds on
[stack-safe-evaluation.md](stack-safe-evaluation.md), which made the
evaluator a machine and put a stack guard on every recursive pass that
existed in October. This note is about the gaps found since, and how to
stop new ones from appearing.

## Summary

**What users get.** No input, however deep or long, crashes the command
line, the language server or the playground. Input past a limit gets an
`E-RESOURCE` error that points at the declaration (or the place, for the
parser and formatter), and the rest of the file and the editor keep working.
Today a deep enough expression can kill the language server, so the editor
loses every diagnostic and goal until it restarts.

**The policy, in one line each:**

1. **Length never costs stack.** Anything whose depth grows with how *long*
   the input is (a list, a chain of `+` or `<`, a block of lines, a nested
   array built by a loop) is walked with a loop and a work list. That
   includes every `Drop`, `Clone`, `Debug` and comparison on a recursive
   type, which have no way to report an error.
2. **Nesting costs stack, under a guard.** Anything whose depth grows with
   how deeply the user *nested* things (parentheses, functions inside
   functions) may recurse, but every recursive function checks the stack
   (`budget.nesting(PASS)` or the parser's `deeper()`), inside an operation
   that has a stack floor. Going past it is `E-RESOURCE`.
3. **Every entry point opens an operation.** A guard outside an operation
   does nothing today. Every place that runs a pass on user input (the
   formatter, the runtime's compiler, the editor's outline) runs it inside
   one, sized from the thread it is on.
4. **A big stack is headroom, not the fix.** The CLI's 64 MiB thread stays;
   the `stacker` crate is not adopted.
5. **A test finds the cases, not reviews.** One generated corpus of deep and
   long inputs runs through every consumer, in a child process, and must give
   an answer or `E-RESOURCE`, never a crash. A static check lists every
   self-recursive function that has neither a guard nor a stated bound.

The five findings (SW-1874, SW-1936, SW-1892, SW-1895, SW-1876/SW-1877)
each fall under rule 1 or rule 2, and the fixes the reviews proposed are
the right ones. What the policy adds is the reason they keep appearing, and
a test that would have found all five.

## 1. The problem

### What a user sees

Some examples, from the reviews:

- A test file has a long tuple or list pattern, generated by a script:
  `| [a0, a1, a2, …, a99999] => …`. The parser builds it in a loop, so its
  own depth check never fires, but the tree is 100,000 levels deep. Dropping
  it at the end recurses once per level and overflows (SW-1874,
  `ast.rs:800`, review F4).
- A chain `a < b < c < …` of a few thousand comparisons: the parser's
  `chain` helper recurses once per operand after parsing them in a loop
  (`parser.rs:4980`, `go`); `exists` with many typed parameters likewise
  (`parser.rs:5044`).
- A proof calls `omega` on a goal that has unfolded to `x + (x + (x + …))`,
  stuck on `x`. The reader that turns it into a linear form recurses once per
  `+` with no check (`omega.rs:1959`, `ring.rs:794`; SW-1936).
- A program builds a rose tree of arrays a million deep in a loop. When the
  runtime frees it, `Value::Array`'s automatic drop recurses
  (`rt/src/value.rs:54`; SW-1892).
- The runtime's compiler (`code.rs:258`, `compile`) recurses over every body,
  including the very deep ones the optimiser deliberately skips for being
  too deep (`opt.rs:232`; SW-1895).
- Formatting a file with a 5,000-line block: the formatter's safety check
  clones the whole tree and prints it with `{:#?}` (`equivalence.rs:16-27`),
  both recursive and derived (SW-1876 for the shape, SW-1877 for the
  `DEFAULT_STACK` it parses with, `fmt/src/lib.rs:114`).

In every case the process aborts. Rust can't catch a stack overflow, so
`catch_unwind` doesn't help, and the language server's panic handling
(SW-1948) doesn't either. On the language server's thread the abort is a
bare `SIGSEGV`, not even Rust's "has overflowed its stack" message
(`host/src/stack.rs:118-170`, cli review F11), so it looks like memory
corruption. In the playground, the worker dies with V8's `RangeError`.

Most of these need generated or unusual input. That is the point: the
inputs are rare, but the cost (the editor's server dying, everything
unsaved in its state lost) is out of proportion, and it can come from a
file the user didn't write.

### Why the holes keep appearing

The October work built the right mechanism, and the new findings are all
places it doesn't reach. There are four reasons, and each new recursive
function is a fresh chance to hit one of them.

1. **The guard is opt-in, one function at a time.** Each recursive function
   must call `budget.nesting(PASS)` itself (`core/src/budget.rs:650`), and
   nothing notices one that doesn't. There are 64 call sites today; `omega`
   and `ring` were written later and have none.
2. **Derived code recurses invisibly.** `#[derive(Clone, Debug, PartialEq)]`
   and Rust's automatic drop on a recursive type recurse once per level, and
   they return no `Result`, so a guard can't stop them. `Expr`, `Term`,
   `Values` and the runtime's `Fields` have hand-written drops that loop
   (`ast.rs:498`, `term.rs:235`, `value.rs:428`, `rt/src/value.rs:345`);
   `Pattern` and `Value::Array` were missed. `Expr`'s loop depends on a list
   of boxed variants kept by hand (`ast.rs:513`, `has_nested`; syntax
   review F14), so a new variant quietly brings the recursion back.
3. **A guard outside an operation does nothing.** `nesting` compares the
   stack position with the operation's floor, and the floor is 0 outside an
   operation (`budget.rs:178`, `:652`). So a guard written correctly, in a
   pass called from a place that didn't start an operation, never fires. The
   runtime's `compile` runs outside lowering's operation (`run.rs:204`),
   and the formatter and the editor's outline have no operation at all; they
   parse with a fixed `DEFAULT_STACK` of 1.5 MiB (`parser.rs:45`,
   `fmt/src/lib.rs:114`, `lsp/src/lens.rs:23`) rather than their thread's.
4. **Trees built by loops are deeper than the parser's recursion.** The
   parser's check (`parser.rs:716`, `deeper()`) measures the parser's own
   recursion. Chains, blocks, list and tuple patterns are parsed in a loop,
   so the tree can be any depth while the parser stays shallow. Every pass
   after the parser then meets a depth the parser never checked.

## 2. What Stitchwort already does (the model)

This is the base to build on, and in my judgement it is already the right
model; the question is only how to make it complete.

- **Measured stack, not counted levels.** A pass compares the address of a
  local with a floor set when the operation started
  (`syntax/src/stack.rs:15-38`, `budget.rs:337-347`). The same limit in
  bytes works in debug and release, whose frames differ by about ten times
  (stack-safe-evaluation.md, step 4).
- **Limits come from the thread.** `Limits::for_stack` keeps a quarter of
  the thread's stack (at least 256 KiB) in reserve (`budget.rs:104`). With
  the `stack-check` feature, an operation that claims more stack than its
  thread has is a test failure (`budget.rs:134`).
- **Exhaustion is sticky and fails, never chooses (D2543).** Running out
  sets the budget's error, and every later step fails (`budget.rs:737`,
  `too_deep`). An attempt that runs out of stack passes that to the
  operation it is part of, rather than taking it as "no"
  (`budget.rs:256-273`). This was the fix for SW-962: attempts with their
  own byte budgets failed 790 times in debug and 7 in release, so proofs
  hashed differently by build. The exception is `start_attempt`/`restore`,
  which drop the propagation (core review F4, SW-1886).
- **Data walks are loops.** `conv`, `quote`, `unify`'s comparison, the
  hasher and the checks the kernel runs before typing a term use work lists
  (stack-safe-evaluation.md, steps 3 and 4). Evaluation itself is a machine
  with its own frame stack on the heap, so a program's recursion depth is a
  frame limit (`Depth`), not a Rust-stack one.
- **Display may truncate; results may not.** The printer shows what it can't
  reach as `…` (`pretty.rs:586`), but showing a result uses
  `pretty::term_in_full`, which fails with `E-RESOURCE` instead.
- **Tests in a child process.** `crates/driver/tests/elaboration/nesting.rs`
  runs each case in a child (`isolated`, line 24), so an overflow is a failed
  test. It covers ten hand-written shapes, and terms built a million deep
  for the passes after the elaborator.
- **Big threads.** The CLI and language server run on 64 MiB
  (`cli/src/main.rs:509`), mapped with `MAP_NORESERVE` so untouched pages
  cost nothing (`host/src/stack.rs`); the language server's worker threads
  get the same (`lsp/src/lib.rs:250`).
- **The browser** links an 8 MiB linear-memory stack but guards at 256 KiB
  (`web/build.rs`), because V8's own call stack (about 1 MiB) overflows
  first, as a `RangeError` the compiler can't recover from. The guard
  measures the linear-memory stack, which only some locals live on, so it is
  a proxy for the real limit, calibrated with `web/stress.html`.

Two counted limits choose rather than fail, and both are allowed because
they don't change an answer: the optimiser leaves a body nested more than
1,000 deep unoptimised (`opt.rs:63`, `:232`), and the printer's `…`. The
rule for such exceptions: the output must mean the same thing, only slower
or visibly shortened.

## 3. The options

### A. Depth guards that fail with an error

**What it is:** each recursive function checks the stack and returns
`E-RESOURCE` (what Stitchwort does today).

- **For:** one line per function; works on every target, the browser
  included, since it stops before either stack runs out; the error is
  deterministic for a given build and thread; fits D2543.
- **Against:** needs an error path, so it can't be used in `Drop`, `Clone`,
  `Debug` or comparisons. Opt-in per function, so it is forgotten. The limit
  depends on the build and the thread, so a file can check on the command
  line and fail in the playground (it never gets a *different* answer,
  only an error). And it turns long input into an error that a loop would
  have handled: in the playground, a list literal of a few hundred elements
  is already too long (`web/build.rs`, comment on `WASM_GUARD`, measured
  when it was 128 KiB; I haven't re-measured at 256 KiB).

### B. Rewriting the recursion as loops

**What it is:** an explicit work list on the heap, as `conv`, `quote` and
`Expr`'s drop already do.

- **For:** no limit at all from the stack: memory is the only bound. The
  only option for code with no error path. The same on every build and
  target, which matters most in the browser, where the guard is a proxy.
- **Against:** much more code for a pass that does real work (the
  elaborator's `check` and `infer` would be a large rewrite, and order
  matters for metavariables, stack-safe-evaluation.md §1); easy to get the
  order subtly wrong. Worth it for simple walks, drops and comparisons;
  not, for now, for the elaborator.

### C. Growing the stack on demand (`stacker`)

**What it is:** rustc's `ensure_sufficient_stack` calls
`stacker::maybe_grow` at chosen recursion points: if less than a red zone
(100 KiB) is left, it allocates a new segment (1 MiB and up) and continues
there. rustc pairs it with counted limits users can raise
(`#![recursion_limit]`).

- **For:** almost no code change; depth limited by memory, not stack.
- **Against, for us:**
  - **Natively it buys nothing we don't have.** Our threads are already
    mapped with `MAP_NORESERVE` at any size we choose (up to 64 GiB for
    native runs), and untouched pages cost nothing. A bigger thread gives the
    same headroom with no new dependency.
  - **It doesn't help in the browser.** `stacker` moves the linear-memory
    stack pointer, but every WebAssembly call still uses the engine's own
    call stack, which is what overflows there (stack-safe-evaluation.md,
    "What others do"; `web/build.rs`).
  - **It can't reach derived code.** `maybe_grow` wraps a call; the
    automatic drop of a recursive type recurses inside itself.
  - **It moves the crash, not removes it.** Without a guard, deep enough
    input exhausts memory, and Rust aborts on that too. We would still need
    the guard, measuring total use across segments, which `StackLimit`'s
    single floor doesn't do.
  - It brings `psm`'s assembly into a workspace that forbids `unsafe` in its
    own code.

### D. Running on a thread with a big stack

**What it is:** what the CLI and language server do now (64 MiB).

- **For:** free natively; raises every guarded limit at once.
- **Against:** it's headroom: an unguarded recursion still overflows, just
  later (a 100,000-deep derived `Debug` takes several frames per level).
  Not available in the browser, whose engine stack is fixed. Keep it, but
  don't count on it.

### E. Checking in a separate process (for completeness)

The language server could run its checks in a child process and restart it
after any abort (overflow, out of memory, a crash in native code).
rust-analyzer does this for procedural macros, which run user code it can't
trust. It is the only option that also covers bugs of kinds we haven't
thought of, but it is a large change to the server (sessions, caches,
cancellation all cross a process boundary), and it doesn't help the CLI's
user or the playground. See D2753.

### Comparison

| | Error path needed | Browser | Derived code | Effort per site | Limit users meet |
|---|---|---|---|---|---|
| A. Guard | yes | yes (proxy) | no | one line | build- and thread-dependent `E-RESOURCE` |
| B. Loop | no | yes | yes | a rewrite | memory only |
| C. `stacker` | no | no | no | one line | memory, then an abort |
| D. Big thread | no | no | partly | none | later overflow |
| E. Process | no | n/a | yes | large, once | a restarted server |

### How kernel and `core` evaluation do it, and whether that is the model

`core` already combines A, B and D: the evaluator is a machine (B, for the
deepest thing, a program's recursion), data walks are work lists (B),
recursive passes over terms are guarded (A), and everything runs on a big
thread (D). The kernel recurses at its entry points (`infer`, `check`,
`check_case`) under the guard and walks unchecked terms with work lists
(`Term::subterms`), so a malformed term can't overflow before it is
rejected. Lean 4's kernel is similar in spirit: recursive, with
`check_system` testing stack and memory, and resource exceptions that
elaborator code is not allowed to treat as ordinary failure.

So yes: this is the model, and the policy below just states its rule and
applies it everywhere. The one place `core` itself isn't yet consistent is
`matches_at_once` (`value.rs:682`), which recurses with neither a guard nor a
step (core review F6, SW-1887).

## 4. The policy

**Recommendation: A and B by kind of depth, D as headroom, no C, E deferred.**
The reason: each of A and B is the only thing that works for one kind of
recursion (B where there is no error path or the depth is length, A where
real work recurses over user nesting), both work in the browser, and both
already exist in the code, so the policy is a rule for choosing between
them rather than a new mechanism.

**Rule 1: length never costs stack.** A function walks with a loop when
either holds:

- it has no error path: `Drop`, `Clone`, `Debug`, `PartialEq`, `Hash`, span
  computation, small queries like `has_absurd` and `first_bound`;
- the depth it follows can come from the input's length: chains built by a
  loop in the parser, list and tuple patterns, blocks, data built by a
  running program (arrays, `Ret::Apply` chains in the runtime, SW-1898).

A recursive type either has no derived `Clone`/`Debug`/`PartialEq`, or has a
test that exercises it a million deep (below). Its `Drop` loops, and the loop's
list of children is an exhaustive `match` with no `_` arm, so a new variant
is a compile error until someone decides (fixing F14 for `Expr`).

**Rule 2: nesting costs stack, under a guard.** Every other recursive
function calls `budget.nesting(PASS)` (or `deeper()` in the parser) on entry,
before its first recursive call, and returns `Result`. A function whose
depth is bounded by something else (a type's arity, a fixed table) says so
in a comment starting `// Depth:`, which is what the static check looks for.

**Rule 3: every entry point opens an operation.** Any pass run on user
input runs inside a `Budget::operation` (or, in the syntax crate, a
`StackLimit::from_here`) sized from its thread with `Limits::for_stack`.
`DEFAULT_STACK` stays only for tests. With `stack-check` (on in tests),
`nesting` called with no operation open panics, so a pass that relies on a
guard that can't fire fails its tests instead of shipping. (I haven't
confirmed that no current caller relies on the no-op; the stage that adds
the panic will find out. Medium confidence.)

**Rule 4: a guard inside an attempt propagates.** Code that tries something
and takes failure as "no" (search, `auto`, `omega` inside `rewrite`) must
use `Budget::attempt`, so running out of stack fails the whole operation
instead of choosing the next candidate. SW-1886 fixes the one helper that
doesn't (`start_attempt`); SW-1936 the `omega` call sites that turn its
errors into "not proved".

**Rule 5: big threads are headroom.** Keep 64 MiB for the CLI and server.
Give the server's thread a normal overflow report (F11 of the cli review):
use `std::thread::Builder` for sizes std can map, keeping the hand-mapped
stack for native runs, so an overflow that slips through says what it is.

### The browser

The policy is what makes the browser safe, because there a guard is only a
proxy: it measures the linear-memory stack, while V8's call stack is what
overflows, and the ratio between them depends on the pass (how many locals
have their address taken). Rule 1 removes that uncertainty for every walk
it covers. For guarded passes, `web/stress.html` stays the calibration: the
corpus below runs there too, so a pass whose frames are heavy in V8 but
light in linear memory shows up as a crash in a worker, not in a user's
playground. A pass that crashes there under the guard needs a loop (rule 1)
or a lower guard.

### What it costs and what it rules out

- **Costs:** the five fixes already filed (about 4 hours of Sonnet lanes),
  plus the corpus test and the static check (about 2.5 hours), plus a few
  minutes per new recursive function from now on. A loop is slower than
  recursion in some passes; for drops and comparisons the measurements in
  stack-safe-evaluation.md found no measurable difference.
- **Rules out:** relying on a bigger stack anywhere (including `stacker`);
  deriving `Clone`/`Debug` on recursive types without the deep test;
  counted depth limits that pick a different answer.
- **Leaves as is:** the elaborator still recurses over long chains under
  the guard (rule 2 is enough to stop crashes), so long list literals and
  sums are still limited, most visibly in the playground. Making those
  loops too is D2751.

## 6. Finding them systematically

Five crates, five reviewers, five findings of the same kind: a review found
these, and the next new pass will need another review. The tests below are
meant to find them instead. Three parts, cheapest first.

### 6.1 A deep-input corpus through every consumer

**The problem it solves:** today's `nesting.rs` tests ten shapes someone
thought of, each through the parts of the pipeline its author thought of.
`Pattern`'s drop wasn't among them; neither was the formatter.

**The change:** one table of *shapes* and one list of *consumers*, and a
test that runs every pair.

- **Shapes:** for each place the grammar repeats, a generator taking `n`:
  - repeated by a loop (length): application spines, `+`/`++`/`|>` chains,
    comparison chains, block lines, `let` chains, list and tuple
    literals and patterns, text literals, `exists` and `def` parameter
    lists, record fields, match arms, `calc` steps;
  - repeated by nesting: parentheses, lambdas, function types, nested
    patterns, nested `match`, nested `if`, nested records.

  Each shape is a short function in a table (`("comparison chain", |n| …)`),
  so adding a construct to the grammar means adding a line. The list of
  repeatable constructs can be checked against the parser: a stage can
  grep the parser for its loops (`while`/`loop` that push to a `Vec` of
  `Expr` or `Pattern`) and compare. I'm moderately confident that is a good
  enough proxy; an AST generator driven from the `Expr` and `Pattern`
  types would be more complete but much more work.
- **Consumers:** lex, parse, drop, format (and the formatter's check),
  outline, elaborate, kernel check, hash, `stitchwort test`, extract to JS,
  lower and compile for the runtime, run, print a result, and the language
  server's per-file features (hover, semantic tokens, outline) through its
  library API.
- **The check:** each pair runs at `n` = 100,000 for length shapes and
  10,000 for nesting shapes, in a child process (the `isolated` helper, made
  shared) on a 2 MiB thread with the default limits. It passes if every
  consumer either succeeds or returns `E-RESOURCE`; a crash, a hang past a
  time limit, or any other error code fails it, naming the shape and the
  consumer. A known gap is a line in an expectation table naming its ticket,
  so the test lands green and each fix removes a line.
- **The browser:** the same table, exported, drives a section of
  `web/stress.html`, so the V8 stack is tested by the same shapes.
- **Rule-1 types:** separately, for each recursive type (`Expr`, `Pattern`,
  `Term`, `Value` in both evaluators, `Program`'s `Expr`), a value a million
  deep is built directly, through each boxed variant in turn, and dropped,
  cloned and compared on a 2 MiB thread (SW-1874 asks for this for
  `Pattern`).

**What it should do, and how we'd know:** with the expectation table
emptied of today's gaps, deleting any one of the guards or loop drops named
in §5 should make exactly the matching pairs fail. Each fixing lane does
that once by hand, as stack-safe-evaluation.md did for the parser's guard.

**Cost:** the length shapes at 100,000 are the expensive part (an
elaborator guard fires early, but parsing and dropping a million-node tree
is real work). It needs measuring; my guess is 10 to 30 s for the whole
table in release, inferred from the existing `nesting.rs` sizes. See D2754
for which tier it runs in.

**Relation to fuzzing:** SW-1875 widens the parser fuzzer with deep and long
generators. Random deep input finds crashes slowly, since a crash needs one
construct repeated many times; the corpus does that deliberately. SW-1875
should keep its other parts and take its deep generators from this table.

### 6.2 A static check for unguarded recursion

**The problem it solves:** a new recursive function with no guard (as in
`omega`) is invisible until a test happens to go deep through it.

**The change:** a small script, run by `task lint`, that lists every
function in `crates/*/src` that calls itself by name and contains none of
`nesting(`, `deeper()`, `exceeded()`, `stack_exhausted()` or a `// Depth:`
comment. Known cases go in an allow file with a reason, so the list starts
at what exists and only new entries fail the lint. Mutual recursion
(`infer` calling `check` calling `infer`) is missed by a by-name check, but
those are the big elaborator passes, which are already guarded; most of the
review findings were direct self-recursion. A `syn`-based Rust tool would
be more precise than a script; I'd start with the script and see how
noisy it is (implementation detail, the lane decides).

**How we'd know:** run against today's tree, it should list the `omega` and
`ring` readers, `code.rs`'s `fill`/`builds`/`expr`, `has_absurd`,
`first_bound` and `chain`'s `go`. If it misses any, the approach is too weak
and the corpus carries the load alone.

### 6.3 Guards that can't fire are test failures

Rule 3's `stack-check` panic: a guard reached with no operation open fails
the test that reached it. This turns reason 3 of §1 from a silent gap into
a failing test, and is a few lines in `budget.rs`.

## 7. What users see

**The limits:**

- **Nesting, for each pass** (parser, elaborator, kernel, hasher, printer,
  JavaScript generator, runtime lowering, formatter). In bytes of stack,
  so it depends on the build and the thread: the command line and the
  editor allow 48 MiB (64 MiB less a quarter), the playground 256 KiB of
  linear-memory stack, which isn't directly comparable but in practice is
  far less depth. Users see it as depth, not bytes. In a native
  release build on 2 MiB, it is about 260 nested applications and 300 terms
  of a `+` chain (stack-safe-evaluation.md, step 4); at 64 MiB, scaled,
  roughly 30 times that (inferred, not measured).
- **A program's recursion depth** when it runs: the machine's frame limit
  (2 million by default), already an `E-RESOURCE`.
- Under rule 1, **length** has no stack limit in the walks it covers; only
  memory and the work limit.

**The errors (D2543: they fail, they never choose).** All of them are
`E-RESOURCE`, never a different result:

- The parser's, as today: "ran out of resources: the program is nested too
  deeply to parse", labelled at the place (`parser.rs:716-727`).
- The other passes', as today: "ran out of resources: the program is nested
  too deeply for the type checker", on the declaration, with the note
  "this isn't a type error or a failed test" (`budget.rs:63`, `:76`).
  Proposed addition: a second note when the limit is the playground's
  smaller one, "the playground allows less nesting than `stitchwort check`".
  The pass names should read as nouns in that sentence (`"equations"`
  becomes "the equation compiler").
- **The formatter**: today a depth problem would show as an internal error
  ("the output parses to a different syntax tree") or a crash. Under the
  policy, `stitchwort fmt` reports `E-RESOURCE` for that file and leaves it
  unchanged; in the editor, formatting gives no edits (as for any refused
  file, `lsp/src/lib.rs:1509`) and logs why.
- **Nothing is cached or published** from an operation that ran out: tests
  get `OutOfResources`, declarations fail, as today.

Should users be able to raise the limit, as with Lean's `maxRecDepth` or
rustc's `recursion_limit`? I recommend not (D2752): a limit in bytes means
nothing to a user, the command line already has generous headroom, a
per-file setting would have to enter the check cache's key, and rule 1 removes the
cases (long data) where raising it would be the natural fix.

## 8. Decisions for Matt

- **D2750:** Adopt this policy: loops for anything whose depth comes from
  length or that has no error path, guards for the rest, every entry point
  inside an operation, big threads as headroom only, and no `stacker`?
  **[rec: yes, because it is the model `core` already follows, it works in
  the browser where the alternatives don't, and it covers all five
  findings]**
- **D2751:** As an end state, should the elaborator and kernel also walk
  long chains (list literals, `+` chains, blocks) without recursion, so the
  only limit on length is memory? That is the user-visible win in the
  playground, where a list literal of a few hundred elements is too long
  today. **[rec: yes as the direction, but as its own design note after
  these stages, since it touches metavariable order and is a large
  elaborator change; compact literals (stack-safe-evaluation.md, later
  work) may cover the common case more cheaply]**
- **D2752:** Should users be able to raise the nesting limit (a flag or a
  per-file setting, like Lean's `maxRecDepth`)? **[rec: no, because the
  limit is in bytes, depends on the build, and would have to enter cache
  keys; the error says how the playground differs instead]**
- **D2753:** Should the language server check in a child process, so that
  any abort restarts the checker instead of the server? **[rec: not now;
  revisit if the corpus still finds crashes after these stages, or with
  D2730's recovery work]**
- **D2754:** Which tier runs the deep-input corpus? **[rec: a fixed small
  subset (each shape once, through parse, drop, format and elaborate) in
  the merge tier if it stays under 5 s; the full table in the daily tier;
  the browser section with `task test:browser`]**

Decided here as implementation details: script before a `syn` tool for the
static check; the exact shape list; `compile` becoming fallible rather than
looping (it runs after lowering, which already has an operation to join);
building comparison chains in a loop rather than guarding them.
