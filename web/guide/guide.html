A short tour of what Stitchwort can do, one feature at a time. Each example is real code: press Open in editor to run it, change it and see what the compiler says. This is a guide, not a reference; the full details are in the docs folder of the repository.

Everything starts with def. A definition has a name, optional parameters, a type after the colon, and a body after :=. There are Nat (whole numbers with no upper limit), Bool, Text, Char, Int when you need negatives, and Float for measurements. Division on whole numbers never fails: x / 0 is 0 and x % 0 is x. A --| comment above a declaration documents it; hover shows it, and stitchwort doc prints it.







  
A block is a few lines at the same indent: let names an intermediate value and the last line is the result. if is an expression. match (or a function written as a list of | cases) takes a value apart, and the compiler insists every case is covered. Inside text, ${...} inserts a value.

  






  
A variant type lists the shapes a value can have, like a tagged union; each constructor carries its own fields. A record has named fields: read one with ., change some with { b | field = ... }, take them apart in a pattern with { title, pages }.

  






  
Declare a constructor's fields in braces, | Circle { id: Text, radius: Nat }, and you can use their names. Circle { radius = 3, id } builds one by name, in any order, and a pattern Circle { radius, .. } picks fields by name. When every constructor has a field of the same name and type, as id is here, the field works on the whole type: shape.id reads it and { shape | id = x } changes it, whichever constructor the shape is. A constructor declared with brackets, like Some, takes braces as a record argument instead: Some { name = "tea", price = 3 }.

  






  
Any explicit parameter can be passed by name with (name := value), in any order and mixed with positional arguments; [name := value] does the same for implicit ones. Name only some and the rest become a function, in their original order. It is the same call as the positional one, so nothing about the function changes.

  






  
A field of a record, or of a constructor, can have a default after :=, and a literal may then leave it out. This is how Stitchwort does options: a record with a few defaulted fields in place of optional parameters. The default can use the fields before it. A function's parameters can have defaults too: they are given by name, and a call that leaves one out gets its default.

  






  
A lowercase name in a type, such as a, stands for any type, so you don't declare it; the compiler works out what it is from the arguments. Types can take parameters too, like List a.

  






  
An interface names operations a type can support, like a TypeScript interface or a Scala trait. An instance says how one type does it. A function asks for one with [auto Describe a], and the compiler finds the instance from the type, so callers write nothing.

  






  
Every type you declare gets ==, an ordering (Ord.compare, List.sort) and text for ${...}, as long as its fields have them too. There is no deriving clause to write. Write your own instance when you want something different.

  






  
x.f y calls the function T.f where T is the type of x, so functions on a type read like methods. |> passes the value on its left as the first argument of the call on its right, as dot notation does. A leading dot, as in .name, is a short function: p => p.name.

  






  
A function that only takes its argument apart can be written as its cases: match | A => … | B => …. match some keeps only what matches, as Scala's collect does, and matches answers true or false. Any case may have a condition after its patterns, | n if n > 5 => …; when it is false, the cases below are tried.

  






  
There is no null: a value that may be missing has type Option a, which is Some value or None. Lists are written [1, 2, 3] and come with the usual map, filter, find, sum and many more, called with dot notation.

  






  
Some lists can never be empty: the people in a group, the numbers on a line. A NonEmptyList a says so in its type, so the functions that need a first element, such as maximum, last and reduce, return the value itself instead of an Option. Where the type says it is one, brackets write it, [1, 2, 3]; [] there is an error, and the pattern [first, ..rest] covers every value, with rest a plain List.

  






  
Map k v and Set k are ordered collections: they keep their keys sorted, so toList, keys and printing come out in a fixed order, and two maps with the same entries are equal. Insert, lookup and remove are logarithmic. They live in Std and need an import.

  






  
When a program keeps numbers by position and changes them in a loop (a table of counters, the cells of a board), use an Array. Reading and changing a position takes one step, and when nothing else holds the array, the change happens in place, with no copy. Advent of Code 2020 day 15, a memory game of thirty million turns that updates a table of positions, went from 357 seconds with a Map to 16 seconds with an array, with the same answer and the same proofs. An array is its list to a proof, so the list lemmas still apply. get gives an Option, getOr a fallback, and getLt a plain value when the index is known to be in range; nothing panics. It needs import Std (Array).

  

  
One thing to know: if you keep the old array and use it after a change, the change must copy it first. The answer is still right, but a run that does this many times on big arrays prints a note saying so at its end.






  
Names live in namespaces. The library is Std; a few things (Nat, List, Option, ==) are always in scope, and import Std (Option) brings in the rest of a namespace such as Option.map. A type owns a namespace (Item.cost), and a namespace Shop line at the top of a file puts the whole file in one. A project is a folder with a stitchwort.yaml of such files; try the Advent of Code entries in the Example menu to see one.

  






  
A test is a named Bool that must be True. The Tests tab runs them all, on the same fast runtime as Run; from a terminal, stitchwort test does the same for a whole project (--only NAME picks one test), and in VS Code the run icons and the Testing panel do it. Side effects are described, not hidden. An ability lists operations like say; a function that uses them says so in its type ({Log}), and a handler decides what they mean: print them, collect them, or run them in a test. The code that performs them is plain, straight-line code. IO (printing and reading input) is an ability too.

  






  
Each is an ability from the library for searching. each chooses an element from a list, require discards a combination that doesn't qualify, and Each.collect returns every combination that survives. It reads like nested loops with a filter.

  






  
Fail is an ability for giving up with a reason, so there are no exceptions and the type shows which code can fail. need takes an Option and fails if it is None; fail stops with a message; the handler toResult turns the outcome into Ok or Err. A main of type {IO, Fail} () may leave Fail unhandled: the message goes to standard error and the exit status is 1. That makes strict input parsing short: read every line, and a bad line stops the run saying which. (Abort is the same without a message.)

  






  
Parse is an ability for reading text. A parser is ordinary straight-line code: nat() reads a number, char 'x' a given character, and oneOf, optional and many choose and repeat. A runner such as Parse.eachLine gives it the input and turns a failure into a Fail that names the line and column and says what was expected there.

  






  
A function type can say {e} for "whatever effects the callback has". Pass it a pure function and the call is pure; pass it one that can fail and the call can fail, with the same definition. The library does this for List.map, whose callback may perform effects or none.

  






  
When a data type holds callbacks, its effects become a parameter of type Effects, just as an element type is a parameter of List. You never write an Effects value yourself; the compiler works it out from the functions you put in.

  






  
A theorem states a fact about your programs and the compiler checks the proof. rfl means "both sides compute to the same thing". For a fact about every value of a type, split on the cases like a function does; a call to the theorem on the smaller piece is the induction step.

  






  
A hypothesis can rule a case out. When, in some case, a hypothesis computes to an equation of two different constructors, such as False = True, that case can't happen: leave its arm out and the compiler fills it in, or write the arm with (), the pattern for a value that can't exist, and no =>.

  






  
A statement about every value reads ∀ (n: Nat) => P, or forall (n: Nat) => P in ASCII. It's the function type (n: Nat) -> P written another way: a proof is a function, and using one is a call. Goals show such statements with ∀.

  






  
A Bool test and the statement it decides are two views of one fact. A fact about a test, such as booking.fits capacity, can be taken apart with the patterns of its statement (Both for &&, Inl and Inr for ||) and built with its constructors. To use the whole fact as its statement, write .read. auto and cases use the facts in scope this way too.

  






  
For facts about whole numbers and integers built from +, -, comparisons, multiplication by constants, and division and remainder by a constant, omega finds the proof itself, using the hypotheses in scope.

  






  
Two ways to write longer proofs readably. calc is a chain of steps, each related to the one before (=, <=, <), each with its reason. rewrite p in t replaces, in the goal, the left side of the equation p by its right side, so you don't write out the expression around it. When a lemma takes functions as arguments, such as List.mapCong, write _ for them and the compiler reads them off the goal.

  






  
A recursive function comes with an induction principle shaped like its own equations: one case for each branch, with a hypothesis for each recursive call. match induct (f args) proves a statement about f by those cases, so a proof about a function with an if in it needs no case analysis of its own. The equations are theorems you can name too, such as countAbove.eq2.ifFalse.

  






  
In the editor, a ? is a place to start. With the cursor on it, the light bulb offers "Split on b" for each variable in scope whose type has constructors; picking one replaces the ? with a match and one ? for each case, each showing its own goal. Splitting another variable from the ? of one arm adds a column to that match rather than nesting a new one.

  






  
For a proof, a case with a condition is an if. Its equation takes the condition as a hypothesis, the cases below it take that it failed, and match induct splits at each condition. A condition that can be decided is stated as a proposition: n != 3 becomes n ≠ 3.

  






  
Comparisons chain, as in mathematics: lo <= x <= hi is lo <= x && x <= hi, and 0 <= i < xs.length says that i is a valid index. A middle that is a call is computed once, and in a proof the chain is the conjunction written out, so h.left and h.right are its two facts. Chains go one way (< and <=, or > and >=); a mixed one is an error that says what to write instead.

  






  
a ..< b is the numbers from a up to, not including, b, and a ..= b is the numbers from a through b. A range is an ordinary list, so .map, each, in and spreads all work on it. It binds more loosely than + and ++ and more tightly than ==, in and |>. In a proof, omega reads membership as the two bounds (List.memRange states it as a lemma). Write 0 ..< n, not [0 ..< n] (a list of one list) or 0 .. n (an error).

  






  
A handler applied to code it can see through just computes, so a proof about it is often rfl. For a fact about any computation, match reify t with splits on what the computation does first, with the clauses written as a handler's. It works only in proofs, so programs can never take a computation apart.

  






  
Functions must terminate, since that is what makes proofs about them meaningful. Recursion on a piece of an argument is accepted as written; otherwise name the number that shrinks with decreasing. A decreasing function still runs and tests like any other.

  






  
Declarations can come in any order, so main can come first and its helpers below. Definitions may call each other, and types may refer to each other; the compiler checks them together and still requires every cycle of calls to get smaller.

  






  
A type may mention values. Vec a n is a list whose length n is part of its type, so Vec.head can only be given a non-empty vector and Vec.zipWith only vectors of the same length. Mistakes like these become compile errors rather than runtime checks.

  






  
export on a definition makes it part of a generated ES module with TypeScript declarations (the JavaScript tab shows both). Records become plain objects, variants become objects with a tag, Nat is a bigint, and Option a is a | undefined. SafeNat is a whole number that fits a JS number. When a function asks for a proof the caller can't supply, such as percent <= 100, the generated code checks it when called and throws StitchwortInputError. The declarations for the example below:

  

  
export type Profile = { readonly name: string; readonly nickname?: string };
export declare function displayName(p: Profile): string;
export declare function toNumber(n: bigint): number | undefined;
export declare function percentOf(percent: bigint, total: bigint): bigint;
